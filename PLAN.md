# Markdown-backed Daily Tasks + Journal App

> This is the living design doc for this project. For build status/what's done vs. not, see [PROGRESS.md](PROGRESS.md). For working conventions when picking this project up, see [CLAUDE.md](CLAUDE.md). Update this file (not a copy of it) whenever the design changes.

## Context

The user wants a personal daily-tasks/journal system stored entirely as plain markdown files: task files grouped by project, journal/daily notes bucketed by year. Existing tools (Obsidian, Logseq, Dendron, org-mode/org-journal, Foam, SilverBullet) all approximate this but none match the exact layout without heavy plugin config or accepting a different file-per-unit convention, so the user chose to build a custom local web app (Node.js + React).

Beyond the original CRUD scope, the user wants tasks and projects to carry real detail (descriptions, creation time, time-spent tracking), projects to be visually taggable (color) for a calendar, journal entries to reference the tasks worked on that day, and is open to SQLite for performance — **on the condition that the markdown files remain the portable, user-owned source of truth**; SQLite may only be a derived, rebuildable cache, never a place where data lives that isn't also in the `.md` files.

The user also wants AI agents (Claude Code, Claude Desktop, or any other MCP client) to be able to manage and summarize tasks/journals directly — decided via **MCP**, not a custom in-app chat feature: the app exposes a local MCP server with full read+write tools, so any MCP host supplies its own agent loop, model, and UI for free. Because that grants agents full read+write, the data itself needs an independent undo mechanism (git-backed, see Backup & recovery) so an unwanted agent edit is always reversible.

Finally, like Obsidian, the user wants **multiple workspaces** — any folder on disk can be opened as a workspace — plus the ability to **push a workspace's git history to a remote**, and a design that doesn't foreclose adding other cloud-sync backends (Google Drive, WebDAV, etc.) later.

**Direction change: this is now an Electron desktop app, not a browser-opened web app.** Two things needed a real OS integration that a browser tab can't provide: a native folder picker for "open workspace" (rather than the browser-tab workaround originally planned — a pasted path), and a daily reminder delivered as a native OS notification, reliably, even when the app window isn't open (which needs a tray icon + optional start-at-login). See **Desktop shell (Electron)** and **Daily reminder** below. This is a thin wrap, not a rewrite — the Express server, service layer, REST API, SQLite index, git backup, and MCP server designs below are unchanged; Electron's main process just launches that same server locally and points a `BrowserWindow` at it.

The working directory (`/home/lap16152/Documents/Code/poco`) currently has only an empty scaffold (`package.json`, `.gitignore`, empty dirs) plus a `design/` folder (a UI prototype canvas, see [design/README.md](design/README.md)) — nothing implemented yet.

## Workspaces

A **workspace** is any folder on disk containing (or about to contain) a vault — exactly Obsidian's model: you point the app at a folder, it becomes self-contained there.

- **App-level registry**: `~/.poco/config.json` (outside any workspace, since the app needs to know the workspace list *before* opening one) — `{ workspaces: [{ id, path, name, lastOpenedAt }], activeWorkspaceId }`.
- **Per-workspace hidden directory**: `<workspace>/.poco/` (mirrors Obsidian's `.obsidian/`), holding:
  - `cache/index.sqlite3` — the SQLite index (WAL mode), scoped to that workspace only.
  - `backups/vault-<date>.zip` — periodic snapshots (see Backup & recovery).
  - This directory is added to the workspace's own `.gitignore` (it's a cache, not content) but otherwise travels with the folder if copied — opening a copied/moved workspace elsewhere just works, or self-heals via reconciliation if `.poco/` didn't come along.
- **Adding a workspace**: `POST /api/workspaces {path, name?}` — validates the path exists (or offers to create it), is readable/writable, scaffolds `.poco/` and `projects/`/`journal/` subfolders if missing, `git init`s it if not already a repo, and registers it. Opening an *existing* folder that already has content just adopts it (like Obsidian's "Open folder as vault").
- **Switching**: `POST /api/workspaces/:id/open` closes the previous workspace's SQLite connection and git context, points everything at the new path, and runs index reconciliation for it. **One workspace is active at a time per running server** (matching how you actually use Obsidian day to day); running two workspaces open simultaneously means running two instances of the server on different ports — not needed for v1.
- **Removing**: `DELETE /api/workspaces/:id` un-registers it only — never deletes the folder or its content, same as Obsidian's "Remove from list."
- Aggregates/reports are always scoped to the single active workspace; there's no cross-workspace query surface (again, matches Obsidian — each vault is independent).
- **MCP is decoupled from "whichever workspace the app has open"**: each MCP server registration takes an explicit workspace path (`POCO_WORKSPACE=<path>` env var, or defaults to the registry's `activeWorkspaceId` if omitted) at launch, so an agent's target vault is deterministic and doesn't change underneath a conversation just because someone switched vaults in the app.
- **Folder picker**: a native OS picker (`dialog.showOpenDialog({properties:['openDirectory']})`, in the Electron main process), not a pasted path — see Desktop shell below. The renderer's "+ Open folder" button calls this via the preload bridge, then hands the returned path to the existing `POST /api/workspaces {path, name?}` — the workspace API itself doesn't change at all, only how the path is obtained.

The existing `vault/` directory already created under the repo becomes just a convenient default/dev workspace, not a hardcoded runtime path — nothing in the app code assumes a fixed vault location once workspace management ships.

## Desktop shell (Electron)

A thin wrap around the already-designed server + client, not a rewrite:

- **Main process** (`electron/src/main.ts`) launches the existing Express server bound to `127.0.0.1` on a free local port (no external network exposure), waits for it to be ready, then opens a `BrowserWindow` pointed at it — in dev, at the Vite dev server URL with the API proxied to the embedded server; in production, at the server's own URL, which also serves the built client static files. **No IPC rewrite of the REST API** — the renderer keeps talking to `/api/...` exactly as designed; Electron only adds native-OS affordances the browser couldn't provide.
- **Preload script** (`electron/src/preload.ts`, `contextBridge` + `contextIsolation: true`, no `nodeIntegration` in the renderer) exposes a minimal `window.poco` surface: `pickFolder()` → wraps `dialog.showOpenDialog`, returns the chosen path or `null`; `getLaunchAtLogin()` / `setLaunchAtLogin(bool)`; `getReminderSettings()` / `setReminderSettings({time, enabled})` for the active workspace; `openWorkspaceFolder(path)` → reveals a workspace folder in the OS file manager; `canCreateDesktopEntry()` / `isDesktopEntryInstalled()` / `setDesktopEntryInstalled(bool)` → Settings' Linux-AppImage-only "Add to applications menu" toggle (`electron/src/desktopEntry.ts`). Everything else the client needs still goes over HTTP to the embedded server.
- **Window lifecycle**: closing the window hides it (`event.preventDefault()` + `win.hide()`) rather than quitting — the app keeps running via the tray (see Daily reminder) so the scheduler stays alive; the tray menu's "Quit" is the only real quit path, which cleanly stops the embedded server first.
- **Single instance**: `app.requestSingleInstanceLock()`, called before anything else in `main.ts` — a second launch attempt (double-clicking the AppImage again, a second Start Menu/Dock click, launch-at-login racing a manual launch) quits immediately instead of spawning a second embedded server/tray/reminder-scheduler against the same workspace; the already-running instance's `second-instance` event just shows/focuses its existing window.
- **Packaging**: `electron-builder`, configured in a new `electron/` npm workspace (own `package.json`, `electron` + `electron-builder` deps) — per-OS installers (dmg/nsis/AppImage) are future polish, not required for local development (`npm run dev` can launch Electron directly against the dev server without packaging).
- Using `node:sqlite` (not a native module) means there's no Electron-ABI rebuild step for the index — this was already anticipated and is why that library was chosen.

## Daily reminder

A native OS notification nudging the user to write today's journal entry if they haven't yet — scoped to whichever workspace is currently active in the running app.

- **Tray + background running, with an opt-out**: a tray icon keeps the app alive after the window is closed, so the reminder fires reliably even on a day the user never opens the window. **Start-at-login is on by default but user-toggleable** (`electron/src/loginItem.ts`, wraps `app.setLoginItemSettings`) — a "Launch at login" switch in Settings, persisted as `launchAtLogin: boolean` in `~/.poco/config.json`. Turning off start-at-login does not disable the tray — the app still stays alive for the rest of the current session once opened, it just won't auto-start next time the OS boots.
- **Per-workspace reminder time**: each workspace registry entry (`~/.poco/config.json`) gains `reminderTime: "HH:MM" | null` (24h local time; `null` = disabled for that workspace), editable in Settings, default `"20:00"` on a newly-added workspace.
- **Scheduler** (`electron/src/reminder.ts`): a main-process interval, checked once a minute, comparing local wall-clock time against the active workspace's `reminderTime`. Fires only if (a) it matches, (b) a `lastReminderFiredDate` field on that workspace entry isn't already today's date (prevents refiring within the same minute or after waking from sleep past the time), and (c) today's journal entry for that workspace has no body yet (skip silently if the user already journaled today — a smart no-op, not a nag). On fire: `new Notification({title: 'Time to journal', body: "You haven't written today's entry yet"})`, `lastReminderFiredDate` updated to today; clicking the notification shows/focuses the window and navigates to `/journal`.
- Native `Notification` API (Electron's own cross-platform wrapper over each OS's notification center) — no extra notification library needed.

## Storage format (paths below are relative to whichever workspace is active)

### Project file — one per project, `<workspace>/projects/<slug>.md`

Frontmatter (native YAML via `gray-matter`) carries project metadata; slug comes from the filename, never stored in frontmatter.

```markdown
---
name: "Website Redesign"
created: 2026-09-10
archived: false
description: >
  Full redesign of the marketing site, launching alongside the
  Q4 product announcement.
group: "Marketing"
color: "#4f86f7"
---

- [/] Draft new homepage copy @due(2026-09-20) @created(2026-09-08T09:15:00Z) @doingSince(2026-09-10T13:00:00Z) @spent(2h15m) #content <!-- id:t_9f0e21 -->
  - [x] Get sign-off on tone from marketing
  - [ ] Write final copy
  Marketing wants a warmer tone than the old site. Pull inspiration from
  the Q3 brand deck before writing final copy.

  Check with Linh about the hero image licensing before this goes live.
- [x] Buy domain name @due(2026-08-01) @created(2026-07-20T10:00:00Z) @done(2026-08-01) <!-- id:t_1122aa -->
```

**Color**: server auto-assigns from a fixed 12-color palette at project creation (cycled by creation order) and always writes it to frontmatter — never left to client-side hashing, so every consumer (calendar marks, badges) reads one authoritative field. Editable via a color-picker in the project form.

**Group** (milestone 26, replaces the earlier per-project `tags`): every project belongs to exactly one group — a free-text field, not a fixed managed list — left blank at creation or edit, it falls back to `DEFAULT_GROUP` ("Default"), same normalization on read for a hand-edited file with no `group` field at all (`lib/markdown/project.ts`'s `parseProjectFile`). The project form's group field is a combobox (an `<input list=…>` + `<datalist>`, not `TagInput`) suggesting every group name already in use plus "Default", so picking an existing group is as easy as typing a new one. A task has no group field of its own — it inherits its project's group purely at read/query time (`IndexedTask.projectGroup`, joined in `lib/index/queries.ts`'s `TASK_JOIN_SELECT`), never stored redundantly on the task line. Projects no longer carry `tags` at all (removed, not just superseded) — the project-level tag filter/pills are gone from every page; task-level `#tag`s (PLAN.md's "Task line grammar" below) are unrelated and unaffected.

**Task line grammar** — checkbox marker is status (`[ ]` todo, `[/]` doing, `[x]` done). Inline tokens, always re-emitted in this fixed order on write (parser accepts any order/whitespace on read):

```
@due(YYYY-MM-DD) → @created(<ISO8601 UTC>) → @doingSince(<ISO8601 UTC>) → @spent(<Xd><Yh><Zm>) → @done(YYYY-MM-DD) → #tag(s) → <!-- id:t_xxxxxxxx -->
```

- `@created(...)` — set once at creation, never rewritten.
- `@doingSince(...)` — present only while `status == doing`; added the instant a task enters doing, removed (folded into `@spent`) the instant it leaves.
- `@spent(...)` — cumulative time-in-doing, compact human format (`2h15m`, `45m`, `3h`, `1d2h15m`, `3d`), omitted entirely when zero. A day is a flat 24h (no calendar/timezone awareness) purely to keep a long-running task's total readable instead of growing into triple-digit hour counts.
- **Time tracking is automatic, tied to status**: moving a task to `[/]` doing starts the implicit timer (`@doingSince` = now); moving it away (to done or back to todo) computes elapsed time and adds it to `@spent`, then clears `@doingSince`. No separate start/stop control. `@doingSince` is a durable file field, so elapsed time is computed correctly even across a server restart while a task was left in doing.
- `#tag`(s) — zero or more, also used for priority (e.g. `#high`).
- `<!-- id:t_xxxxxxxx -->` — stable id in an HTML comment, assigned once via `crypto.randomUUID()`.
- **Description**: multi-line/multi-paragraph free text as indented continuation lines (2-space indent) directly beneath the checkbox line; blank indented lines preserve paragraph breaks; the block ends at the first non-indented line (naturally the next checkbox line or other body content). Non-checkbox, non-description body lines are preserved verbatim — the parser is non-destructive to content it doesn't understand.
- **Checklist (sub-tasks)**: zero or more plain nested GFM checkboxes (`  - [ ] ...` / `  - [x] ...`, one 2-space indent level, immediately beneath the checkbox line and before the description) — deliberately lightweight compared to a top-level task: just text + done, no `@due`/`@tags`/`<!-- id -->`/time-tracking of its own, so it stays a quick hand-editable checkbox rather than a second copy of the task-line grammar. Addressed by array position (no stable id), since the only mutation path is a full-array replace (`checklist` on `PATCH .../tasks/:taskId` and the `update_task`/`create_task` MCP tools) — same convention as `tags`. No blank line separates the checklist block from the description that may follow it (matches the existing checkbox-line-to-description precedent above); the parser tells them apart structurally (checklist lines are checkbox-shaped, description lines aren't), not by a blank-line boundary.

### Journal file — one per day, `<workspace>/journal/<YYYY>/<YYYY-MM-DD>.md`

```markdown
---
date: 2026-09-10
tags: []
linkedTasks: [t_a1b2c3, t_9f0e21]
---

Freeform markdown body, unparsed.
```

`linkedTasks` is a plain array of task ids, insertion-ordered, deduped on add. Year folder created on demand.

### Note file — one per note, `<workspace>/notes/<slug>.md`

```markdown
---
title: "Reading list"
created: 2026-09-14T09:47:01.639Z
updated: 2026-09-14T09:47:01.715Z
tags: [books]
---

Freeform markdown body, unparsed — same convention as journal entries.
```

A flat collection of standalone markdown files with metadata (tags, created/modified) — the simplest of the three content types: no per-line grammar (unlike tasks), no date-bucketed folder (unlike journal entries), no color/archived state (unlike projects). `created`/`updated` are full ISO8601 UTC timestamps (not bare dates) — `created` set once, `updated` rewritten on every write, both server-managed, never hand-set by the client.

**Slug**: derived from `title` via the same `slugify()` projects use, but *not* re-derived automatically on a later title edit — the filename is assigned once at creation from the title and otherwise stays fixed, exactly like a project's slug. Unlike a project (which rejects a duplicate name outright, PLAN.md's "Color" section's sibling rule), a colliding note title auto-suffixes (`meeting-notes`, `meeting-notes-2`, `meeting-notes-3`, ...) rather than erroring — a note's title is far more likely to be reused verbatim ("Meeting notes", "Ideas") than a project's, and forcing a rename before creation would be needless friction for something this disposable to create.

**Renaming the file** (added shortly after the initial build, at the user's request — "allow edit note file name. I don't want they always be untitled-note-x"): `PATCH /api/notes/:slug` and the `update_note` MCP tool both accept an optional `newSlug`, a deliberate, explicit rename distinct from `title` — the only way to change a note's filename after creation, since it still never follows an ordinary title edit automatically (an automatic re-slugify-on-every-title-keystroke was considered and rejected: it would fire a file rename/git commit on every autosave debounce tick while retitling, and any external reference to the old path would break silently and repeatedly rather than once, deliberately). `newSlug` is sanitized through the same `slugify()` creation uses; renaming onto an already-existing slug **rejects with a 409** rather than auto-suffixing like creation does — a rename's target is a specific, deliberate choice the caller made, so silently substituting a different one would be surprising in a way that creation's auto-disambiguation (picking *some* unique slug for an otherwise-arbitrary default title) isn't. The rename is a real file move: the service writes the new path, removes the old one, and stages both in one commit (`rename_note <old> -> <new>`) — git's own diff/`log --follow` detects this as a rename, same as a plain `git mv` would. On the frontend, `NoteDetailPage`'s filename is a small, muted, click-to-edit control (shown as `notes/<slug>.md`) separate from the continuous title/tags/body autosave — it commits only on blur/Enter, not per keystroke, folds in whatever title/tags/body edits were still pending in the autosave debounce (so a stale autosave never fires against the now-removed old path), and on success navigates to `/notes/<newSlug>` (the route remounts the page, same as switching between two different notes already does). The slug otherwise stays filename-only, never the note's *displayed* identity elsewhere in the UI — `title` is what every other view (the notes list, search, etc.) shows.

**Indexing**: notes get their own `notes` table (slug, title, created, updated, tags — reconciled the same stat-diff way as projects/journal). Like journal entries, **the index never caches note body text** — only `getNote`/`loadNoteFile` (direct file reads) ever see the body; `GET /api/notes` and search are metadata-only. This means note search (`GET /api/notes?q=`, and the `list_notes` MCP tool's `query`) matches title/tags only, not body content — the same trade-off journal entries already accepted for the same reason.

**Frontmatter timestamp quirk**: a full ISO8601 datetime scalar left unquoted (exactly how a human would hand-type `created: 2026-09-14T09:15:00.000Z`) triggers the same YAML 1.1 auto-Date-coercion as a bare `YYYY-MM-DD` date (see "Frontmatter date normalization" in PROGRESS.md's decisions log) — `lib/markdown/frontmatter.ts`'s `normalizeYamlDates` now only slices a coerced `Date` down to `YYYY-MM-DD` when it lands exactly on UTC midnight (a bare-date field's only possible value); any other time-of-day is preserved as a full ISO string. App-written files are unaffected either way (gray-matter/js-yaml always quotes a string that would otherwise round-trip as a `Date`, confirmed by the existing `journal-sample.md`/`project-sample.md` fixtures) — this only matters for a hand-edited, unquoted value.

**Routes**: `GET /api/notes` (metadata list, or `?q=` to search title/tags — one route for both, since they return the same shape), `POST /api/notes`, `GET/PATCH/DELETE /api/notes/:slug` (`PATCH` is full-replace-on-provide, same `undefined` = leave alone convention as `updateProject`).

**MCP tools**: `create_note`, `update_note`, `delete_note`, `get_note`, `list_notes` (optional `query` does the same title/tag search as the REST route's `?q=`) — full read+write parity with the REST API from the start, same as every other content type (PLAN.md "Agent access via MCP").

**Frontend**: `/notes` (list, most-recently-updated first; client-side title-substring + tag-pill filtering over the full loaded list, same reasoning as `/projects`'s tag filter; "+ New note" navigates to `/notes/new`, a draft page — see below — rather than skipping straight to a real, already-created note) and `/notes/:slug` (title/tags/body all autosave-debounced together, reusing the exact `MarkdownEditor` + autosave-interval-preference + dirty-tracking-via-explicit-handlers pattern `JournalDayPage` established, plus a delete button, a filename-rename control, and the standard `HistoryPanel`). A new "Notes" nav item sits between Projects and Journal in `AppShell`.

**`/notes/new` — a draft that isn't a file yet** (added shortly after the initial build, at the user's request — "don't create new note file before user edit anything": "+ New note" originally called `create_note` immediately on click, so opening the page and leaving without typing anything still left behind an `untitled-note-N.md` file and a git commit every time). This route renders a distinct, lightweight page (no fetch, no delete button, no filename control, no `HistoryPanel` — there's nothing yet for any of those to act on) holding its own local title/tags/body state. The first actual edit to any of the three starts the same debounce `NoteDetailPage`'s autosave uses; when it fires, that's the point the note is finally created for real, via `createNote` (there's no slug yet to `updateNote`). On success, the page navigates to `/notes/<newSlug>` — from then on it's an ordinary `NoteDetailPage`, the same "hand off once a slug exists" pattern the filename-rename flow (below) already uses. Leaving the page (in-app navigation, not a hard browser close/reload — no client-side code can intercept that) before the debounce fires still flushes whatever was actually typed, same reasoning as every other autosave-flush-on-unmount in this app; leaving genuinely untouched creates nothing at all, which is the point. `new` is reserved (`RESERVED_SLUGS` in `services/notes.ts`) so a note titled "New" can never legitimately slugify to `new` and collide with this route — React Router ranks a literal path segment over a dynamic `:slug` one regardless of declaration order, so an unreserved collision would make that note permanently unreachable by direct URL, shadowed by the draft page.

**Preview mode** (added shortly after the initial build, at the user's request — "add md preview for note body"): an Edit/Preview segmented toggle above the body, same `.ws-row-btn`/`.is-active` pattern `CalendarPage`'s due/journal toggle already established. Preview renders the body to real HTML via `markdown-it` (`client/src/lib/renderMarkdown.ts`) — deliberately **not** reopening the "Journal editor" section's settled decision against a rendered/Obsidian-style view for the journal body; notes get their own separate mode instead, chosen explicitly via `AskUserQuestion` (edit↔preview toggle vs. an always-on split view vs. "no, the existing syntax coloring is enough") rather than assumed. Configured `html: false` (raw HTML in the source is escaped as literal text, not parsed/injected) since a note body is effectively untrusted input — freely writable by an MCP agent or an external sync tool — and this renders straight into `dangerouslySetInnerHTML`; `linkify: true` auto-links bare URLs, matching the editor's own GFM dialect. Rendered typography (`.note-preview` in `app.css`) reuses the same `--md-heading`/`--md-link`/`--md-quote`/`--md-code`/`--md-code-bg` tokens `MarkdownEditor`'s `HighlightStyle` uses, so headings/links/quotes/code read as the same colors in both modes.

## Backend (Express + TypeScript)

`gray-matter` for all frontmatter; a hand-rolled regex/line-based parser for the task-line grammar (not remark/unified — the custom tokens aren't a native markdown construct, and a small regex module is simpler and easier to unit-test). `date-fns` for date math. `crypto.randomUUID()` for ids.

All business logic (task/project/journal read-modify-write, doing-timer transition, index upsert, git commit) lives in plain **service functions** (`server/src/services/*.ts`), not inside Express handlers — both the REST routes and the MCP server call the same functions, so there is exactly one implementation of "what a status change does." Every service function operates against the currently-active workspace context (or, for MCP, the workspace it was launched against).

### SQLite index layer (derived cache, not source of truth)

**Library**: `node:sqlite` (`DatabaseSync`, built into Node ≥22.5 — no npm dependency, no native module to rebuild for Electron later). Ruled out `sql.js` specifically because it has no real file-backed persistence (in-memory + manual whole-buffer serialize/reload), which can't support two separate processes (Express + MCP) concurrently reading/writing the same file the way WAL mode does; ruled out `better-sqlite3` only because it's a native module requiring an Electron-ABI rebuild step later, which `node:sqlite` avoids entirely for equivalent functionality at this app's scale. `node:sqlite` is still Node-experimental — isolate all access behind `lib/index/db.ts` so a future API shift (or a switch back to better-sqlite3, e.g. for FTS5 full-text search) is a contained, single-file change.

**Location**: `<workspace>/.poco/cache/index.sqlite3` — one index per workspace, gitignored within that workspace. Deleting it and reindexing must always reproduce identical query results from a clean scan — this is the hard portability constraint. Schema (sketch): `projects`, `tasks` (FK → project slug, includes `description`, `due`, `created_at`, `done_at`, `doing_since`, `spent_minutes`, `tags` JSON), `journal_entries` (`has_body` flag, `tags` JSON), `journal_task_links` (date, task_id), `index_meta`. Each file-backed table carries `source_mtime`/`source_hash` for staleness bookkeeping. Opened in **WAL mode** so the Express server and a concurrently-running MCP server process (pointed at the same workspace) can both read/write it without lock contention.

**Sync strategy — reconciliation, not blind reparsing** (a full reparse-everything rebuild on every boot scales badly and is wasted work when nothing changed):
- **Startup/open-time reconciliation** (runs whenever a workspace is opened, not just process boot): walk the workspace directory tree doing only `readdir`/`stat` (no file content read), compare each file's `mtime`/size against what's stored in the index from last time. Only **read and parse** files that are new or changed (this is also what picks up hand-edits made while the server was off, or changes an external sync tool — see Remote & cloud sync — made to the folder). Delete index rows for files that no longer exist. On a normal reopen with nothing changed, this is just stat calls — no parsing, effectively instant. Still exposed as `POST /api/index/rebuild` for an explicit forced full reparse. **This was documented from the start but not actually wired in until a real bug surfaced it** (milestone 25 follow-up): every other reconcile call in this codebase fires from a *write* path (`services/{tasks,notes,journal,projects,sync}.ts`), so a workspace that was already open before an index-schema/cache change (e.g. milestone 25's `body`/FTS columns) — with no note/task/journal write happening on it since — silently kept an empty/stale cache for that new field, and a plain process restart re-activated the same workspace without ever calling `addWorkspace`/`openWorkspace` again either. Fixed by adding the missing calls: `services/workspaces.ts`'s `addWorkspace`/`openWorkspace` now reconcile on the way out (best-effort, same as every write path), and `index.ts`'s `startServer` reconciles whatever workspace is already active right after the HTTP server starts listening — covering "process boot" specifically, not just "a workspace gets opened/switched while already running."
- **Non-blocking**: the HTTP server starts listening immediately; reconciliation runs asynchronously right after boot or workspace-switch. File-backed routes (single project/journal read, task CRUD) work immediately since they never depend on the index. Aggregate endpoints return `503` with an "indexing…" body for the brief window before reconciliation finishes.
- **Incremental upsert-on-write**: every mutating service function re-uses the structured object it just wrote to disk to also upsert the index row(s) in the same call, immediately after the file write succeeds. Best-effort — if it throws, log and continue; the file write already succeeded and is authoritative, the index self-heals on the next reconciliation.
- **Write path, always in this order**: read file → parse → mutate (incl. doing-timer logic) → serialize → **write file (durable, authoritative step)** → upsert index row(s) (best-effort) → git commit (best-effort, see Backup & recovery) → return the in-memory structured form (never re-read the DB to respond).
- **Which reads go where**: single-project, single-journal-entry, and all task CRUD always read the source file directly (never stale, regardless of index state). Aggregate/cross-file views (`/api/tasks/open`, `/api/calendar/:year/:month`, `/api/tasks/:taskId/journal-links`, `/api/tasks/search`, `/api/reports/time-spent`, `/api/journal/:year` listing) read from the index — documented trade-off: only these can show stale data if the workspace is hand-edited (or externally synced) while the server is running; they self-correct on next reconciliation or a manual reindex.

### Routes

- Workspaces: `GET /api/workspaces`, `POST /api/workspaces`, `POST /api/workspaces/:id/open`, `DELETE /api/workspaces/:id`, `GET /api/workspaces/active`.
- Projects: `GET/POST /api/projects` (create accepts `description`, `group` — blank falls back to "Default" — `color`, else auto-assigned), `GET/PATCH/DELETE /api/projects/:slug`.
- Tasks: `POST /api/projects/:slug/tasks` (accepts `description`, `checklist`; server sets `createdAt`, `spentMinutes=0`), `PATCH /api/projects/:slug/tasks/:taskId` (status changes trigger the doing-timer transition logic; also updates `text`/`description`/`due`/`tags`/`checklist` — `checklist`, like `tags`, is a full-array replace, not an index-addressed add/toggle/remove; an optional `afterTaskId` reorders the task — `null` moves it to the front of the project file, a task id moves it to immediately after that task's block — backing the Kanban drag-and-drop described under milestone 18), `DELETE .../tasks/:taskId`.
- Journal: `GET /api/journal/:year`, `GET/PUT /api/journal/:year/:date` (PUT accepts `linkedTasks` full-replace), `POST /api/journal/:year/:date/links/:taskId` (idempotent add, auto-creates the day's file), `DELETE .../links/:taskId`.
- Notes: `GET /api/notes` (metadata list, or `?q=` to search title/tags), `POST /api/notes`, `GET/PATCH/DELETE /api/notes/:slug`.
- Aggregates: `GET /api/tasks/open`, `GET /api/tasks/:taskId/journal-links`, `GET /api/tasks/search?q=` (matches task text, description, *and* tags — one query for "search by text or tags", milestone 18), `GET /api/calendar/:year/:month`, `GET /api/reports/time-spent?groupBy=&from=&to=&includeInProgress=`, `GET /api/search?q=&from=&to=&types=` (milestone 25, cross-type full-text — see "Search (cross-type full-text)" below).
- Index/misc: `POST /api/index/rebuild`, `GET /api/index/status`, `GET /api/vault/status`.
- Backup/history: `GET /api/vault/history?path=&limit=`, `GET /api/vault/diff/:commit`, `POST /api/vault/revert/:commit`.
- Remote sync: `GET/PUT /api/vault/git/remote`, `POST /api/vault/git/push`, `POST /api/vault/git/pull`, `GET /api/vault/git/status` (see Remote & cloud sync).

**Doing-timer transition** (inside the task status PATCH handler / service function):
```
if newStatus == task.status: return task   # no-op guard, avoids double counting
if task.status == 'doing':
  task.spentMinutes += minutesBetween(task.doingSince, now)
  task.doingSince = null
if newStatus == 'doing': task.doingSince = now
if newStatus == 'done': task.doneAt = today
else if task.status == 'done': task.doneAt = null
task.status = newStatus
```
The live "N (tracking...)" value shown in the UI is computed client-side (`spentMinutes + elapsed-since-doingSince`, ticking locally); the file's `@spent` token only updates on an actual status transition, never on a timer tick, to avoid write amplification.

## Backup & recovery (git-backed workspace)

Since MCP grants agents full read+write, the write path needs an undo mechanism that doesn't depend on the connecting agent's host catching a bad edit before it happens.

**Mechanism: each workspace is its own git repository, managed entirely by the app.**

- On workspace add/open, if `<workspace>/.git` doesn't exist, `git init` it and make an initial commit of whatever's already there.
- Every mutating service-function call commits the changed file(s) right after the file write succeeds, with a self-documenting message: `[origin] action target`, e.g. `[mcp:update_task] t_9f0e21 status doing→done (website-redesign)`, `[api] create_journal_entry 2026-09-10` — history always shows whether a human (web UI) or an agent (and which MCP tool) made a change.
- Best-effort, same footing as the SQLite upsert: if git isn't installed or a commit fails, log and continue — the file write already succeeded and is authoritative; versioning is a safety net, not a dependency for the app to function.
- Because it's a plain git repo, the user can always recover with nothing but a terminal (`cd <workspace> && git log`/`git diff`/`git revert`) — no dependency on the app's own UI.

**Recovery surface**: `GET /api/vault/history?path=&limit=`, `GET /api/vault/diff/:commit`, `POST /api/vault/revert/:commit` (`git revert --no-edit <commit>` — a new undo commit, not a rewrite of history, so it's safe even with later commits on top — followed by reconciling the index for the affected file(s)). Plus a small **History panel** on project detail and journal day pages: recent commits touching that file, each with a one-click "Undo this change."

**Belt-and-suspenders**: a periodic full snapshot to `<workspace>/.poco/backups/vault-<date>.zip` (daily, keep the last ~14) — cheap insurance against the git repo itself being deleted/corrupted; git history is still the primary recovery path.

## Remote & cloud sync

Two genuinely different sync models, both enabled by the workspace-is-a-folder + workspace-is-a-git-repo design above:

**1. Git remote push/pull (active, explicit) — built in v1.**
- `GET/PUT /api/vault/git/remote` — read/set the `origin` remote URL (`git remote add|set-url origin <url>`).
- `POST /api/vault/git/push`, `POST /api/vault/git/pull`, `GET /api/vault/git/status` (ahead/behind counts, dirty state, last sync time).
- No credential management is built — pushing/pulling shells out to plain `git`, so it relies on whatever credential helper/SSH key the user's own git setup already has (same as running `git push` from a terminal). This keeps the app out of the business of storing secrets.
- **Conflicts are surfaced, never auto-resolved**: on a pull that would conflict, return the list of conflicted files as a structured error rather than attempting a merge — these are personal notes and task files, and a bad auto-merge could corrupt the task-line grammar; the user resolves conflicts with normal git tooling (or the History/diff UI) and pulls again.
- Designed as a `SyncProvider` interface (`server/src/lib/sync/types.ts`: `push`, `pull`, `status`) with `gitRemote.ts` as the only v1 implementation, and the workspace registry entry storing `sync: { provider: 'git-remote', remoteUrl } | { provider: 'none' }` — a later provider (see below) slots into the same interface without touching the workspace/vault model.

**2. Passive filesystem sync (Google Drive, WebDAV, Dropbox, Syncthing, …) — works today, zero code needed.**
Because a workspace is just "any folder," the user can already point one at a folder that an external tool keeps synced (a mounted WebDAV share, a Google Drive/Dropbox desktop-sync folder, etc.) — the app doesn't need to know or care that this is happening. Two things make this safe rather than build features for it:
- The app already tolerates files changing underneath it (that's exactly what reconciliation is for).
- The vault scanner should **ignore/skip files that don't match the expected naming pattern** rather than erroring — this specifically covers sync-conflict artifacts these tools create (e.g. `task-list (conflicted copy 2026-09-10).md`).
A future first-class Google Drive/WebDAV `SyncProvider` (API-driven push/pull, like the git-remote one, rather than "just point a folder at a sync client") can be added later behind the same interface if that's ever wanted — not needed for v1.

## Agent access via MCP (Claude Code, Claude Desktop, etc.)

Instead of a custom in-app chat feature backed by an OpenAI-compatible API, the app ships a local **MCP server** so any MCP-capable agent becomes the chat/management interface for free — no server-side agent loop, model config, or chat UI to build.

- **Transport**: stdio, a standalone process (`server/src/mcp/index.ts`, built with `@modelcontextprotocol/sdk`), registered with an MCP host via `claude mcp add` or `.mcp.json` — no network port, no auth to manage. Takes an explicit target workspace (`POCO_WORKSPACE=<path>` env var, defaulting to the app registry's active workspace if omitted) so an agent's vault doesn't silently change if someone switches workspaces in the browser mid-conversation.
- **Tools — full read+write**, each a thin wrapper over the same service functions the REST routes use: `create_task`, `update_task`, `delete_task`, `search_tasks`, `list_open_tasks`, `create_project`, `update_project`, `list_projects`, `get_project`, `upsert_journal_entry`, `get_journal_entry`, `link_task_to_journal`, `unlink_task_from_journal`, `create_note`, `update_note`, `delete_note`, `get_note`, `list_notes` (optional `query` for a title/tag search), `get_task_summary({projectSlug?, dateRange?, status?})` returning structured aggregates — the calling agent narrates the summary itself, no summarization logic needed server-side — and `search_everything({query, dateRange?, types?})` (milestone 25, see "Search (cross-type full-text)" below), a cross-type full-text search over task/note/journal/project body content combined with an optional date range, which none of the other tools do together.
- **Concurrency**: the MCP process and the Express process may open the same workspace's `index.sqlite3` directly — this is exactly why WAL mode is required. Each process does its own read-modify-write directly against the workspace's files, same as any two writers of a text file — WAL mode covers the *index*, not the markdown files themselves, which have no equivalent protection; see milestone 22 (deliberately deferred, not yet designed).
- **Errors are structured and returned to the model** (e.g. "no project with slug X, did you mean: ..."), so the agent can self-correct rather than fail silently.
- **Self-serve setup**: `/settings`' "Agent access" section (milestone 18) generates copy-pasteable config for the standalone entrypoint above — a Claude Desktop `claude_desktop_config.json` snippet, a Codex CLI `~/.codex/config.toml` snippet, and a `claude mcp add` one-liner — built from `GET /api/system/mcp-info`'s absolute entrypoint path, so a user never has to hand-derive it. For a packaged Linux AppImage install specifically, the snippet also carries `DISPLAY`/`DBUS_SESSION_BUS_ADDRESS` (read from the running server's own env, only if actually set): re-invoking the AppImage always boots Electron's native layer first, even for this headless relaunch flag, which segfaults without a real display/session-bus connection — and some MCP hosts spawn the configured command with a stripped environment that drops both even on a machine that has them (milestone 18 part 20). The generated snippet deliberately **does not** hardcode `POCO_WORKSPACE` — the MCP server already falls back to whichever workspace the app currently has open when it's unset (see "Tools" above), so the snippet just documents that default and shows `POCO_WORKSPACE` as an opt-in for anyone who wants an agent pinned to one specific workspace regardless of what's open (milestone 18 part 21).

## Search (cross-type full-text) — milestone 25

Gap this closed (surfaced by a design conversation with the user about what an MCP agent can and can't answer): a journal entry's index row used to be just a `has_body` flag and a note's title/tags only — neither body was cached, so nothing could search their content, and there was no single query looking across tasks+notes+journal(+projects) at once. A task's `description` was already cached and already substring-searched by `querySearchTasks` — no gap there. Previously, an agent could only answer a content question if it already knew (or brute-forced, one `get_note`/`get_journal_entry` at a time) which file held the answer.

- **Schema**: add a `body` TEXT column to `journal_entries` and to `notes` (`lib/index/db.ts`), populated by the existing reconciliation pass in `reindex.ts` — no change to the stat-diff mechanism itself, just one more field read per changed/new file, same as any other column. `projects` already had `name`/`description`/`tags` cached from the start — only its FTS mirror is new, not a column.
- **Mechanism: SQLite FTS5 virtual tables** (`tasks_fts`, `notes_fts`, `journal_fts`, `projects_fts`), a deliberate departure from the plain `LIKE`-scan pattern every search query in this codebase uses today (`querySearchTasks`, `querySearchNotes`) — confirmed working against this project's `node:sqlite` build. Chosen over extending the `LIKE` pattern specifically because FTS5 gives ranked results and `snippet()`-based excerpts (useful once a result can be a task, a note, a journal entry, or a project mixed together), at the cost of being genuinely new territory for this codebase — virtual tables kept in sync, not just a wider `WHERE` clause. Repopulated during reconciliation (rebuild-on-reconcile, matching every other index table) rather than trigger-maintained, so a missing/corrupt FTS table self-heals on the next reindex exactly like the rest of the index does. A brand-new FTS table added to an *existing* index (as `projects_fts` was, in a follow-up) needs the same one-time backfill reasoning as a new column: `openIndexDb` checks `sqlite_master` for whether the table already existed before this open, and if it didn't, resets every existing row's `source_mtime` to force one reparse — otherwise an unchanged file's row would never get inserted into the new FTS table at all.
- **Cross-type query**: `queryFullTextSearch(workspacePath, {query, from?, to?, types?})` (new, `lib/index/queries.ts`) unions matches from all four FTS tables into one discriminated-union list (`{type: 'task'|'note'|'journal'|'project', ..., snippet}`), optionally filtered by each type's own natural date (task: `relevantDateOf` — done/due/created, same field `get_task_summary` already uses; journal: the entry's own date; note: `updated`; project: `created`, the only date a project has), sorted by relevance then recency.
- **REST**: `GET /api/search?q=&from=&to=&types=` → a new `services/search.ts` — its own service module since this crosses `services/{tasks,notes,journal,projects}.ts` and doesn't belong inside any one of them, same "aggregate queries get their own isolated file" precedent as milestone 9.
- **MCP**: one new tool, `search_everything({query, dateRange?: {from, to}, types?: ('task'|'note'|'journal'|'project')[]})` — answers "find anything mentioning X" and "...within this date range" in one call, which nothing today does (`get_task_summary`'s `dateRange` filters structured counts, not text; `search_tasks`/`list_notes` have no date filter at all). Existing `search_tasks`/`list_notes` calls are additive-upgraded for free once description/body is FTS-searchable — their interface (just `query`) doesn't need to change.
- **Prefix matching, not whole-word-only** (a real bug the user hit: searching "zago" found nothing even though "zagoo" existed): `toFtsMatchQuery` quotes each token as an escaped literal phrase *and* appends a trailing `*` outside the closing quote — `"zago"*`, which FTS5 parses as a prefix query on that phrase's last token — rather than `"zago*"` (the star lands *inside* the quotes there, which FTS5 treats as a literal, non-matching character and silently returns nothing — confirmed empirically against this project's `node:sqlite` build, not assumed). A whole word still matches under this scheme (it's trivially its own prefix), so this is a strict superset of the earlier exact-token behavior.
- **Wired into the Dashboard's search popup** (milestone 18's popup, upgraded here after asking the user which of three options they wanted — upgrade the popup vs. leave it task-only vs. something else — rather than assuming): the popup now calls `GET /api/search` instead of the old task-only `GET /api/tasks/search`. A task result still renders through the existing `TaskRow` exactly as the Today/Overdue/This-week buckets do; a note/journal/project result gets its own compact row (a small type badge, its title — the note's title, the project's name, or the journal date formatted the same way the rest of the app formats dates — the `snippet()` excerpt with the match in **bold** rendered as `<mark>`, and a "go to" link to `/notes/:slug`, `/journal/:year/:date`, or `/projects/:slug` respectively). The clickable tag-pill row above the results is still sourced from open tasks' own tags only (a note/project-only tag isn't offered as a pill, though typing it still matches) — a known, minor limitation left as-is rather than expanded, since building a combined tag list across four content types wasn't part of the ask.

## File attachments — milestone 27

Lets the user attach files/images to a task, journal entry, or note, and give a project a profile image — requested by the user ("add new milestone: file attachment. allow user to attach files, images to journal, task and note. user can also use a profile image for project"). Before building, four real design forks were confirmed with the user (`AskUserQuestion`, same practice as milestones 24-26): inline markdown embed vs. a structured attachment-list field, a flat vs. per-type attachments folder, whether to add an MCP `attach_file` tool in this pass, and whether to cap upload size. The user chose: inline markdown embed, per-type subfolders, UI-only for now (no MCP tool), and no size limit.

- **Storage**: `<workspace>/attachments/<folder>/`, one subfolder per content type — `tasks`, `journal`, `notes`, `projects` (`server/src/services/attachments.ts`'s `ATTACHMENT_FOLDERS`). Plain content, not under `.poco/` — committed to git and travels with the workspace like everything else, same as a task/project/note/journal file. No SQLite index table: an attachment carries no queryable metadata of its own (unlike a task/note/journal/project, there's no frontmatter to parse), so file-system-only is the right fit — the index's job (per "SQLite index layer" above) is caching *parsed* vault content, and there's nothing here to parse. A colliding filename auto-suffixes (`foo.png`, `foo-2.png`, `foo-3.png`, ...) rather than overwriting, same precedent as a note's colliding-title auto-suffix. No size limit is enforced (the user's explicit choice) — a very large attachment does mean a permanently larger git repo for that workspace from then on (git doesn't diff binaries efficiently), a deliberate accepted trade-off, not an oversight.
- **Referenced as a real relative markdown link, not a new grammar/frontmatter field**: attaching a file to a task description, journal body, or note body inserts a plain `![alt](../attachments/<folder>/<file>)` (image) or `[alt](../attachments/<folder>/<file>)` (any other file) at the end of that field's current text (`client/src/lib/attachments.ts`'s `attachmentMarkdown`/`appendAttachment`) — the number of leading `../` segments matches that file's actual depth under the workspace root (1 for a note at `notes/<slug>.md` or a task description inside `projects/<slug>.md`, 2 for a journal entry at `journal/<year>/<date>.md`), so it's a genuine working relative link in any external tool pointed at the same workspace, not just this app (unlike a `/api/attachments/...` URL baked directly into the text, which would only resolve here). This needed **no server-side change at all** to the task/note/journal write paths — `description`/`body` were already opaque freeform text to every one of those service functions (confirmed before building: `createTask`/`updateTask`, `createNote`/`updateNote`, `putJournalEntry` all just assign the string through untouched), so an embedded reference round-trips exactly like any other markdown a human might type.
- **A project's profile image is the one exception**: it's a structured frontmatter field (`ProjectFrontmatter.profileImage?: string`, `server/src/types.ts`), not a body-embedded link — there's no freeform body on a project file to embed into. Stores a plain workspace-relative path (`attachments/projects/foo.png`, no leading `../`, since it's a data field rather than a link that needs to resolve when the raw file is opened elsewhere) and follows the same `undefined` = leave alone / `null` = clear convention `UpdateTaskInput.due` already established (`UpdateProjectInput.profileImage?: string | null`). Deliberately edit-only, not offered at project creation — `ProjectForm`'s image control is gated behind `showArchived` (the same "edit mode only" flag the archived toggle already uses), which sidesteps the ordering problem of uploading a file for a project that doesn't have a slug yet (unlike notes' `/notes/new` lazy-create page, projects are created immediately, before any attachment upload could target them). Renders in place of the plain color swatch wherever it's shown (`ProjectCard`'s `.project-color-tab` → `.project-avatar-tab`, `ProjectDetailPage`'s `.pd-color` → `.pd-avatar`) — falls back to the color swatch when absent, exactly as before this milestone.
- **Upload endpoint**: `POST /api/attachments/:folder` (multipart, field `file`, `multer` with in-memory storage — a new server dependency, nothing else in this codebase parsed `multipart/form-data` before) saves the file (`saveAttachment`, sanitizing the original filename via `path.basename` + a character allowlist, auto-suffixing on collision) and commits it — its own independent commit (`attach_file <path>`), decoupled from whatever later save of the task/note/journal/project embeds a reference to it, same as any other independent write in this app. Returns `{folder, filename, path, url}`; the client builds the markdown snippet (or, for a project, sets `profileImage` directly) from `path`.
- **Serving**: `GET /api/attachments/:folder/:filename`, resolved against the *active* workspace per-request (not a static mount computed once at app startup, since the active workspace can change at runtime) via `res.sendFile(filename, {root: attachmentsDir})` — Express's own `root`-relative resolution rejects a `filename` that would escape it, so this needs no separate traversal check (verified live: a `..`-laden filename 404s rather than reading outside the folder).
- **Rendering an embedded reference**: a file-relative link like `../attachments/notes/foo.png` means nothing to a browser rendering this app's single-page HTML (there's no matching route), so `client/src/lib/renderMarkdown.ts`'s `markdown-it` instance now rewrites an `image`/`link_open` token's `src`/`href` from that relative form to `/api/attachments/<folder>/<file>` right before rendering, for both Notes' Preview mode and the task view modal's rendered description (both already went through this one `renderMarkdownToHtml`) — any other link (a normal `http(s)` URL) passes through untouched. A rewritten link also gets `target="_blank"` (opens the file in a new tab rather than navigating the SPA away from the note/task), which an ordinary unrewritten link still doesn't.
- **`AttachmentField`** (`client/src/components/AttachmentField.tsx`): the shared "attach file" toolbar button + inline thumbnail/chip list, used identically by the journal body (`JournalDayPage`), note body (`NoteBodyEditor`, both its Edit and — new — visible-while-editing list), and task description (`TaskForm`). Solves a real gap the journal specifically has: unlike notes (a Preview mode) and tasks (the view modal), the journal editor deliberately never renders markdown as HTML (PLAN.md "Journal editor" — a settled decision from milestone 23, not reopened here), so an embedded image would otherwise be inert raw text with zero visual feedback there. `AttachmentField` closes that gap for all three uniformly rather than special-casing the journal: it re-parses the current body/description text for attachment references belonging to its own folder (`client/src/lib/attachments.ts`'s `parseAttachmentRefs` — there's no separately stored list, the markdown text is the only source of truth) and renders each as an image thumbnail or a filename chip, live, independent of whatever preview mode (if any) the surrounding editor has. Uploading appends to the *end* of the current text via the same `onChange` the editor already uses (not inserted at the cursor — `MarkdownEditor` doesn't expose one, and end-of-field is simple and predictable) — a deliberate simplification, not an oversight; cursor-precise insertion would need a new imperative API on `MarkdownEditor`, which nothing else in this app currently needs.
- **No MCP tool this milestone** (the user's explicit choice) — every MCP read tool (`get_task`, `get_note`, `get_journal_entry`, etc.) already returns body/description text as-is, so an agent can see that a file is referenced, it just can't attach one itself yet. An `attach_file(target, filePath)`-shaped tool could follow later behind the same `saveAttachment` service function if wanted.
- **Follow-up: paste from clipboard** ("allow paste from clipboard") — pasting a file directly into the journal body, note body, or task description (a screenshot copied from an OS tool, a file copied from a file manager) uploads and embeds it the same way clicking the attach button does, no click required. `MarkdownEditor` gained an optional `onPasteFiles?: (files: FileList) => void` prop, wired via a CodeMirror `EditorView.domEventHandlers({paste: ...})` extension that checks `event.clipboardData.files` — present only for a file paste, never a plain text/markdown one, so an ordinary paste is completely unaffected (confirmed live: pasting plain text still lands as plain text at the cursor). The upload+insert logic itself was pulled out of `AttachmentField` into a `useAttachmentField(folder, value, onChange)` hook (`client/src/components/AttachmentField.tsx`) specifically so both the click-the-button path and the paste-anywhere-in-the-editor path share one implementation rather than two that could drift — `AttachmentField` is now a presentational component taking that hook's return value as props. `handleFiles` accepts and uploads every file in the paste in order (a clipboard paste, unlike the attach button's single-file input, can carry more than one file at once — e.g. copying several files from a file manager), appending a reference for each.
- **Follow-up: open in the system's default app** ("open image, file by system apps when click on image, file link") — clicking an attachment image/link (in `AttachmentField`'s chip list, Notes' Preview mode, or the task view modal) opens it with the OS's own default handler for that file type (an image viewer, a PDF reader, ...), the same as double-clicking it in Finder/Explorer/Nautilus — not a browser tab. Needed **no client-side change at all**: every attachment link already carried `target="_blank"`, and Electron's `BrowserWindow` already intercepts every `window.open`/`target="_blank"` navigation through `setWindowOpenHandler` (`electron/src/main.ts`) for exactly this reason (previously used only to send a plain external link, like Settings' git-download link, to the system browser via `shell.openExternal` instead of a second Electron window). That handler now recognizes a URL whose path matches `/api/attachments/<folder>/<file>` and resolves it to the real file on disk (via the same `GET /api/workspaces/active` call `poco:get-reminder-settings` already makes to find the active workspace's path) before handing it to `shell.openPath` — the same primitive `openWorkspaceFolder` already uses successfully to reveal a workspace folder, just pointed at a file instead of a directory this time. Any other `target="_blank"` link (not matching that path shape) still falls through to the pre-existing `shell.openExternal` behavior unchanged. `folder`/`filename` are decoded and validated as single, traversal-free path segments (no `/`, `\`, `.`, or `..`, checked *after* percent-decoding — a first draft of this check compared the resolved absolute path only against the *workspace* root rather than `attachments/<folder>/` specifically, which a `path.resolve`-based traversal could still slip past; caught by writing an isolated Node script exercising the exact regex/decode/join logic against several encoded-traversal payloads before shipping it, not just against benign input) before ever being joined into a path, so a crafted URL can't make `shell.openPath` launch a file outside `<workspace>/attachments/<folder>/`. This is an Electron `main.ts`-only change — a plain browser tab (dev, or the client opened outside Electron) has no `setWindowOpenHandler` to intercept anything and keeps the previous "open in a new tab" behavior, which is the best a browser can do anyway.
- **Fix: an embedded image had nothing to click** ("image and file link in detail modal are unclickable") — `renderMarkdown.ts`'s `link_open` rewrite only ever covered a plain `[text](...)` link; `![alt](...)` is a different markdown token entirely and rendered as a bare `<img>` with no surrounding `<a>`, so there was never anything for a click to act on (a plain-link attachment was already clickable the whole time; only an *embedded image* wasn't). Fixed by having the `image` rule also wrap its rendered `<img>` in a real `<a href={resolvedSrc} target="_blank" rel="noopener noreferrer">` — but only when the image's `src` actually matched the attachment-relative-path pattern, so a normal `![alt](https://...)` embed is untouched. `AttachmentField`'s own chip list was never affected (it already wraps every thumbnail in a real link).
- **Fix: the previous system-app-open follow-up didn't actually work for non-image files** ("i still can't click on non-image file linke") — the prior bullet's "no client-side change at all" claim turned out to be wrong for anything Chromium can't render inline in its own window: `setWindowOpenHandler` only fires for a genuine new-window/tab request, but a file this app's `BrowserWindow` has no built-in viewer for (a PDF — Electron doesn't bundle Chrome's PDF plugin unless explicitly enabled) makes Chromium fire a `will-download` session event *instead*, which never reaches `setWindowOpenHandler` at all — the file silently downloads to the OS's default Downloads folder, indistinguishable from the click doing nothing. The image case only ever appeared to work because an image *is* something Chromium renders inline as a new-window navigation. Real fix: stop depending on the browser's own navigate-vs-download decision entirely — the renderer now intercepts the click itself (`client/src/lib/attachments.ts`'s `openAttachmentIfPossible`, wired onto `AttachmentField`'s own links and, via one delegated container handler using `closest('a')` since there's no per-element React handle on raw HTML, `handleRenderedAttachmentClick` on Notes' Preview mode and the task view modal), calls `preventDefault()`, and invokes a new `poco:open-attachment` IPC bridge (`electron/src/preload.ts`/`main.ts`) directly — before Chromium ever gets a chance to decide anything. The old `openAttachmentPath`/`setWindowOpenHandler` path (renamed `openWorkspaceRelativeAttachment` for its shared core logic) is kept only as a fallback for whatever the renderer's click interception can't catch (a middle-click, which fires no ordinary `click` event). Outside Electron (no `window.poco`), `openAttachmentIfPossible` is a no-op and the plain `target="_blank"` anchor behavior proceeds exactly as before.
- **Fix: a filename with a space produced no link at all** ("i mean file link below image is unclickable") — a genuine CommonMark parsing failure, not a click-handling bug like the two above: `attachmentMarkdown()` wrote the destination bare (`[text](../attachments/.../name with space.xlsx)`), and a bare link destination cannot contain a literal space (or unbalanced parens) per the CommonMark spec, so `markdown-it` correctly refused to parse it as a link at all and rendered the literal `[text](...)` text instead — confirmed directly against `markdown-it` before touching any code. Fixed by always wrapping the destination in `<...>` (the angle-bracket destination form, which allows any character except a literal `<`/`>`/newline — none of which a filename can contain, since `sanitizeFilename` already strips them server-side); `markdown-it` parses this natively and auto-percent-encodes the space in the rendered `href`/`src`, so `renderMarkdown.ts` needed no changes. `parseAttachmentRefs` (`AttachmentField`'s own body-scanning regex, independent of `markdown-it`) was extended to recognize both the new bracketed form and the old bare one, so an already-saved space-free reference from before this fix still shows up in the list — only an already-saved *space-containing* bare reference (impossible to have ever worked) needs a one-time manual edit (wrapping its existing destination in `<...>`) to fix, since the saved markdown text itself is invalid CommonMark and can't self-heal.

## Localization (i18n)

The UI language is a personal display preference, not vault content — it never touches the markdown files, and isn't scoped per-workspace (a user has one language for the whole app, the same way they have one launch-at-login setting). English and Vietnamese ship first; the mechanism doesn't hardcode either, so a third language is just another resource file.

- **Storage**: one `language: 'en' | 'vi'` field on `~/.poco/config.json`'s app-wide registry, alongside `launchAtLogin` — `undefined` (never set) normalizes to `'en'`. Exposed as `GET/PUT /api/preferences/language` (`server/src/routes/preferences.ts`, `services/workspaces.ts`'s `getLanguagePreference`/`setLanguagePreference`), the same pattern already established for `launch-at-login`.
- **No Electron bridge for the client's own use** — unlike launch-at-login/reminder settings, a language switch touches no OS-level API, so the React client reads/writes the preference directly over HTTP (`api/client.ts`'s `getLanguagePreference`/`setLanguagePreference`) and works identically in a plain browser tab, not just inside Electron.
- **Client**: `react-i18next` + `i18next`, resources bundled statically as `client/src/i18n/{en,vi}.json` (`client/src/i18n/index.ts` does the `i18next.init`). `main.tsx` fetches the stored preference once and calls `i18n.changeLanguage` before the first render, so the app never flashes in the wrong language. `/settings` gains a **Language** picker (EN/VI) that persists via the API and calls `i18n.changeLanguage` directly for an instant switch, no reload needed.
- **Electron native strings**: the tray menu (Open/Settings/Quit + tooltip) and the daily-reminder OS notification's title/body are also translated — these are rendered by the main process, outside the React bundle, so they use a small hand-rolled dictionary (`electron/src/i18n.ts`) rather than pulling `react-i18next` into a non-React process. `main.ts` reads the preference once at startup (for the tray's initial language) and the daily-reminder scheduler (`reminder.ts`, already polling once a minute) re-reads it on every tick, calling back into `main.ts` to rebuild the tray menu whenever it changes — so a language switch made in Settings takes effect on the tray within a minute without an app restart.
- **Convention for new UI text going forward**: every user-facing string in `client/src/{pages,components}` goes through `useTranslation()`'s `t()`, keyed by a per-page/component namespace in `en.json`/`vi.json` (e.g. `settings.language.sectionTitle`) — a new hardcoded string in a component is a regression here, the same way an unhandled inline-token variant would be in `taskLine.ts`.

## Theming

The UI theme (light/dark) and accent color (palette) are personal display preferences, not vault content — same reasoning as Localization above, and deliberately the same storage/bootstrap mechanism, minus the Electron side (neither the tray icon nor OS notifications are styled by this app's CSS, so — unlike `language` — nothing outside the React client ever needs to read these).

- **Storage**: `theme: 'light' | 'dark'` and `accentPalette: 'default' | 'green' | 'blue' | 'violet'` fields on `~/.poco/config.json`'s app-wide registry, beside `language`/`launchAtLogin`. `undefined` normalizes to `'light'` / `'default'` — `'default'` is the single accent color this app shipped with before this preference existed, kept as the default so an existing install's appearance doesn't change on upgrade. Exposed as `GET/PUT /api/preferences/theme` and `GET/PUT /api/preferences/accent-palette` (`server/src/routes/preferences.ts`, `services/workspaces.ts`'s `get/setThemePreference` and `get/setAccentPalettePreference`).
- **Client**: read/written directly over HTTP (`api/client.ts`), same as `language` — works identically in a plain browser tab. `main.tsx` fetches both, alongside the language preference, before the first render and applies them as `data-theme`/`data-palette` attributes on `<html>` (`lib/theme.ts`'s `applyTheme`/`applyAccentPalette`) so the app never flashes the wrong appearance. `/settings` gains **Theme** (Light/Dark) and **Accent color** (Default/Green/Blue/Violet, each a small swatch dot) pickers, right after Language — persist via the API and call `applyTheme`/`applyAccentPalette` directly for an instant switch, no reload needed.
- **CSS mechanism** (`client/src/styles/app.css`): every color in the file is a `:root` custom property (or an alpha variant of one) — no component rule hardcodes a color literal. The accent family (`--accent`, `--accent-hover`, `--accent-soft`) derives its hue from one `--accent-hue` variable rather than a literal hue, which is the whole point of using oklch here: `[data-palette='green'|'blue'|'violet']` overrides only `--accent-hue` (45/145/250/305; `'default'` needs no override, it's `:root`'s own value), keeping the same lightness/chroma "feel" across all four palettes. `:root[data-theme='dark']` overrides every neutral/semantic token (`--paper`, `--ink`, `--hairline`, `--good`, `--danger`, `--today-*`, plus muted-surface/border/overlay/shadow tokens) for the dark variant, still referencing `var(--accent-hue)` so a palette choice applies identically in both themes — the two attributes are independent axes, not eight hardcoded combinations. `color-scheme` is set to match (`light`/`dark`) so native form controls and scrollbars follow along.
- **On-fill text contrast**: dark theme brightens `--accent`/`--good`/`--danger` (so they stay legible as *text/border* color against the dark page background), which as a side effect ruins the contrast of the existing "white text on a solid fill" pattern (buttons, the "today" markers, the done-status checkmark) — measured ~2.5:1 in dark theme, well under WCAG AA, against ~4.5:1 in light theme. `--accent-contrast`/`--good-contrast`/`--danger-contrast` (default `white`, overridden to `var(--paper)` — the dark theme's own near-black — inside the dark block) fix this at ~6-8:1 measured, and are what any new solid-fill-plus-text component must use instead of a literal `white`. Native text selection (`::selection`) is themed too, via `--accent-soft` (enough contrast against `--ink` in both themes without needing its own dedicated color) — otherwise it's the one visual the browser/OS default (an unthemed blue) would leave untouched by `data-theme`/`data-palette`.
- **A calendar day's journal-entry highlight is accent-family, not a fixed semantic color**: `CalendarSidebar`'s `.has-journal` and `CalendarPage`'s `.cp-day`/`.cp-year-day` equivalents use `--accent-soft`/`--accent-border` (a new token, `--good-border`'s exact pattern but keyed to `--accent-hue`), not `--good-soft`/`--good-border` as originally shipped — a user picking Blue or Violet expects the "has a journal entry" wash to actually read as blue/violet, not stay a fixed green regardless of palette. `--good`/`--good-soft` themselves are unchanged and still mean "success/done" everywhere else (the completed-task checkmark, the active-workspace pill) — that *is* meant to stay a fixed semantic green independent of palette, this was specifically the journal-day highlight being miscategorized as the same "done" semantic rather than an accent-colored one. On a day that's both today and journal-logged, `.cp-day.today`'s full-strength solid border/box-shadow still layers visibly over the softer `.has-journal` wash — same hue family now, but distinguished by intensity rather than by a second hue.
- **Convention for new component CSS going forward**: a new color needs a token (existing or new) added to `:root` (and, if it's a neutral/semantic one rather than accent-family, to the `:root[data-theme='dark']` override block) — a hardcoded `oklch(...)`/hex/rgb literal in a component rule is a regression here, the same way an untranslated string is for Localization.

## Journal editor

The journal body editor highlights markdown syntax live as you type — colors/weights headings, bold, italic, strikethrough, links, inline code, and blockquotes distinctly, the way VS Code colors a `.md` source file. Explicitly **not** an Obsidian-style live-preview: no mark is ever hidden and nothing is rendered as rich HTML — the on-screen text is still the exact raw markdown, still stored verbatim (unchanged from "Freeform markdown body, unparsed" above). This was a deliberate, narrower scope than "live preview" after asking the user, who chose syntax coloring over a hide-the-marks rendering.

- **Engine**: `MarkdownEditor.tsx` wraps CodeMirror 6 (`codemirror`, `@codemirror/lang-markdown`, `@codemirror/language`, `@codemirror/search`, `@lezer/highlight` — added as client deps) directly, not a React wrapper package, so theming/sizing stays under this app's own CSS. Originally the journal body only (`JournalDayPage`); milestone 18 extended it to task descriptions too (`TaskForm`, sized down via a `.task-desc-editor` class rather than the journal's full-page `.journal-body`), with the rendered result (`renderMarkdownToHtml`, same as `NoteBodyEditor`'s preview) shown in `TaskRow`'s expanded view — the stored value is still the identical plain string in `taskLine.ts`'s indented continuation-line block, only how it's edited/displayed changed. Project descriptions still keep the plain `MarkdownTextarea` — not asked for there, and not revisited when tasks moved.
- **Find-in-editor** (milestone 18): Cmd/Ctrl+F opens a find/replace panel — built on CodeMirror's own search state/commands (`@codemirror/search`'s `search()` + `searchKeymap`) but with a **from-scratch panel** (`lib/vscodeSearchPanel.ts`'s `VscodeSearchPanel`, wired in via `search()`'s `createPanel` config option) instead of that package's default one, styled and laid out like VS Code's own find widget at the user's request: a single search row (chevron · input · a live "n of m" match-count readout, computed via a plain full-document cursor scan since `@codemirror/search` exposes no count of its own · `Aa`/`ab`/`.*` icon-style toggle buttons for case/whole-word/regex, styled as VS Code's own widget actually renders them (small styled text, not abstract glyphs) · prev/next chevrons · a close ×), with the replace row (input + replace/replace-all icons, indented to align under the search input) collapsed behind that chevron by default rather than always visible. `VscodeSearchPanel` reuses 100% of `@codemirror/search`'s own query/command machinery (`SearchQuery`, `setSearchQuery`, `findNext`/`findPrevious`, `replaceNext`/`replaceAll`, `closeSearchPanel`) — only the DOM is custom. Applies to the journal body and note bodies alike (both go through this one `MarkdownEditor` component). `search({ top: true, ... })` — these editors have no internal scroll of their own (they grow to fit their content; the *page* scrolls instead), so the default bottom-panel placement would land past the end of anything longer than a screenful. Panel colors come from `app.css`'s own `.find-*` classes (the app's own `--paper`/`--ink`/`--surface-*`/`--accent-soft` tokens, no fighting CodeMirror's own injected base theme needed since this panel doesn't use its default class names at all) — deliberately with its own explicit `font-family`/`line-height` too, not inherited from the editor: the editor's own `'JetBrains Mono'` + `1.75` line-height (sized for full lines of prose/code) didn't reconcile cleanly with a single-line `<input>`'s own text layout, visibly offsetting/clipping typed characters — the panel is app chrome sitting *on* the document, not document content itself, so it uses the same UI font every other input in the app already does. `searchKeymap` alone only fires while the CodeMirror view itself has focus and doesn't exist at all in a page's Preview mode (no view mounted there) — `MarkdownEditor` also exposes an imperative `openFind()` (via `forwardRef`/`useImperativeHandle`), and `JournalDayPage`/`NoteBodyEditor` (the two pages with an edit/preview toggle) each use a shared `useFindShortcut` hook: a page-scoped Cmd/Ctrl+F listener that switches to Edit mode first if needed, then calls it — so find works regardless of current focus or view mode, not just while already editing with the cursor in the body.
  - **Match-highlight colors are their own dedicated tokens, not `--accent`**: `--find-match-bg`/`--find-match-selected-bg` (warm yellow/orange, translucent, fixed hue independent of `--accent-hue` and every `--md-*` token — same "fixed hue so it stays distinct regardless of accent palette" reasoning `--md-code` already documents for itself). Reusing `--accent-soft`/`--accent` here was tried first and genuinely broke on a matched heading (`--md-heading = var(--accent)`): a `color` override on the match span can't fix that — CSS inheritance means a child's own explicit color rule (the heading text's own syntax-highlight span) always beats an ancestor's, `!important` or not, since `!important` only resolves conflicts between rules targeting the *same* element. Translucent for the same reason `--md-code-bg` already is (see that token's own comment): the underlying text color always shows through, tinted, rather than betting on an override that can't work.
- **Contract**: same controlled `{value, onChange(next: string), placeholder?, disabled?, className?}` shape `MarkdownTextarea` used, so `JournalDayPage`'s autosave/dirty-tracking logic didn't need to change — only the import and the `onChange` signature (`(next: string)` instead of a change event). `onChange` fires only for genuine user edits, never for the component's own effect that pushes an externally-changed `value` prop into the CM doc (e.g. the journal entry's fetch resolving after the editor already mounted empty) — that dispatch is tagged with a dedicated CodeMirror `Annotation` the `updateListener` checks for and skips, specifically because an earlier version *didn't* distinguish the two and every page load fired a real (and pointless) autosave indistinguishable from actual typing.
- **Markdown dialect**: `@codemirror/lang-markdown`'s GFM-extended `markdownLanguage` (strikethrough, tables, autolinks, task-list checkboxes), matching the GFM-checkbox grammar the rest of the app already uses for tasks. No `codeLanguages` config (that would add a lazy-loaded chunk per possible fenced-code-block language — pug, nginx, verilog, etc. — well past what coloring the markdown itself needs); a fenced code block still gets a flat monospace/code-color treatment via the block's own `monospace` tag, just no per-language syntax coloring *inside* the fence.
- **Typeface**: `JetBrains Mono`, embedded rather than named-and-hoped-for — `client/public/fonts/jetbrains-mono/*.woff2` (regular/bold/italic/bold-italic only, not the full 16-weight family) plus its `OFL.txt` (SIL Open Font License, redistribution-safe), pulled in via `@font-face` rules at the top of `app.css`. Vite copies `public/` verbatim into `client/dist`, which both the dev server and the packaged Electron app already serve, so no build/packaging config changed. This is also now the app's *one* monospace typeface — every other `IBM Plex Mono` reference in `app.css` (badges, task/journal IDs, commit hashes, tags, timestamps) was replaced with it too, at the user's request, for one consistent mono font app-wide; `Newsreader` is unaffected and still just named-and-hoped-for (not embedded). The app's sans-serif UI typeface is `Inter`, embedded the same way — `client/public/fonts/inter/{Inter-Variable,Inter-Italic-Variable}.woff2` (the variable font instanced down to the `wght` range and `opsz` this app actually uses, `400 700`/`14`, rather than shipping its full 100-900/14-32 design space) plus `OFL.txt`, at the user's request in place of the previously-named-only `Manrope`.
- **Colors are theme tokens, not literals**: `--md-mark` (dims all syntax punctuation — `#`, `**`, `` ` ``, `>`, list markers, fences — the same "structure, not content" treatment VS Code gives them), `--md-heading` (accent-family, `= var(--accent)` — deliberately *not* the same token bold text uses, so headings visually stand out from a merely-bold word; see the `styleTags` gotcha below for why that needed splitting into two separate HighlightStyle rules), `--md-link`, `--md-url`, `--md-quote`, `--md-code`/`--md-code-bg`. `--md-link` is a fixed hue (`oklch(52%/72% 0.15 210)`, light/dark) rather than `--accent`, at the user's request — both had shared `--accent` originally, which meant a heading and a link rendered as the exact same color with no visual cue telling them apart; `210` (azure) was picked to avoid colliding with any `--accent-hue` option (45/145/250/305), `--good` (155), `--danger` (25), or `--md-code` (350), the same "stays distinct regardless of accent palette" reasoning `--md-code` already used for itself. `--md-code` is a fixed hue independent of `--accent-hue` (same reasoning) so code stays visually distinct from links/headings regardless of accent palette; `--md-code-bg` is a *translucent* wash of `--ink` (6% alpha light / 8% dark), not an opaque fill — see "Code block background is its own layer" below for why opacity specifically matters here. The rest follow the Theming rules above (light/dark blocks, no hardcoded literals in component CSS).
- **Code block background is its own decoration layer, not a HighlightStyle color** — and why that's more than a style preference: a `HighlightStyle` rule can only paint the characters it matches, never the empty space to the right of a short line, so a fenced/indented code block's background needs to come from a full-*line* decoration instead. `MarkdownEditor.tsx`'s `codeBlockBackground` (a `ViewPlugin`) walks the syntax tree for `FencedCode`/`CodeBlock` nodes and adds a `Decoration.line` with a background class to every line the block spans (plus corner-rounding classes on the first/last line). A parallel `inlineCodeBackground` plugin does the equivalent for `InlineCode` nodes specifically, as a tight `Decoration.mark` chip — kept as a *second* tree-walking plugin, not folded into the same one, because `@lezer/markdown` tags inline code and fenced/indented code block text with the exact same `monospace` tag (no way to tell them apart via `HighlightStyle` alone); an earlier version relied on `t.monospace`'s own `backgroundColor` for both cases and the two literally stacked wherever a fenced block's per-character background sat on top of its own line's background, visibly doubling up. `t.monospace` now only sets text `color`, never a background.
  - **This full-line background also uncovered a genuine CodeMirror selection bug**: `.cm-line` (where the background lives) is stacked *above* CodeMirror's own selection-highlight layer (a `.cm-layer` sibling with a negative `z-index` — confirmed by inspecting `@codemirror/view`'s injected stylesheet), so an *opaque* line background fully hid the selection highlight underneath it whenever you selected text inside a code block. Making `--md-code-bg` translucent instead of opaque was the fix — the selection color now shows through, blended, rather than being erased.
- **Selection color is themed to match the rest of the app, not CodeMirror's own default**: `drawSelection()` replaces the browser's native `::selection` (which this app already themes everywhere via `--accent-soft`) with CodeMirror's own selection layer, styled by CodeMirror's *own* injected stylesheet — hardcoded light-grey (`#d9d9d9`/`#d7d4f0`) with no awareness of `data-theme='dark'` at all. In dark theme this meant near-white `--ink` text sitting on a background nearly as light as the text itself. `app.css`'s `.md-editor .cm-selectionBackground` forces `background: var(--accent-soft) !important` to match; `!important` is needed (not just normal specificity) because CodeMirror injects its stylesheet at runtime, after `app.css` loads, with several chained classes of its own.
- **A `styleTags` gotcha worth remembering**: `@lezer/markdown` maps list nodes (`BulletList/... OrderedList/...`) to the `list` highlight tag *recursively* — every descendant, not just the bullet character — so an earlier version of this that styled `tags.list` directly ended up bolding/accent-coloring *all* text inside any list item (including nested bold/code/links), fighting with their own token styles. Fixed by not styling `tags.list` at all — the bullet/number mark is already covered by `--md-mark` via its own `processingInstruction` tag, which is not recursive. The same tag-granularity limitation is *why* `t.strong` and the `heading1`-`heading6` tags need to stay two separate `HighlightStyle` rules even though they once shared one: `--md-heading` couldn't move to accent-only-for-headings otherwise without tinting every bold word too.
- **Autosave interval is a user preference**, not a fixed constant — originally a hardcoded 800ms (every autosave is also a git commit, this app's undo mechanism, and 800ms fired on almost every normal mid-sentence thinking pause while journaling, producing a commit per pause), then a hardcoded 4000ms, now `autosaveIntervalSeconds` on `~/.poco/config.json`'s app-wide registry (same shape/reasoning as `theme`/`calendarMode` — a personal editing preference, not vault content; `undefined` normalizes to `30`). Exposed as `GET/PUT /api/preferences/autosave-interval` (`server/src/routes/preferences.ts`, `services/workspaces.ts`'s `get/setAutosaveIntervalPreference`), validated server-side to an integer in `[1, 300]` seconds (`AUTOSAVE_INTERVAL_MIN_SECONDS`/`MAX_SECONDS`, exported from the service so the route's validation can't drift from the preference's own bounds). `/settings` gets a matching **Autosave** number field (seconds), draft-state + validate-on-blur same pattern as the Sync panel's remote-URL field. `JournalDayPage.tsx` reads it via its own `useQuery` (not bootstrapped app-wide in `main.tsx` like theme/language — this only affects a debounce timer, never anything rendered before the page exists) into a ref so `scheduleSave`'s `setTimeout` always reads the current value without needing to be redefined. The debounce still resets on every keystroke (continuous typing never saves mid-word), and the existing unmount-flush effect still saves immediately on navigate-away regardless of the configured delay, so nothing can be lost by a longer setting.

22. **Concurrent-write safety (multiple writers, same project file)** — not started, deliberately deferred: raised by the user asking whether it's safe for multiple MCP agent processes, or a human in the UI and an agent, to write at the same time. It isn't, fully — this milestone is to actually fix it, not just document the gap.
    - **The core problem**: `services/projects.ts`'s `saveProjectFile` (reused by every task/project mutation) does a plain `fs.readFileSync` → mutate the in-memory parsed structure → `fs.writeFileSync`, with no locking and no optimistic-concurrency check. The REST API (Express) and the MCP server are always separate OS processes (and multiple MCP server processes — e.g. several agents, or several `--poco-mcp-server` relaunches, milestone 18 part 19 — can also run concurrently against the same workspace) with no shared JS event loop, so two writers' read-modify-write windows can genuinely interleave: whichever writes second silently overwrites the *entire* project file as the first writer left it, not just a conflicting field — because the unit of "modify" is the whole parsed project file (every task in it), not a single task or field. This can lose an edit with no error, no conflict surfaced, nothing in `git log` to even suggest it happened (the losing write's content is simply never committed).
    - **A second, more likely-in-practice failure mode found investigating this**: `client/src/components/TaskForm.tsx`'s edit form doesn't send a diff — it seeds local state once from the `task` prop when the form opens and always resubmits the complete `{text, due, tags, description, checklist}` bundle on save, regardless of which fields the human actually touched. `UpdateTaskInput` genuinely supports partial updates server-side (`undefined` = leave alone), but the client never uses that. So even with zero literal-millisecond race, a task edited by an agent while a human's edit form for the *same task* happens to be open (a window of however long the human takes, not milliseconds) gets silently reverted on the fields the human didn't intend to touch, the moment they hit Save. `VaultChangePoller`'s 4s poll (milestone 18 part 3) refreshes list views in the background but doesn't reach into an already-open form's local state, so it doesn't close this window.
    - **Two candidate fixes discussed with the user, neither decided yet**: (a) cheap, client-only — make `TaskForm` diff against its own initial snapshot and only send changed fields, which removes the "silently reverts untouched fields" failure mode entirely but doesn't address the underlying cross-process race for fields actually edited by both sides; (b) a real fix — optimistic concurrency on the project-file read-modify-write cycle itself (e.g. compare an expected version/mtime/hash captured at read time; reject and surface a structured conflict, rather than silently applying, if the file changed underneath) at the `saveProjectFile` layer, which would close the gap for the REST API, the MCP server, and any future writer alike, but needs a decision on what the conflict actually *does* — reject the write and make the caller (human or agent) retry against fresh data, or something smarter — and how it surfaces up through the MCP tool contract (a structured `isError` result, matching milestone 10's convention) vs. the REST API (an HTTP conflict status the client's mutation handlers don't currently expect).
    - Scope is deliberately open — no `Verify` step yet, since neither the mechanism nor which of (a)/(b) (possibly both) has been chosen. Revisit this section once that's decided.

24. **Notes** — a new content type requested by the user: "just a collection of md files with some meta: tag, create at, last modified", added at the user's request after checking storage layout/indexing/MCP-parity questions with them first (see "Storage format"'s "Note file" subsection above for the full design). `<workspace>/notes/<slug>.md`, one file per note, frontmatter `{title, created, updated, tags}`; slug assigned once from the title at creation (auto-suffixed `-2`/`-3`/... on a colliding title, unlike a project's outright-reject) and never changes even if the title is edited later.
