## Milestone 17 notes
- **New server surface, all thin wrappers over `services/workspaces.ts`**: `GET/PUT /api/workspaces/active/reminder` (`{enabled, time}`) and `POST /api/workspaces/active/reminder/fired` (body `{date}`, YYYY-MM-DD) in `routes/workspaces.ts`; a new `routes/preferences.ts` (`GET/PUT /api/preferences/launch-at-login`, `{enabled: boolean | null}`), mounted at `/api/preferences` in `index.ts`. This is a deliberate architecture choice beyond PLAN.md's literal text (which describes `reminder.ts` as reading/writing `~/.pivot/config.json` fields directly): the embedded server stays the **one** process that ever touches the registry file, exactly as it already was for every other registry mutation — `electron/src/main.ts`'s `pivot:get/set-reminder-settings` IPC handlers, and the launch-at-login default/persistence logic, all proxy through these routes over HTTP (the same pattern main.ts already used for `/api/health`) rather than a second direct JSON reader/writer racing the server's own writes.
- **`WorkspaceEntry` gains `reminderTime?: string | null` / `lastReminderFiredDate?: string | null`; `WorkspaceRegistry` gains `launchAtLogin?: boolean`** (`server/src/lib/workspaces.ts`) — `undefined` on each is treated as "not yet decided" by the reader, same pattern as milestone 6's `sync` field: no forced migration write, `services/workspaces.ts`'s `reminderSettingsOf`/`getLaunchAtLoginPreference` normalize at read time (reminder → PLAN.md's stated default of `'20:00'`/enabled; launch-at-login → `null`, meaning "apply the one-time default"). `addWorkspace` now sets `reminderTime: '20:00', lastReminderFiredDate: null` explicitly on every newly-created entry, matching PLAN.md's "default '20:00' on a newly-added workspace" literally rather than relying only on the read-time fallback.
- **All wall-clock/local-date logic lives in `electron/src/reminder.ts`, not the server** — the server treats `reminderTime`/`lastReminderFiredDate` as opaque strings it stores and returns, and `POST .../reminder/fired` takes the fired date as an argument rather than computing "today" itself (server code elsewhere already computes "today" via `new Date().toISOString().slice(0,10)`, i.e. UTC — fine for what it's used for there, but not something this feature should inherit for a check PLAN.md explicitly specifies as "local wall-clock time"). `reminder.ts`'s once-a-minute `startReminderScheduler` fetches `GET /api/workspaces/active` (already returns `reminderTime`/`lastReminderFiredDate` for free once added to `WorkspaceEntry` — no new route needed for that part) and `GET /api/journal/:year/:date` (existing route) to decide, then `Notification` + `POST .../reminder/fired` only on an actual fire.
- **Condition (a) is `localTime >= reminderTime`, not `===`** — a deliberate reading of PLAN.md's own parenthetical ("`lastReminderFiredDate`... prevents refiring within the same minute or **after waking from sleep past the time**"), which only makes sense if crossing-or-passing the time is what triggers a fire: a laptop asleep through 20:00 that wakes at 20:30 should still get reminded once, not silently miss the day because the exact matching minute was slept through. `lastReminderFiredDate` (day-granularity, set only on an actual fire, never on a skip) is what then prevents any later same-day tick — whether the very next minute or hours later — from refiring, exactly per PLAN.md.
- **`electron/src/main.ts`** wires: `pivot:get/set-reminder-settings` IPC handlers (proxy to the new reminder routes); `applyLaunchAtLoginDefaultIfUndecided(port)`, called once in `app.whenReady()` before window creation, which calls `loginItem.ts`'s `setLaunchAtLogin(true)` (the real OS-level toggle, unchanged since milestone 3) and persists `{enabled:true}` only if the preference was never explicitly decided; `pivot:set-launch-at-login` now also best-effort persists the user's explicit choice via the same preference route, so a later opt-out is never silently re-forced back on; `startReminderScheduler(...)` started after the window is created, stopped in `will-quit` alongside `stopServer()`; a new `navigateMainWindow(path)` helper (`showMainWindow()` + `loadURL` to the dev client or prod server URL + `path`) backing both the notification's click handler (→ `/journal`, per PLAN.md) and the tray's new "Settings" item (→ `/settings`).
- **`electron/src/tray.ts`** gained the "Settings" menu item (PLAN.md's project-scaffold comment for this file: "tray icon + menu (Open, Settings, Quit)") — `TrayCallbacks` gained `onSettings`.
- No new client-facing behavior — milestone 16 already built the Settings UI against this exact `window.pivot.getReminderSettings/setReminderSettings` contract; this milestone is what makes those calls actually resolve instead of rejecting with "no handler registered".
- **Verified live**, not via automated tests (no test runner in this repo drives the actual `electron` module — `Notification`/`app` only exist under the real Electron runtime, unlike everything else in `server/`, which does get automated coverage: `services/workspaces.test.ts` gained tests for `getReminderSettings`/`setReminderSettings`'s defaulting-and-persistence and for the launch-at-login preference's null-until-decided behavior). Built `electron/` (`npm run build -w electron`) and drove the real, compiled `reminder.js` under a real launched `electron` process (`electron/dist/reminder.js`, required directly — not `main.ts` as a whole, to isolate the scheduler from the rest of the app's window/tray lifecycle) against the real running server and a scratch workspace, with `Notification.prototype.show` patched to auto-emit a `'click'` shortly after showing (same technique as monkey-patching `window.confirm` to verify milestone 15/16's UI — the OS notification banner itself is a well-tested Electron/OS feature, not what needed proving here). Set `reminderTime` to 2 minutes in the past with today's journal entry empty: the first ~60s tick called `Notification.show()` with the exact PLAN.md-specified title/body, the simulated click fired the app's `onNotificationClick` callback exactly once, and `lastReminderFiredDate` was persisted to today via the real `POST .../reminder/fired` route; a second tick 60s later (same run, same day) did not refire (one click total across two ticks) — satisfying "fires... and not again after". Separately, on a second scratch workspace with today's journal entry given a real body and `reminderTime` again in the past, a single tick logged zero `Notification.show()` calls — confirms the "already journaled — smart no-op" path. `GET/PUT /api/preferences/launch-at-login` exercised directly (`null` before ever set, persists the exact boolean after). All scratch workspaces/registry entries and processes cleaned up afterward; `npx tsc --noEmit` (server/client/electron) and `npm test` (85 tests) all still clean.

Bucketing logic is transcribed directly from `design/Main.dc.html`'s own dashboard view-model code: overdue (`diff < 0`, hidden entirely when empty), today (`diff === 0`), this week (`0 < diff <= 7`); undated tasks and anything due further out are deliberately excluded from the dashboard (still visible in each project's own Todo column) — not a milestone-14 omission, the design this was built from does the same thing on purpose.

- **Two real bugs found and fixed during live testing** (not just typechecked — see "Verified live" below):
  1. **Journal autosave lost an edit made just before navigating away.** The original implementation scheduled the debounced save from a `useEffect` watching `[body, tags]`, which also raced against the *separate* effect that syncs freshly-loaded server data into that same local state — on the render where loaded data first lands, one effect sees the update and the other doesn't yet, and a stale/empty value could get scheduled for save; navigating away (the day-page remounts entirely on date change, by design) could then flush that stale value before the correct one ever got a chance to overwrite it, observed live as a typed tag and body edit reverting to empty on disk. Fixed by driving saves only from the actual `onChange` handlers via an explicit `dirtyRef` flag (true only on a real edit, cleared on load-sync and on successful save) instead of diffing two independently-updated snapshots — removes the ambiguity entirely rather than papering over the race. A `useEffect` with an empty dependency array now flushes any still-dirty edit synchronously in its cleanup (fire-and-forget `PUT`) so a fast prev/next-day click never drops work.
  2. **A 404 (e.g. a bad project slug in the URL) could crash `ProjectDetailPage`** with "Cannot read properties of undefined (reading 'project')". Fixed at the `QueryClient` level (`main.tsx`): a 4xx (`ApiError` with `statusCode < 500`) is never retried (a bad slug won't start existing on attempt 2), 5xx/network errors keep the default retry behavior; `ProjectDetailPage` also gained a defensive `if (!data) return <Loading/>` rather than relying solely on that timing invariant holding forever.

## Milestone 3 notes
- `electron/src/main.ts` **spawns** the server as its own process (via the hoisted `tsx` binary in dev, fixed port `4174`) rather than importing it in-process — keeps the server always running under a real `node:sqlite`-capable Node regardless of which Node version a given Electron release bundles, and keeps electron's own `tsconfig.json` from having to reach across into `server/src` (separate CommonJS project, no cross-package `rootDir`). Waits for `/api/health` before opening the `BrowserWindow`.
- `electron/src/preload.ts` exposes the full `window.pivot` bridge contract (`pickFolder`, `getLaunchAtLogin`/`setLaunchAtLogin`, `getReminderSettings`/`setReminderSettings`) per PLAN.md's Desktop shell section. `pickFolder` and the launch-at-login pair have real `ipcMain.handle` wiring in `main.ts` (login-item via `electron/src/loginItem.ts`, a thin `app.setLoginItemSettings` wrapper — trivial enough to build now even though the fuller registry-backed version is milestone 17). The reminder-settings pair is declared but **not yet wired** — no handler is registered until milestone 17 builds the per-workspace `reminderTime` data model and `reminder.ts` scheduler; calling it before then rejects with Electron's own "no handler registered" error.
- `electron/src/tray.ts` — minimal tray (Open/Quit) needed for the hide-not-close pattern to be testable at all; the reminder-specific tray items land in milestone 17. Uses a real generated PNG (`electron/src/assets/tray-icon.png`), not `nativeImage.createEmpty()`, which renders invisible on some platforms.
- Window `close` is intercepted (hide, not destroy); `window-all-closed` is a no-op; only the tray's Quit (or `before-quit`) actually quits. On real quit, `stopServer()` uses `tree-kill` to kill the server's **whole** process tree by PID, not just the immediate child — `tsx` spawns its own grandchild loader process, and killing only the wrapper leaked an orphaned server on quit until this was caught during verification.
- The server subprocess is spawned **without** `detached: true` (a first attempt detached it so `stopServer()` could group-kill tsx's grandchild via a negative-PID signal). That broke `npm run dev` + Ctrl+C: a real terminal sends SIGINT to the *whole foreground process group*, and detaching removed the server from that group, so its cleanup then depended on Electron's own JS-level `app.quit()` racing against its own Chromium helper processes (gpu-process, network utility) receiving that same raw signal independently — unreliable, and empirically it left orphaned Electron helpers *and* the server itself running, with `concurrently` hanging forever waiting for them. Fix: leave the server in the group (so a raw Ctrl+C reaches it directly and it dies on its own — no orchestration needed) and use `tree-kill` (walks by PID, not group membership) only for the *explicit* graceful-quit path. Verified by scripting the actual `npm run dev` → Ctrl+C sequence twice (simulating a real terminal by sending `SIGINT` to the whole process group) and confirming zero leftover processes within ~1s each time.
- Root `package.json`: added the `electron` workspace (package renamed to `pivot-electron` internally — naming the workspace itself `electron` collides with the `electron` npm dependency it needs and made npm nest a duplicate copy instead of hoisting it) and repointed `npm run dev` at client+electron (electron's own dev script spawns the server itself, so root no longer also launches `server` directly).
- Added a minimal, deliberately unstyled `client/` scaffold (Vite + React + TS: `vite.config.ts` proxies `/api` to the fixed dev port `4174`, `App.tsx` just renders embedded-server health + active workspace) — needed as infrastructure for this milestone's own verify step, not the real frontend (that's milestones 11-16).
- **Verified live** (not just typechecked): built a one-off Playwright `_electron` driver, ran it under this machine's real X display — launched the app, confirmed the window shows "Embedded server: ok" / "Active workspace: none", called the equivalent of the window's close button and confirmed the window persisted (hidden, not destroyed) while the server process kept running, then simulated the tray's reopen and confirmed the window came back responsive. No permanent driver script was committed (one-off verification, not a recurring need yet); a future `run`-skill pass can build a persistent one if headless Electron testing becomes routine.
- Gotcha for future reinstalls: `electron`'s postinstall binary download has silently no-op'd on a plain `npm install` in this sandbox at least once; if `node_modules/electron/dist/electron` (or `electron/node_modules/electron/dist/electron`, depending on how npm hoists it) is missing, `cd` into that package dir and run `node install.js` directly.

## Key decisions log
(Full rationale is in PLAN.md; this is a quick index so a future session doesn't re-litigate them.)

- **Storage**: markdown files are the sole source of truth; SQLite is a derived, always-rebuildable cache — never required to interpret vault content.
- **SQLite library**: `node:sqlite` (built into Node ≥22.5), not `better-sqlite3` (native module, Electron-rebuild friction) or `sql.js` (no real file-backed multi-process concurrency — ruled out because the server + MCP both need concurrent access via WAL mode).
- **Indexing**: reconciliation (stat-diff, parse only changed files) on workspace open, not a blind full reparse — keeps repeat startup fast regardless of vault size.
- **Agent access**: MCP server with full read+write, not a custom in-app chat/OpenAI-compatible feature — any MCP host supplies the agent loop for free.
- **Undo safety net for agent edits**: every workspace is its own git repo, auto-committed on every write (tagged by origin: `[api]` vs `[mcp:<tool>]`), with revert/history routes — independent of whatever approval flow the connecting MCP host does or doesn't have.
- **Multi-workspace**: Obsidian-style — any folder can be a workspace, app-level registry at `~/.pivot/config.json`, one active workspace per running app instance, MCP targets an explicit workspace independent of what's open in the app.
- **Remote sync**: git push/pull to a user-supplied remote, no credential management (shells out to the user's own git setup); conflicts are surfaced, never auto-merged. Built behind a `SyncProvider` interface so Google Drive/WebDAV could be added later without a redesign — though passive folder-sync via those tools already works today with zero extra code.
- **Desktop shell**: Electron, not a plain browser-opened web app (direction change) — a thin wrap: the main process launches the existing Express server locally and points a `BrowserWindow` at it, no IPC rewrite of the REST API. Chosen specifically to get a native folder picker and a reliable daily reminder (native OS notification), neither of which a browser tab can do. The main process **spawns** the server as its own process (not an in-process import) — see "Milestone 3 notes" for why.
- **Daily reminder**: tray-resident app (window close hides, doesn't quit) with start-at-login **on by default but user-toggleable**; per-workspace reminder time in `~/.pivot/config.json`; a main-process scheduler fires a native notification only if today's journal entry is still empty, once per day.
- **Indexing (milestone 4)**: reconciliation is a pure `mtime` stat-diff, not a content-hash compare — a file touched without content changes still gets reparsed. `source_hash` is stored but not load-bearing for staleness today. Non-blocking startup reconciliation is deliberately *not* wired into workspace open yet — no consumer needs it until the aggregate routes (milestone 9) exist.
- **Git identity/history (milestone 5)**: workspaces get a real initial commit (`ensureGitHistory` in `vaultGit.ts`, called from `services/workspaces.ts` in place of the bare `ensureGitRepo`) and a local git identity fallback if the user has no global one configured — both needed for `commitChange`/`revertCommit` to work reliably in a fresh environment, not just conceptually.
- **Frontmatter date normalization**: `lib/markdown/frontmatter.ts`'s `parseFrontmatter` recursively coerces any js-yaml-parsed `Date` back to `YYYY-MM-DD` — an unquoted date scalar (`created: 2026-09-10`, no quotes) is exactly how a human hand-edits the file and otherwise breaks anything downstream expecting a string (found because it broke SQLite parameter binding in milestone 4).
- **Structured service errors (milestone 7)**: `lib/httpError.ts`'s `HttpError` is now the one base class every service module's structured error extends (`WorkspaceServiceError`, `ProjectServiceError`, `TaskServiceError`, `SyncServiceError`) — `index.ts`'s error handler checks `instanceof HttpError` generically instead of importing and special-casing each one.
- **Conflict-safe git pull (milestone 6)**: `lib/sync/gitRemote.ts`'s `pull` never lets a conflicted merge land on disk — it stages a merge with `--no-commit`, inspects `git status --porcelain` for conflict markers, and `git merge --abort`s if any are found, returning the conflicted file list as plain data (not a thrown error) rather than attempting to auto-resolve. `push`/`pull` require a remote already configured via `setRemote`; no credential management, shells out to the user's own git.
- **Task write path reuses the project file I/O (milestone 7)**: `services/tasks.ts` has no filesystem code of its own — `services/projects.ts` exports `loadProjectFile`/`saveProjectFile` (the parse and serialize-write-reindex-commit halves of PLAN.md's write-path order) specifically so task CRUD reuses them, since a task's only storage is as a block inside its project's file. Project color auto-assignment cycles through a fixed 12-color palette by *current project count at creation time* (no separate persistent counter).
- **Journal GET auto-defaults instead of 404ing (milestone 8)**: a `GET` for a date with no file yet returns an in-memory default entry rather than an error — nothing is persisted until an actual write, so opening/browsing dates never creates empty files or git commits. `linkTask` auto-creates the file (PLAN.md, explicit); `unlinkTask` never does (nothing to remove from a file that doesn't exist).
- **Aggregate queries are isolated to `lib/index/queries.ts` (milestone 9)**: all direct `node:sqlite` access for read-only aggregate views (open tasks, search, calendar, time-spent) lives in this one file, matching `db.ts`/`reindex.ts`'s existing isolation of the still-experimental API — `services/{tasks,calendar,reports}.ts` call into it rather than opening `DatabaseSync` connections themselves. Time-spent reporting does its date-filter/group/live-elapsed math in JS over the full task set rather than in SQL, since the file format only stores one cumulative `@spent` total per task (no per-session log to group by day in the database).
- **MCP workspace targeting is resolved once, at process startup (milestone 10)**: `mcp/index.ts` reads `PIVOT_WORKSPACE` (or falls back to the app registry's active workspace) exactly once and threads that fixed path through every tool call for the process's whole lifetime — an active-workspace switch made later through the REST API/app UI never reaches an already-running MCP server. Verified live, not just asserted. Every MCP tool is tagged `mcp:<tool_name>` as its git commit origin, and errors are returned as structured `isError: true` tool results (never thrown) so the calling agent can read and self-correct rather than hitting a raw protocol failure.
