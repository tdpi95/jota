# Milestone 19 notes (Localization)

[← back to PROGRESS.md](../../PROGRESS.md)

- Scope decided with the user up front (CLAUDE.md: don't add a feature not already in PLAN.md without checking first): covers client UI *and* Electron's own native strings (tray menu, daily-reminder notification), the language preference is a single app-wide setting (not per-workspace), and the client uses `react-i18next` rather than a hand-rolled dictionary. PLAN.md gained a new "Localization" design section, a milestone-19 bullet + Verify step, and a `client/src/i18n/` line in the Project scaffold.
- **Storage**: `WorkspaceRegistry.language?: 'en' | 'vi'` (`server/src/lib/workspaces.ts`), read/write via `services/workspaces.ts`'s `getLanguagePreference`/`setLanguagePreference` — same shape as `launchAtLogin` except it normalizes `undefined` straight to `'en'` (no "undecided" state to track, unlike launch-at-login's one-time OS-default logic). `routes/preferences.ts` gained `GET/PUT /api/preferences/language`. Covered by a new case in `server/src/services/workspaces.test.ts` (92 tests total now, up from 91).
- **Deliberately no Electron preload/IPC bridge for this** — unlike launch-at-login/reminder settings, a language switch touches no OS-level API, so the client calls `GET/PUT /api/preferences/language` directly over HTTP (`api/client.ts`'s `getLanguagePreference`/`setLanguagePreference`) and works the same in a plain browser tab as inside Electron. The Electron main process still needs to know the language for its *own* native strings, so it polls the same route directly (see below) rather than going through the renderer.
- **Client scaffold**: `client/src/i18n/index.ts` (`i18next.use(initReactI18next).init(...)`, resources bundled statically from `en.json`/`vi.json`, not lazy-loaded — two languages, not worth the split). `main.tsx` resolves the stored preference (`getLanguagePreference()`) and calls `i18n.changeLanguage` *before* the first `createRoot(...).render(...)` — avoids a flash of the wrong language while that fetch is in flight, falling back to i18next's own default `'en'` on any failure.
- **`SettingsPage.tsx` gained a Language section** (EN/VI toggle buttons, reusing the existing `.ws-row-btn`/`.is-active` styling plus a small new `.lang-picker` flex-row rule in `app.css`) — not gated behind `getPivotBridge()` like the reminder/launch-at-login sections below it, since it works in a browser tab too. Clicking a language calls `api.setLanguagePreference` then `i18n.changeLanguage` in the mutation's `onSuccess` — persists *and* switches instantly, no reload.
- **Electron native strings** (`electron/src/i18n.ts`, new — a small hand-rolled `Record<Lang, {...}>` dictionary, not `react-i18next`, since this runs in the non-React main process for exactly four strings: tray tooltip/Open/Settings/Quit and the daily-reminder notification's title/body): `tray.ts`'s `createTray` now takes a `language` param for its initial build, and a new exported `applyTrayLanguage(tray, callbacks, language)` rebuilds the tooltip+menu in place. `main.ts` fetches the language once at startup (a new `fetchLanguage(port)` helper, same "default to 'en' on any failure" pattern as everything else here) before creating the tray, and keeps a module-level `tray`/`trayCallbacks` pair so a later language change can rebuild it. `reminder.ts`'s already-existing once-a-minute poll gained a second fetch (`GET /api/preferences/language`) run on *every* tick regardless of the reminder logic's own early-returns (no active workspace, already journaled today, etc. — language isn't tied to workspace state), which both translates that tick's notification text and, only on an actual change from the previous tick, invokes a new `onLanguageChange` callback that `main.ts` wires to `applyTrayLanguage` — so a language switch made in Settings reaches the tray within a minute, no app restart, reusing the existing poll rather than adding a second timer.
- **Every remaining page/component converted**: `DashboardPage`, `ProjectsListPage`, `ProjectDetailPage`, `JournalYearPage`, `JournalDayPage`, the rest of `SettingsPage` (workspaces/sync/reminder/launch-at-login sections), `AppShell`, `CalendarSidebar`, `DueDateBadge`, `HistoryPanel`, `Modal`, `ProjectCard`, `ProjectForm`, `TagInput`, `TaskForm`, `TaskRow`, `TimeSpentBadge`, `WorkspaceSwitcher` all now go through `useTranslation()`/`t()` — `en.json`/`vi.json` hold 166 identical leaf keys each, namespaced per page/component (`dashboard.*`, `projectsList.*`, `taskRow.*`, etc.), reusing `common.*` for generic actions. `window.confirm(...)` messages and dynamic labels use i18next interpolation (e.g. `t('taskRow.confirmDelete', {text: task.text})`), never manual string concatenation.
- **`lib/date.ts`** — `formatDueShort`/`formatDateLong` gained an optional `language: 'en' | 'vi' = 'en'` parameter (every call site now passes `i18n.language` from its own `useTranslation()`), plus a new `monthShortLabel` for `CalendarSidebar`'s month header. Vietnamese doesn't abbreviate month names the way English does ("Tháng 9" is both the full and short form), so `MONTH_NAMES_VI` covers both; day/month order swaps per language (`"Sep 10"` vs `"10 Tháng 9"`); the weekday name in `formatDateLong` comes from `Intl`/`toLocaleDateString('vi', ...)` rather than a hand-rolled list, since the platform already knows Vietnamese weekday names. `formatTimestamp` (git-commit/last-synced timestamps) was deliberately left alone — it already follows the browser's own locale via `toLocaleDateString(undefined, ...)`, not a hardcoded language.
- **Verified**: `npm test -w server` (92 tests, all passing); `npx tsc --noEmit` clean for `server/`, `client/`, and `electron/`; `npm run build -w client` clean; a throwaway script confirmed `en.json`/`vi.json` have identical key trees (166 leaf keys each); a manual grep sweep for stray hardcoded JSX text/`placeholder=`/`title=`/`window.confirm(...)` across every changed page/component turned up nothing left over (one incidental `.filter((t) => …)` naming collision with the `t` translation function in `JournalDayPage.tsx` was harmless but renamed to `task` for clarity). **Verified live** against the real running server + Vite dev server in an actual browser: registered a scratch workspace (`i18n verify`, cleaned up afterward — the real `Pivot Demo` workspace already registered was left untouched throughout, never opened or modified), seeded a project + task, and clicked "Tiếng Việt" on `/settings` — every visible page (Dashboard, Projects, the project detail Kanban board + History panel, Journal day, Settings itself including the calendar sidebar's weekday/month labels) switched instantly with no reload, including `formatDateLong`'s weekday+month localization ("Thứ Sáu, 11 Tháng 9, 2026") and the calendar's "CN T2 T3 T4 T5 T6 T7"/"Tháng 9 2026". Switched back to English, reloaded the page, and confirmed the choice persisted (read back from `GET /api/preferences/language` before first render, per `main.tsx`). Not click-tested inside an actual packaged/launched Electron window in this pass (tray menu + daily-reminder notification) — that side was verified at the code level only (see milestone 17's own precedent for testing `reminder.ts` directly under a real `electron` process, which the tray-language-poll wiring here reuses the exact same scheduler for).
