# Milestone 7 notes

[← back to PROGRESS.md](../../PROGRESS.md)

- `server/src/services/projects.ts` — `createProject`/`getProject`/`listProjects`/`updateProject`/`deleteProject`. Color auto-assignment (`COLOR_PALETTE`, 12 fixed hex colors) is cycled by the *current* number of project files at creation time (`existingSlugs.length % 12`) — there's no separate persistent creation counter, so this is the natural proxy for "creation order" PLAN.md asks for; a caller can still override with an explicit `color`. Exports `loadProjectFile`/`saveProjectFile` (the read-parse and serialize-write-reindex-commit halves of the write path) specifically so `services/tasks.ts` reuses the exact same file I/O rather than duplicating it — a task always lives inside its project's file, so "create a task" *is* "rewrite the project file with one more block".
- `server/src/services/tasks.ts` — `createTask`/`updateTask`/`deleteTask`, all operating on the `ProjectBodyBlock[]` a project file parses into. `applyStatusTransition` is PLAN.md's "Doing-timer transition" pseudocode transcribed directly (same-status no-op guard, fold elapsed `doing` time into `spentMinutes` via `date-fns`'s `differenceInMinutes`, `doneAt` set/cleared on entering/leaving 'done'). The live "N (tracking...)" ticking value PLAN.md describes is explicitly a frontend concern (milestone 11) — `@spent` here only ever updates on an actual status transition, never on a timer tick, per PLAN.md's write-amplification note.
- Both services follow PLAN.md's write-path order exactly: read → parse → mutate → serialize → write file (authoritative) → `reconcileWorkspace` (best-effort, logged-and-swallowed on failure — reuses milestone 4's stat-diff reconciliation rather than a separate incremental-upsert code path, since a single-file reconcile after a write is just one stat + one reparse) → `commitChange` (best-effort, milestone 5) → return the in-memory structured form (never re-read from disk or the index to respond).
- `server/src/lib/httpError.ts` — new shared `HttpError` base class; `WorkspaceServiceError` now extends it, and `ProjectServiceError`/`TaskServiceError`/`SyncServiceError` (milestone 6) do too. `index.ts`'s error handler now checks `instanceof HttpError` generically instead of special-casing `WorkspaceServiceError` — no behavior change, but every service module's structured errors map to the right HTTP status without the handler having to know about each one.
- `server/src/routes/projects.ts` (`GET/POST /api/projects`, `GET/PATCH/DELETE /api/projects/:slug`) and `server/src/routes/tasks.ts` (`POST /api/projects/:slug/tasks`, `PATCH/DELETE .../tasks/:taskId`, mounted at that path with `Router({ mergeParams: true })` so `:slug` from the parent mount is visible) — both thin, per CLAUDE.md.
- Verified live: registered a scratch workspace, created two projects via `POST /api/projects` and confirmed the second got the next palette color; created a task, PATCHed it todo→doing (confirmed `@doingSince` appended to the file line) then doing→todo two seconds later (confirmed `@doingSince` removed, `@spent` not added since sub-minute durations round to nothing per `formatDuration`), and cross-checked `GET /api/index/status` and `git log` (`create_project`/`create_task`/`update_task ... status todo→doing`/`update_task ... status doing→todo`) all agree.
