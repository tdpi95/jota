# Milestone 6 notes

[← back to PROGRESS.md](../../PROGRESS.md)

- `server/src/lib/sync/types.ts` — the `SyncProvider` interface PLAN.md calls for (`getRemote`/`setRemote`/`push`/`pull`/`status`), plus `SyncStatus`/`PullResult` shapes. `gitRemote.ts` is the only v1 implementation.
- `server/src/lib/sync/gitRemote.ts` — shells out to the user's own `git` (no credential management, per PLAN.md). `pull` is the interesting one: tries `git merge --ff-only` first (the common, can't-conflict case), and only if that fails falls back to a *staged* (`--no-commit --no-ff`) merge attempt so it can be inspected via `git status --porcelain` before anything is finalized — any `UU`/`AA`/etc. line means conflict, in which case `git merge --abort` runs and the conflicted file list is returned as plain data (`{conflict: true, files: [...]}`), never thrown, since a conflict is an expected outcome for the caller to surface, not a failure. This is what makes "never attempt an auto-merge" (PLAN.md) real: the working tree is provably back to its pre-pull state on conflict, not left with conflict markers in a task file.
- `WorkspaceEntry` (`lib/workspaces.ts`) gained an optional `sync` field: `{ provider: 'none' }` (the default, and what an entry written before this milestone implicitly means) or `{ provider: 'git-remote', remoteUrl, lastSyncedAt }` — `lastSyncedAt` isn't in PLAN.md's illustrative registry shape but is needed to back the status route's "last sync time" and belongs with the rest of the sync config rather than as a separate top-level field.
- `server/src/services/sync.ts` bridges the registry's `sync` field with `gitRemote.ts`: `setRemote` writes through to both git (`git remote add/set-url`) and the registry; `push`/`pull` require a remote to already be configured (structured 400 otherwise); a successful (non-conflict) `pull` re-runs `reconcileWorkspace` afterward, same pattern as milestone 5's revert route, since pulled files may have changed under the index. `push`/`pull` failures from git itself (network, auth, no upstream) surface as 502 with git's own stderr.
- `server/src/routes/sync.ts` — `GET/PUT /api/vault/git/remote`, `POST /api/vault/git/push`, `POST /api/vault/git/pull` (returns the `PullResult` — conflict is a 200 with `{conflict: true, files}`, not an error status), `GET /api/vault/git/status`; mounted at `/api/vault/git` (registered before the broader `/api/vault` router in `index.ts`, though Express's path matching means order wouldn't actually matter here — `/api/vault`'s own routes don't overlap `/git/*`).
- Verified live: pointed a scratch workspace at a local bare repo as `origin`, pushed, cloned that bare repo as a second scratch workspace ("device B"), pushed a conflicting edit to the same frontmatter line from device B, made a *different* local edit to that same line through the running server's `PATCH /api/projects/:slug`, then called `POST /api/vault/git/pull` — got back `{"conflict":true,"files":["projects/website-redesign.md"]}`, confirmed the local file still read the local edit verbatim (not remote's, not conflict-marker mush) and `git status --porcelain` was empty (merge cleanly aborted, no leftover state).
