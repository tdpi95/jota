# Milestone 10 notes

[← back to PROGRESS.md](../../PROGRESS.md)

- `server/src/mcp/index.ts` — the standalone stdio entrypoint (`npm run mcp -w server`, or `PIVOT_WORKSPACE=<path> npx tsx server/src/mcp/index.ts` directly). Resolves the target workspace **exactly once at startup** — `PIVOT_WORKSPACE` env var if set, else the app registry's currently-active workspace via `services/workspaces.ts`'s `getActiveWorkspace()` — and passes that fixed path into every tool call for the life of the process. This is what makes PLAN.md's "MCP is decoupled from whichever workspace the app has open" true in practice, not just in principle: verified live (see below) that switching the active workspace through the REST API mid-session does not change what an already-running MCP server operates on. Also self-heals the target folder the same way opening a workspace in the app does (`scaffoldWorkspaceDirs` + `ensureGitHistory`) — so an MCP host can point straight at a brand-new plain folder that was never registered through the app UI at all.
- `server/src/mcp/tools.ts` — all 14 tools from PLAN.md's list, each a thin wrapper calling the exact same `services/{projects,tasks,journal}.ts` functions the REST routes use, tagged `mcp:<tool_name>` as the git commit origin (so `git log` always shows which MCP tool — not just "an agent" — made a change). Uses the SDK's `McpServer.registerTool` (the current, non-deprecated API) with zod input schemas. A caught `HttpError` (or anything else) is returned as `{content:[...], isError: true}`, never thrown — a thrown error surfaces as a raw JSON-RPC protocol failure instead of something in the conversation the model can read and react to (PLAN.md: "errors are structured and returned to the model ... so the agent can self-correct"). `get_task_summary` returns pure structured data (counts by status/project, overdue count, the filtered task list) with no narration — per PLAN.md, the calling agent does that part.
- **"Did you mean" (PLAN.md's own MCP error example)**: `server/src/lib/didYouMean.ts` is a small Levenshtein-distance helper; wired into `services/projects.ts`'s project-not-found error (shared by `loadProjectFile` and `deleteProject`, so both `get_project`/`update_task` *and* the REST API's `GET/PATCH/DELETE /api/projects/:slug` benefit, not just MCP) — `no project with slug "wbsite-redesign" — did you mean: website-redesign?`.
- `services/tasks.ts` gained `getTaskSummary` (backing `get_task_summary`), reusing `lib/index/queries.ts`'s `queryAllTasksForReport` — the same full-task-dump `services/reports.ts` already used — plus a new shared `relevantDateOf` helper extracted out of `reports.ts` so both consumers bucket "when" a task counts the same way (`doneAt` → `due` → creation date). `projectSlug` filtering is validated through `getProject` (free 404 + did-you-mean) rather than a bespoke existence check.
- **Tested through a real MCP client, not just the service layer directly**: `server/src/mcp/tools.test.ts` uses the SDK's own `Client` class connected to the registered `McpServer` over `InMemoryTransport.createLinkedPair()` — a genuine client↔server JSON-RPC round trip in-process, not curl and not calling `registerTools`'s handlers directly. Covers the full tool list, a create→update→journal-link chain cross-checked against the file/git history, `get_task_summary`'s structured shape, the did-you-mean error path, and — mirroring PLAN.md's verify step precisely — making an "unwanted" change via a tool call and confirming `lib/vaultGit.ts`'s `revertCommit` (the same function `POST /api/vault/revert/:commit` calls) cleanly undoes it.
- **Verified live** (a real spawned stdio subprocess, not the in-memory transport used for the automated test): drove `npx tsx server/src/mcp/index.ts` via a one-off `StdioClientTransport` script — listed tools, created a project+task, transitioned it to `doing`, pulled `get_task_summary`, and hit the did-you-mean path, all matching the automated test's expectations; confirmed the target folder was self-scaffolded (`.git`/`.pivot`/`projects`/`journal` all created from nothing) with real git history tagged `[mcp:create_project]`/`[mcp:create_task]`/`[mcp:update_task]`; then, from a separately-running Express server pointed at the *same* workspace, called `POST /api/vault/revert/:commit` on the MCP-made `update_task` commit and confirmed the file's `@doingSince` was cleanly removed — the undo mechanism worked across front doors. Finally, registered a second, different workspace as active via the REST API while the MCP server (targeted via `PIVOT_WORKSPACE`) was still running, and confirmed `list_projects` on the MCP server still returned the original workspace's data, untouched.
