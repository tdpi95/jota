# Milestone 20 notes (Frontend Calendar page)

[← back to PROGRESS.md](../../PROGRESS.md)

- Scope requested directly by the user, mid-session, ahead of milestone 18's remaining items (same pattern as milestone 19): "add calendar page that show task titles with option to show by logged in journal or due date." PLAN.md gained a `/calendar` bullet under "Frontend", a `CalendarPage` line in the Project scaffold's `pages/` list, and a milestone-20 entry + Verify step.
- **New page, not a route on an existing one**: `client/src/pages/CalendarPage.tsx`, wired into `App.tsx`'s router and a new "Calendar" nav item in `AppShell.tsx` (its own icon, placed between Journal and Settings). Deliberately separate from the already-existing `CalendarSidebar` (milestone 13) rather than replacing it — the sidebar stays a compact always-visible dot grid; this page is a full-width task-title view someone navigates to.
- **Backend**: `CalendarTaskMark` (`server/src/lib/index/queries.ts`) gained `text` and `status` fields (both due-task and linked-task join queries in `queryCalendarMonth` now select `t.text, t.status`) — the existing `GET /api/calendar/:year/:month` endpoint (already used by `CalendarSidebar`) didn't need a new route, just richer marks, since a full-page view needs to print the task itself rather than a color dot. Mirrored in `client/src/types.ts`'s `CalendarTaskMark`. Covered by two new assertions in `calendar.test.ts` (101 tests total now, up from 92).
- **Due/journal toggle**: a `CalendarTaskMark.reason` is `'due'` (the task's own due date) or `'linked'` (that day's journal entry links to it) — the toggle's own vocabulary (`'due'`/`'journal'`) is mapped to `reason` via a small `reasonForMode` record rather than reusing the same two strings directly, since "journal" (the toggle label) and "linked" (what the mark actually means) read better each in their own context. Caught and fixed a real bug here during verification: an early version filtered `mark.reason === mode` directly, which meant "Journal log" mode silently matched nothing (mode value `'journal'` never equals reason value `'linked'`) until the mapping was added.
- **Column-width bug (and fix)**: task titles initially could stretch one day's grid column wider than its neighbors despite `text-overflow: ellipsis` already being set on `.cp-task-text` — the ellipsis rule was never actually being hit. Root cause: CSS grid/flex items default to a content-based `min-width`, so a long unbreakable title propagated its intrinsic width all the way up through `.cp-task` (flex row) and `.cp-day` (grid item) before the grid's `1fr` column sizing ever got a chance to constrain it. Fixed with `min-width: 0` on `.cp-day` and `.cp-task`, plus `flex: 1; min-width: 0` on `.cp-task-text` itself — a good example of why `text-overflow: ellipsis` alone is never sufficient inside nested flex/grid without also breaking the min-width chain.
- **Journal-entry highlight, iterated a few times over the session**: started as a small dot next to the day number (matching `CalendarSidebar`'s existing dot); the user asked for a stronger signal, so `.cp-day.has-journal` (a soft `var(--good-soft)` background wash) was added; then asked to drop the now-redundant dot entirely in favor of a hover tooltip on the day number itself (`title={t('calendarPage.openJournalEntry', {date: ...})}`, native browser tooltip); then asked for the same soft-wash highlight to also appear in `CalendarSidebar` (added as `.cal-day.has-journal`, ordered in the stylesheet *before* `.today`/`.selected` so those stronger states still win when a day is both — same technique reused for `.cp-year-day.has-journal` vs `.cp-year-day.today` in the year overview below). `CalendarSidebar` kept its dot (only the full page's dot was removed).
- **`CalendarSidebar` layout-shift fix**: the sidebar's trailing-cell padding used to stop at the next multiple of 7 (`while (cells.length % 7 !== 0)`), so a 4-row month (e.g. Feb 2026, 28 days starting on a Sunday) rendered a shorter grid than a 5- or 6-row month — shifting the persistent sidebar content around it (the calendar sits at the bottom of the nav column via `margin-top: auto`) every time the user browsed months. Fixed by always padding to a fixed 42 cells (6 rows); the extra trailing cells stay `visibility: hidden` (already the existing `.cal-day.blank` rule), which still reserves their layout space. Verified by measuring `.cal-grid`'s `getBoundingClientRect().height` before/after navigating from September (5 rows of real days) to February (4) — identical 151px both times.
- **Year overview** (click the month/year label): `granularity` state (`'month' | 'year'`) toggles between the existing month grid and a new 12-mini-month `.cp-year-grid`. Deliberately built as a fast month-picker, not another place to read task state — no per-month due/linked-task query runs while it's open (`enabled: granularity === 'month'` on the existing `useQuery`). It does still highlight journal-entry days, added after the user asked for it explicitly as a follow-up: a *separate*, much cheaper `GET /api/journal/:year` call (the same endpoint `JournalYearPage` already uses), gated `enabled: granularity === 'year'`, returning every entry for the year in one request rather than one calendar query per month. Verified via `read_network_requests` that opening the year view fires exactly one `/api/journal/2026` call and zero `/api/calendar/*` calls. Clicking a mini-month's header returns to month view on that month; "Today" and the prev/next arrows adapt to whichever granularity is active (year-shift vs month-shift).
- **Toggle icons**: added a clock icon (due date) and a notebook icon (journal log, reusing `AppShell`'s own Journal nav-icon SVG path so the same visual metaphor means the same thing in both places) to the due/journal toggle buttons, via a small `MODE_ICONS` map and a `.cp-mode-btn` flex rule.
- **i18n**: all new strings went through `calendarPage.*` (title, mode toggle + hints, today/loading/failedToLoad, showMore/showFewer, weekdayLabels, openJournalEntry, pickMonth/yearOverview/previousYear/nextYear) plus one new `appShell.nav.calendar` key — `en.json`/`vi.json` stayed structurally identical throughout (188 → 202 → 206 leaf keys across the session's several additions), checked with a throwaway key-diff script after each change.
- **Verified**: `npm test -w server` (101 passing), `npx tsc --noEmit` clean for `server/`/`client/`, `npm run build -w client` clean. **Verified live** against the real running embedded server + Vite dev server (the user's own already-running `npm run dev` instance; the embedded server had to be restarted once mid-session since it runs `tsx` without `--watch` and doesn't pick up backend changes on its own) in an actual browser: task titles render and clip correctly without stretching columns; the due/journal toggle genuinely buckets tasks under different days (confirmed against `/api/calendar/2026/09`'s raw JSON); clicking a day number opens `/journal/:year/:date`, clicking a task opens `/projects/:slug` (checked via the rendered `href`); the sidebar's fixed-height fix measured identical before/after across a 5-row vs 4-row month; the year overview renders 12 clean grids with "today" highlighted, journal days highlighted to match the month view, and only one `/api/journal/2026` network call.

## Follow-up: year-view day links + "show all journal entries" (same milestone)

Requested later in the same session: "in year view clicking on day cell direct to that day journal, add a button to show all journal in that year as a list, ellipse with expand button if a journal content is too long; in month view add similar show all journal button."

- **Year-view day cells now link to the journal day**, matching the month view's existing `cp-day-num` pattern exactly. `buildYearMonthCells` gained a `date` field on each non-blank cell (it already computed the `YYYY-MM-DD` string locally, just hadn't stored it); the cell itself changed from a plain `<span>` to a react-router `<Link to={`/journal/${year}/${date}`}>` (blank padding cells stay a `<span>`, unlinked). New `.cp-year-day:hover` rule (background/color shift, mirroring `.cp-day-num:hover`) makes the new affordance discoverable; `.cp-year-day.today:hover` keeps its contrast-safe text color rather than falling through to the accent-colored hover text on top of an already-solid accent background.
- **New backend endpoint, not an index extension**: the existing `GET /api/journal/:year` (`listJournalYear`) is index-backed and deliberately cheap — it was kept as-is rather than teaching the index to cache body text, since the index is a derived, always-rebuildable cache and body was never part of what it stores. Instead, a new `listJournalYearFull` (`server/src/services/journal.ts`) reads a year's files directly off disk (bounded to at most ~366 small files, so a synchronous read-and-parse of all of them is fine) and returns `{date, hasBody, tags, body}[]`. Routed as `GET /api/journal/:year/full`, registered *before* the existing `/:year/:date` route in `routes/journal.ts` — otherwise Express's generic two-segment matcher would catch `/2026/full` first with `date = "full"` and 400 on date validation.
- **New `JournalEntriesList` component** (`client/src/components/JournalEntriesList.tsx`): fetches `listJournalYearFull(year)` via `useQuery(['journalYearFull', year], ...)` only while shown, optionally filtered client-side to one month (`monthFilter`, a zero-padded "01"-"12"); each entry's date still links to `/journal/:year/:date` and its tags render as the same `.tag-pill`s `JournalYearPage` uses. A body over 320 characters or 6 lines gets clamped (`-webkit-line-clamp: 6`) with its own expand/collapse button — a rough length/line-count heuristic to decide whether to clamp at all, not a pixel-exact measurement (the CSS clamp does the actual visual clipping).
- **Iterated twice on presentation before landing on a true either/or toggle**: first built as a popup on top of the existing `Modal` component; corrected to an inline section appended *below* the grid after the user said "in the same page as calendar, not in a modal"; corrected again after the user clarified it should be "a toggle to show between calendar or entries, not both" — the list now *replaces* the grid rather than sitting under it. `Modal` gained and then lost an optional `className` prop (`"modal-wide"`) across the first round-trip. The final version is a plain `<div className="journal-list-section">` rendered directly in `CalendarPage`'s own JSX flow in place of the grid, with its own `<h2>` title and no overlay/backdrop/close button of its own.
- **One button, two meanings, a genuine either/or toggle**: `CalendarPage` gained a single `.cp-show-all-btn` in the shared `cp-header` row, present in both granularities, its label switching between "Show all journal entries" and "Hide journal entries" (and an `.is-active` pressed style, the same convention `.ws-row-btn.is-active` uses) as `showJournalList` toggles. Every other block that only makes sense against the grid — the year grid itself, the month grid plus its weekday header and loading/error states, and the due/journal mode toggle in the page header — is now also gated on `!showJournalList`, so exactly one of "grid" or "list" renders at a time; the page-header hint line swaps to a dedicated `calendarPage.journalListHint` string while the list is showing instead of the mode-toggle hint. Only the `title` and `monthFilter` passed to `JournalEntriesList` differ by `granularity` (year: no filter, title is just the year; month: `monthFilter` = current `monthStr`, title includes the month name) — no separate month-specific listing endpoint was needed since `listJournalYearFull` already returns the whole year and the list filters client-side. The open/closed state and granularity are independent, so switching between month and year view while the list is showing keeps it showing, just re-filtered and re-titled.
- **i18n**: `calendarPage.showAllJournal`/`hideAllJournal` (the toggle button's two labels) and `calendarPage.journalListHint` (the page-header subtitle while the list is showing), plus a new `journalEntriesList.*` namespace (`yearTitle`, `monthTitle`, `loading`, `empty`, `noBody`, `expand`, `collapse`) in both `en.json`/`vi.json` — renamed from an earlier `journalListModal.*` once the component stopped being a modal.
- **New test**: `listJournalYearFull reads bodies straight off disk, scoped to the given year` and a second case for a year with no journal folder yet at all (`server/src/services/journal.test.ts`) — the first caught a real round-trip quirk worth noting: an empty body written via `putJournalEntry` and reparsed comes back as `'\n'`, not `''` (same reason `hasBody` is computed off `.trim().length > 0` rather than a plain emptiness check), so the test asserts `.trim()` equality rather than exact equality.
- **Verified**: `npm test` from the repo root (112 passing, up from 110), `npx tsc --noEmit` clean for both `server/` and `client/`, i18n key-diff script confirms `en.json`/`vi.json` still structurally identical (228 leaf keys each). **Verified live** against the real running dev server (`.claude/launch.json` added — `npm run dev -w server`/`npm run dev -w client` directly rather than the repo-root script, which also launches Electron and can't run headless here; server `PORT` pinned to 4174 to match `vite.config.ts`'s proxy target) in an actual browser, across all three presentation iterations: year-view day cells open the right journal day; the toggle button correctly shows exactly one of grid-or-list at a time in both month and year granularity, correctly filtered and titled either way; a long entry (Jul 21) renders clamped with a working "Show full entry"/"Show less" toggle. One incidental cleanup mid-session: an earlier failed dev-server launch attempt (the repo-root script, which also starts Electron) had left a detached Electron GUI process running in the background from a previous turn — spotted via a port-5173 conflict, confirmed as a dev-mode instance (not the AppImage-packaged app, and not the terminal's own foreground process) before being stopped.

## Follow-up: persist the due/journal toggle across restarts (same milestone)

Requested later in the same session: "save state of due date or journal log between restarts." The toggle's `mode` (`ViewMode`, `'due' | 'journal'`) had been plain in-memory `useState` since the mode toggle first shipped — reset to `'due'` on every reload, no persistence of any kind.

- **Followed the established app-wide-preference recipe exactly** (mirroring `theme`/`accentPalette` from milestone 21, itself mirroring `language`): `calendarMode?: 'due' | 'journal'` added to `WorkspaceRegistry` (`server/src/lib/workspaces.ts`, `undefined` normalizes to `'due'`, the toggle's pre-existing default); `getCalendarModePreference`/`setCalendarModePreference` in `server/src/services/workspaces.ts`; `GET/PUT /api/preferences/calendar-mode` in `server/src/routes/preferences.ts` (PUT 400s on anything but `'due'`/`'journal'`); matching `getCalendarModePreference`/`setCalendarModePreference` in `client/src/api/client.ts`. Same `~/.jota/config.json`, no new storage mechanism.
- **No `main.tsx` bootstrap involvement, unlike theme/language/accent-palette**: those are fetched before first render specifically to avoid a flash of the wrong appearance/language on the very first paint. A due/journal toggle label (and which tasks a day shows) isn't that kind of first-paint concern, so `CalendarPage` just fetches it itself via `useQuery(['calendarModePreference'], ...)` on mount and applies it with a `useEffect` once it resolves, on top of the same `useState<ViewMode>('due')` default as before — there's a brief instant on load where the toggle shows `'due'` before the real preference arrives (confirmed live: resolves well under a second against localhost), same tradeoff `getJournalEntry` already accepts elsewhere for "show something immediately, correct it once the real data arrives" rather than blocking first paint on every preference fetch.
- **Toggling still writes through immediately**: `setMode` split into a `changeMode` wrapper that updates the local `mode` state (so the toggle button responds instantly, no round-trip wait) and fires a `useMutation` calling `setCalendarModePreference` in the background — no `onSuccess`/local-state sync needed since the local state already changed synchronously, unlike `SettingsPage`'s theme/language pickers which sync local state from the mutation's result instead of setting it eagerly.
- **New test**: `calendar mode preference defaults to due and persists an explicit choice` in `server/src/services/workspaces.test.ts`, same shape as the existing `accent palette preference...` test right above it.
- **Verified**: `npm test` from the repo root (113 passing, up from 112), `npx tsc --noEmit` clean for both `server/` and `client/`. **Verified live**: switched to "Journal log" in a real browser, confirmed `GET /api/preferences/calendar-mode` returned `{"calendarMode":"journal"}` via a direct `curl` against the embedded server (bypassing the client entirely), then forced a genuine `location.reload()` (not just an in-app navigate, which wouldn't re-run the SPA's bootstrap) and confirmed the toggle came back showing "Journal log" — then repeated in the other direction (back to "Due date") to confirm both values round-trip, not just the non-default one. Incidental cleanup: two more stray dev-server processes from earlier in the session were found still bound to ports 5173/4174 (the same `preview_stop`-doesn't-always-kill-the-`tsx watch`-child issue as the previous follow-up) and were stopped before verifying.

## Follow-up: persist month/year granularity too (same milestone)

Requested immediately after the previous follow-up landed: "also save year or month view." Same shape as `calendarMode`, applied to `granularity` (`Granularity`, `'month' | 'year'`) instead.

- **Identical recipe, second field on the same registry**: `calendarGranularity?: 'month' | 'year'` added to `WorkspaceRegistry` (`undefined` normalizes to `'month'`, the page's pre-existing default); `getCalendarGranularityPreference`/`setCalendarGranularityPreference` in `services/workspaces.ts`; `GET/PUT /api/preferences/calendar-granularity` in `routes/preferences.ts`; matching functions in `client/src/api/client.ts`. No new concepts versus the `calendarMode` follow-up above — same `useQuery` + `useEffect`-on-mount + `useMutation` shape in `CalendarPage`, a second, independent `changeGranularity` wrapper alongside `changeMode`.
- **Three call sites needed updating, not one**: unlike `mode` (a single toggle button), `granularity` is set from three places — the month/year label's own toggle click, `goToToday()` (which always forces month view), and clicking a mini-month header from the year overview (which also forces month view). All three now go through `changeGranularity` instead of the bare `setGranularity`, so every path that changes granularity persists it, including the two "forced to month" paths — landing on today's month or drilling into a specific month from the year overview both count as the user now being in month view, so both are worth remembering too.
- **New test**: `calendar granularity preference defaults to month and persists an explicit choice` in `workspaces.test.ts`, same shape as `calendarMode`'s test directly above it.
- **Verified**: `npm test` from the repo root (114 passing, up from 113), `npx tsc --noEmit` clean for both `server/` and `client/`. **Verified live**: switched to year view, confirmed `GET /api/preferences/calendar-granularity` returned `{"calendarGranularity":"year"}` via direct `curl`, forced a genuine `location.reload()` and confirmed the page came back straight into year view (not month); repeated switching back to month view and reloading again to confirm both directions. Incidental cleanup, same as both prior follow-ups: two more stray `vite`/`tsx watch` processes from an earlier turn were found still bound to ports 5173/4174 and stopped before starting this turn's dev server — confirmed via `cmdline` that they were this project's own dev processes before killing.
