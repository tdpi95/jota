# Milestone 13 & 14 notes

[← back to PROGRESS.md](../../PROGRESS.md)

- Built together in one pass — Dashboard (14) is the first consumer of `GET /api/tasks/open` on the client, and `CalendarSidebar` (13) needed a home in `AppShell` that both pages now sit under, so splitting the write-up doesn't reflect how the work split either.
- **`CalendarSidebar`** (`client/src/components/CalendarSidebar.tsx`), rendered inside `AppShell`'s `<aside>` below the nav (`margin-top: auto` pins it to the bottom, matching `design/Main.dc.html`): a month grid backed by `GET /api/calendar/:year/:month` (`api.getCalendarMonth`, new in `api/client.ts`; `CalendarDay`/`CalendarTaskMark` types added to `client/src/types.ts` mirroring `lib/index/queries.ts`'s server-side shapes). The viewed month is the component's own local state (defaults to the current month) — deliberately independent of whatever page is routed to, so paging the calendar forward/back never fights with journal day navigation. The *selected* day (highlighted via `.cal-day.selected`) isn't tracked as separate state at all — it's read back out of the current route with `react-router-dom`'s `matchPath('/journal/:year/:date', location.pathname)`, so it can never drift out of sync with whatever journal day is actually open; today (`.cal-day.today`) is computed once from `todayStr()`. Each day cell dedupes task marks by project color (a project with multiple due/linked tasks the same day still shows one dot per distinct color) and caps at 3 dots, matching the design mockup. Clicking any real day navigates to `/journal/:year/:date` (auto-creates nothing — same as any other journal day visit, per milestone 8's "GET auto-defaults" behavior).
- **Dashboard v2** (`client/src/pages/DashboardPage.tsx`), replacing milestone 11/12's placeholder: `GET /api/tasks/open` (`api.getOpenTasks`, new) bucketed client-side into Today/Overdue/This-week using a new `daysBetween` helper in `lib/date.ts` (local-calendar-day diff, same convention as the file's existing `addDays`/`formatDateLong` — not a UTC `Date` parse, which would be an off-by-one trap across timezones). Bucketing logic is transcribed directly from `design/Main.dc.html`'s own dashboard view-model code: overdue (`diff < 0`, hidden entirely when empty), today (`diff === 0`), this week (`0 < diff <= 7`); undated tasks and anything due further out are deliberately excluded from the dashboard (still visible in each project's own Todo column) — not a milestone-14 omission, the design this was built from does the same thing on purpose.
- **`TaskRow` gained an optional `project` prop** (`{name, color}`) rendering the `.project-badge` (name + color dot) design already has CSS for — shown first in the meta row, before the due badge. Omitted (as before) on `ProjectDetailPage`'s own task columns, where every row is already known to belong to the one open project and the badge would be redundant; Dashboard is the first caller to pass it, since it spans every project at once. A small `toTask()` adapter in `DashboardPage.tsx` maps `IndexedTask` (the aggregate-query shape, with `projectSlug`/`projectName`/`projectColor`/`createdAt` joined in) to the plain `Task` shape `TaskRow`/`TaskForm` render — the only field that doesn't line up by name is `createdAt` vs `created`, and neither component reads that field directly, so this is a pure type-shape adapter, not a behavior difference.
- Dashboard's status-cycle/save/delete/log-to-today mutations call the exact same `api.updateTask`/`api.deleteTask`/`api.linkTaskToJournal` functions `ProjectDetailPage` already uses (keyed off each `IndexedTask`'s own `projectSlug` rather than a single page-wide slug) — no new backend surface, no duplicated request logic.
- **Calendar-cache invalidation wired from every mutation that can move one of its dots**, not just Dashboard's own: `ProjectDetailPage`'s task create/update/delete/log-today, and `JournalDayPage`'s autosave (a body going empty↔non-empty flips the journal dot) and link/unlink (flips a 'linked' task dot), all now also `invalidateQueries({queryKey: ['calendar']})` (a prefix match invalidates every viewed month, not just the current one — cheap, since it's just a refetch of whatever month is actually mounted). Without this the sidebar — a single long-lived component that never remounts across route changes, unlike the pages that mutate it — would only pick up a change on its own next `staleTime` expiry rather than immediately, which felt wrong for something meant to double as at-a-glance navigation.
- **Verified live**, not just typechecked/built (`npx tsc --noEmit` and `npm run build -w client` both clean): seeded a scratch workspace with two projects, five tasks (spanning overdue/today/this-week/next-month/undated due dates) and a journal entry, through the real running server + Vite dev server in an actual browser. Confirmed the calendar showed the right dot colors and reasons on the right days (cross-checked against `GET /api/calendar/2026/09` directly — a due-task dot, a journal-entry dot, and a day carrying both a due dot and a linked dot on the same date all rendered correctly, deduped/capped as designed); clicking a day navigated to that journal date and correctly showed it as `.selected` while `.today` stayed on the actual current date; month prev/next paged correctly including into a different month's own leading-blank-cell count. On the Dashboard, confirmed the three buckets matched the seeded due dates exactly, project badges showed the right name/color per task, cycling a task's status todo→doing persisted `@doingSince` to the actual file (cross-checked via curl) and its `TimeSpentBadge` began live-ticking, editing a task inline through `TaskForm` saved the new tag to the file, and "+ log to today" linked the task into that day's journal file — all reflected in `git log` as the expected `[api] ...` commits, same tagging convention as every other milestone.
