# Milestone 9 notes

[← back to PROGRESS.md](../../PROGRESS.md)

- `server/src/lib/index/queries.ts` — every read-only aggregate query lives here (alongside `db.ts`'s schema and `reindex.ts`'s writes, keeping all direct `node:sqlite` access confined to `lib/index/*.ts` per PLAN.md): `queryOpenTasks`, `querySearchTasks`, `queryTaskById`, `queryJournalLinksForTask`, `queryCalendarMonth`, `queryAllTasksForReport`. Each opens and closes its own `DatabaseSync` connection (same pattern as `reindex.ts`'s `getIndexStatus`) rather than threading a connection through — these are infrequent, cheap reads on a personal-vault-sized index, not a hot path worth pooling.
- `db.prepare(...).all()` is typed `Record<string, SQLOutputValue>[]` by `node:sqlite`'s `.d.ts`; casting that straight to a many-field row interface trips TS's "insufficient overlap" heuristic (existing single/two-field casts in `reindex.ts` stay under whatever threshold that heuristic uses). Fixed with the double cast TS itself suggests, `as unknown as TaskJoinRow[]` — not a real type hole, `node:sqlite` just doesn't type `.all()`'s columns any more precisely than that.
- `queryOpenTasks`/`querySearchTasks`/`queryTaskById` all join `tasks` to `projects` so the response carries `projectName`/`projectColor` inline — the dashboard/search UI (milestones 11/14) needs those for badges and shouldn't have to issue a second request per task.
- `queryCalendarMonth` returns a **sparse** list (only dates with an actual mark), not a full month grid — the frontend `CalendarSidebar` already knows which dates exist in a month and just looks up marks by date. A day is marked `hasJournalEntry` only if `has_body = 1` (an empty-but-existing journal file doesn't count, consistent with the daily-reminder's own "still empty" check) — the `BETWEEN <year>-<month>-01 AND <year>-<month>-31` range is a plain string comparison and stays correct even for months with fewer than 31 days, since no real date ever sorts past its own month's last real day. A task that's both due *and* linked on the same date is recorded once (as `'due'`), not twice.
- `services/reports.ts`'s `getTimeSpentReport` does the date filtering, grouping, and live-elapsed-time math in JS over `queryAllTasksForReport`'s full result rather than in SQL — the file format only ever stores one cumulative `@spent` total per task (PLAN.md "Time tracking ... no separate start/stop control"), so there's no per-session log to group by day in the database; each task is instead attributed to one "relevant date" (`doneAt` if finished, else `due`, else the creation date) and a personal vault's task count is small enough that doing this in JS isn't a real cost. `includeInProgress` adds a currently-`doing` task's live elapsed time on top of its stored `spentMinutes`, mirroring the frontend's own future live-ticking `TimeSpentBadge` math (milestone 11) — this is why the report needed its own test proving both directions (present without the flag once a task is done, missing until `includeInProgress` is set while it's still open).
- New routes: `server/src/routes/taskQueries.ts` (`GET /api/tasks/open`, `GET /api/tasks/search?q=`, `GET /api/tasks/:taskId/journal-links`, mounted at `/api/tasks`) is a **separate file** from `routes/tasks.ts` (mounted at `/api/projects/:slug/tasks` for CRUD) purely to keep the two path prefixes from colliding — both call into the same `services/tasks.ts`. Also `server/src/routes/calendar.ts` (`/api/calendar`) and `server/src/routes/reports.ts` (`/api/reports`).
