# Milestone 26 notes (Project groups)

[← back to PROGRESS.md](../../PROGRESS.md)

- New feature requested directly by the user: "organize projects into groups. each project is in a group, if user don't select it's in default group. all tasks inherit their project's group. add filter by groups in dashboard. no need tags for project any more." Not previously in PLAN.md, so per CLAUDE.md's working conventions, read PLAN.md/PROGRESS.md in full first, then used `AskUserQuestion` to settle two design forks before writing any code: (1) how a group is picked — a free-text combobox (suggesting existing group names, typing a new one just as easy) vs. a separately-managed list of groups with its own CRUD surface; the user chose free-text. (2) whether `/projects` itself should change beyond a bare filter, now that project tags are gone — a flat list with a filter swapped in, or group-sectioned *and* filtered; the user chose sectioned + filtered.
- Before writing any code, grepped the whole tree for every project-tags touchpoint (`ProjectFrontmatter.tags`, the index's `projects`/`projects_fts` tables, routes, the MCP `create_project`/`update_project` tools, and every client component/page rendering or editing them) to scope the change precisely — task `#tag`s (a completely separate grammar/feature) and note/journal tags were confirmed untouched throughout.

## Storage + backend

- **Frontmatter**: `ProjectFrontmatter.tags: string[]` is removed outright (not kept alongside `group`) and replaced with `group: string`. `lib/markdown/project.ts`'s `parseProjectFile` normalizes `data.group = data.group?.trim() || DEFAULT_GROUP` right after parsing — this is the one place that has to run for every reader (REST routes, MCP tools, the index reconciler) to agree, so a hand-edited/pre-migration file with no `group` field at all gets exactly the same "Default" fallback as a form submitted blank. `DEFAULT_GROUP = 'Default'` is exported from `project.ts` and re-exported from `services/projects.ts` for callers.
- **Service layer**: `createProject`/`updateProject`'s `CreateProjectInput`/`UpdateProjectInput` swap `tags?: string[]` for `group?: string`; `updateProject`'s "undefined leaves it alone" convention stays, but an *explicitly blank* group (e.g. `"  "`) resets to `DEFAULT_GROUP` rather than being stored as empty — the one field-level exception to "blank is a legitimate value," because an empty group would be indistinguishable from "no group" everywhere it's read.
- **Tasks inherit group, not stored on the task**: deliberately no `group` field was added to `Task`/the task-line grammar — a task's group is purely `t.projectGroup`, joined in at query time from `lib/index/queries.ts`'s shared `TASK_JOIN_SELECT` (`p.group_name AS project_group`). Every aggregate built on that one shared SQL fragment (`queryOpenTasks`, `querySearchTasks`, `queryTaskById`, `queryAllTasksForReport`, and the cross-type search's task branch) picked up `projectGroup` for free from one change, instead of needing it threaded through five separate queries.
- **Index migration** (`lib/index/db.ts`) follows this file's already-established shape exactly (the same one `checklist`/journal+note `body`/`projects_fts` each used): `projects.group_name TEXT NOT NULL DEFAULT 'Default'` is added to the `CREATE TABLE` for fresh workspaces, plus an idempotent `ALTER TABLE projects ADD COLUMN group_name ...` wrapped in try/catch for an existing index, immediately followed by `UPDATE projects SET source_mtime = 0` so `reconcileWorkspace` sees every existing (even totally unchanged) project as needing a reparse and backfills its real group straight from frontmatter on the next reconcile. Verified directly (`reindex.test.ts`) by hand-constructing a pre-migration `projects` table (no `group_name` column, matching the exact old schema) at the file's *current* mtime — the same "unchanged file still needs a one-time backfill" scenario the `projects_fts` migration test already covered — and confirming both migrations complete correctly from one `openIndexDb` call.
- **The now-pointless `tags` columns are kept, not dropped**: `projects.tags` and `projects_fts.tags` still exist physically (always written `'[]'`/`''` respectively) rather than attempting `ALTER TABLE ... DROP COLUMN` — SQLite added `DROP COLUMN` support in 3.35, and the `node:sqlite` build behind this isn't something this codebase pins/asserts a version for elsewhere, so risking a migration failure on an obscure older build for a purely cosmetic cleanup wasn't worth it. This is a derived, always-rebuildable cache (PLAN.md's own framing) — an inert column costs nothing. `group` was deliberately **not** added to `projects_fts` (no full-text search over group names) since group filtering is an exact-match dropdown/pill selection, not a text query.
- **Routes**: `routes/projects.ts`'s `POST`/`PATCH` handlers destructure `group` in place of `tags` and forward it unchanged — no new validation beyond what the service layer already does.
- **MCP tools**: `create_project`/`update_project` swap their `tags` input for `group` (both optional, same blank-resets-to-Default framing documented in the tool descriptions so an agent doesn't have to guess); `list_projects`/`get_project` needed no changes since they already return the full frontmatter object.

## Frontend

- **`ProjectForm.tsx`**: the `TagInput` field is replaced with a single free-text `<input list={id}>` + `<datalist>` combobox, taking a new `existingGroups: string[]` prop (every group already in use). A native datalist rather than a custom picker — the browser already provides "suggest but allow anything," exactly the free-text-combobox behavior the user asked for, with zero new component code.
- **`ProjectsListPage.tsx`**: `allGroups` derives from the already-loaded `GET /api/projects` response (no new endpoint needed — the full project list, group included, is already fetched here and on the Dashboard). The old tag-pill filter is replaced by a group-pill filter (identical multi-select/OR-matched/"Clear" `.tag-filter-row`/`.tag-pill-filter` CSS — reused verbatim, no new classes needed for the pills themselves), shown only when more than one group exists. The visible (post-archived-and-group-filter) projects are then bucketed by group into a `Map`, rendered as one `.projects-group-section` per group (alphabetical), each with a heading and its own `.projects-list` — new CSS for just the section/heading wrapper.
- **`ProjectDetailPage.tsx`**: fetches `GET /api/projects` a second time (same `['projects']` query key every other page already uses, so it's cache-warm rather than a fresh network round trip whenever `/projects` was visited first in the session) purely to build `existingGroups` for the edit form's combobox, since this page's own query only has the one project being edited. The old `.pd-tags` tag-pill row under the title is replaced by a single `.pd-group` pill showing the project's one group.
- **`ProjectCard.tsx`**: the tag-pill row is removed outright, with nothing added in its place — grouping is now structural (a section heading on `/projects`), not a per-card badge; the Dashboard's "Recent projects" grid variant never showed a group either, for the same reason.
- **`DashboardPage.tsx`**: a second, independent filter — `groupFilters`/`toggleGroupFilter`/`allBucketGroups` (derived from every open task's `projectGroup`, same "stays derived from the full set, not the filtered set" reasoning the existing tag filter already used) — rendered as its own pill row above the pre-existing tag filter row. The two filters stack: `bucketTasks` is the tag-filtered set further filtered by group (AND between the two dimensions, OR within each one's own selections, matching how a second independent facet is expected to combine with the first). Hidden when every open task shares one group.
- **i18n**: `projectForm.tagsLabel` → `projectForm.groupLabel` + a new `projectForm.groupPlaceholder` ("Default"/"Mặc định"), both `en.json`/`vi.json`; every other filter/section label reuses existing generic strings (`projectsList.clear`, `dashboard.clear`) since "Clear" reads correctly regardless of which filter row it's attached to. Confirmed structurally identical afterward (270 leaf keys each).

## Follow-up: distinguishing the Dashboard's two filter rows ("distinct group and tag filter in dashboard")

- The user's real "Everything" workspace initially showed no group filter at all — traced (via a read-only `GET /api/projects` against their live server, disclosed to the user) to their Electron-spawned server process still running the pre-milestone-26 code (`tsx src/index.ts`, no watch mode, so it never picked up the session's edits without a full app restart). A second symptom followed: after quitting and relaunching, Electron's own server failed with `EADDRINUSE` on port 4174 — an orphaned bare `tsx src/index.ts` process from an *unrelated* earlier session restart (found via `ps`, logging to a different session's scratchpad path) was still squatting the port. Killed that orphan; the user's own relaunch then bound cleanly.
- Once the group field actually reached the client, the real ask surfaced: the Dashboard's group filter and its pre-existing task-tag filter both rendered as plain `.tag-pill-filter` pill rows with no distinguishing feature, stacked back-to-back — genuinely ambiguous which pill belonged to which filter dimension.
- Fix, Dashboard-only (`/projects`' group filter has no sibling tag filter to disambiguate from, so it was left untouched): each filter row now opens with a small uppercase `.filter-facet-label` — an inline icon (Feather-style `folder` for Group, `tag` for Tags, matching this app's existing thin-stroke icon convention) plus the facet name (`dashboard.filterByGroup`/`filterByTag`, both languages). Group pills additionally get a `.group-pill-filter` shape override (`border-radius: 6px`, a rounded-rectangle "chip") instead of the fully-rounded pill every tag pill and every other filter pill in the app uses — a second, shape-based cue layered on top of the label. Deliberately did **not** reach for a second color (e.g. a distinct hue for group pills' active state): PLAN.md's "Theming" section already treats every non-neutral color as a token tied to `--accent-hue`, and introducing an arbitrary second hue just for this one row would be exactly the kind of hardcoded-literal regression that section warns against — label + shape gets the same "obviously two different things" result without it.
- Verified live (same isolated scratch server/workspace pattern, seeded with one project each in "Work"/"Personal" and matching tasks with `content`/`urgent` tags): the Dashboard now shows a "GROUP" row (folder icon, squared chips: Personal/Work) directly above a "TAGS" row (tag icon, fully-rounded pills: content/urgent) — visually distinct at a glance; clicking a group chip still filters correctly (active state + "Clear" appear); zero console errors. `npm test -w server` still 154/154, `npx tsc --noEmit` and `npm run build -w client` both clean, `en.json`/`vi.json` re-confirmed structurally identical (272 leaf keys each, up from 270).

## Follow-up: "Due today" header + persisted group filter ("replace header 'today' by 'due today'. remember group filter")

- **Header rename**: `dashboard.buckets.today` ("Today" → "Due today" / "Hôm nay" → "Đến hạn hôm nay") — the bare "Today" read ambiguously once a Group/Tags filter row sat directly above it; "Due today" matches what the bucket actually filters on (each task's `due` date, not when it was touched).
- **Persisted group filter**: the Dashboard's group-filter selection (not the tag filter — the user asked for the group one specifically, and the two are independent, separately-scoped dimensions) now survives an app restart, following the exact `~/.jota/config.json` app-wide-preference shape every other Dashboard/Calendar toggle in this codebase already uses (`dashboardRecentProjectsOpen`, `calendarMode`, etc.): a new `dashboardGroupFilter?: string[]` field on `WorkspaceRegistry` (`lib/workspaces.ts`), `get/setDashboardGroupFilterPreference` (`services/workspaces.ts`, `undefined` → `[]`), `GET/PUT /api/preferences/dashboard-group-filter` (`routes/preferences.ts`), and matching `client/src/api/client.ts` functions. `DashboardPage.tsx` fetches it once on mount (`['dashboardGroupFilterPreference']` query, applied via the same fetch-once-then-apply `useEffect` pattern `recentProjectsOpen` already uses) and persists on every toggle/clear via a `useMutation`.
- **Stale-entry self-healing**: unlike a plain boolean, a persisted group *name* can go stale — its project renamed/regrouped/deleted since, or simply a leftover from a different workspace (the preference is app-wide, not per-workspace, same as every sibling preference). Filtering tasks by a stale group name directly would match zero tasks and silently blank every bucket, with the filter row itself possibly hidden too (`allBucketGroups.length <= 1`) — no visible pill, no visible "Clear," seemingly broken. Fixed by computing `activeGroupFilters = groupFilters.filter(g => allBucketGroups.includes(g))` and using that (not the raw persisted `groupFilters`) for both the bucket filtering and the "Clear" button's visibility — a stale entry silently has no effect rather than a mysteriously empty dashboard. The raw stored value isn't proactively pruned (harmless dead weight, self-heals the moment its group is valid again, e.g. after switching back to the workspace it came from).
- Verified live (same isolated scratch server/workspace pattern, spare ports 4275/5273): "Due today" renders as the bucket header; clicking the "Personal" group pill narrows the bucket from 2 tasks to 1 and a `GET /api/preferences/dashboard-group-filter` immediately afterward confirms `{"groups":["Personal"]}` server-side; a full page reload re-applies the filter automatically (still narrowed to 1, "Personal" still shown active) with no explicit action needed; clicking "Clear" removes it and a follow-up `GET` confirms `{"groups":[]}`; zero console errors throughout. `npm test -w server` 155/155 (up from 154 — one new `services/workspaces.test.ts` case for the new preference's default/persist round trip), `npx tsc --noEmit` and `npm run build -w client` both clean.
