# Milestone 24 notes (Notes)

[← back to PROGRESS.md](../../PROGRESS.md)

- New content type requested directly by the user: "Add notes feature. It's just a collection of md files with some meta: tag, create at, last modified." Not previously in PLAN.md, and CLAUDE.md's working conventions say a new feature/convention needs to be checked with the user before building, so before writing any code this session read PLAN.md/PROGRESS.md in full (per CLAUDE.md's own "before doing anything else" instruction) and then used `AskUserQuestion` to settle three design questions that would otherwise have been guesses: file layout (flat `notes/<slug>.md` vs. an id-based filename vs. year-bucketed like journal), whether notes get SQLite-indexed for a fast list/search aggregate, and whether MCP tools ship in the same pass as the REST API/UI. The user chose flat + slug filenames, indexed, and full MCP parity from the start — all three matching the closest existing precedent (projects for slug-filenames, tasks/journal for indexing, every other content type for MCP parity) rather than introducing a new pattern.
- Before writing any note-specific code, read every file it would need to mirror closely: `lib/markdown/{journal,project,frontmatter}.ts`, `services/{journal,projects}.ts`, `lib/index/{db,reindex,queries}.ts`, `routes/{projects,journal}.ts`, `mcp/tools.ts`, `lib/{slug,didYouMean,httpError,vaultGit,workspaces}.ts`, and on the client `App.tsx`, `AppShell.tsx`, `api/client.ts`, `pages/{JournalDayPage,ProjectsListPage}.tsx`, `types.ts`, `components/{TagInput,HistoryPanel,Modal,ProjectForm,ProjectCard,MarkdownEditor}.tsx`, and both `i18n/{en,vi}.json`'s existing key shapes. Notes ended up closest to journal entries (freeform body, no per-line grammar) for the file/service/index treatment, and closest to projects (a flat directory of one-file-per-item, a stable slug assigned at creation) for the filename/routing treatment.

## Storage + backend

- **Frontmatter**: `{title, created, updated, tags}` — `created`/`updated` are full ISO8601 UTC timestamps (not bare dates, unlike every other frontmatter date field in this app so far), `created` set once, `updated` rewritten on every write. `lib/markdown/note.ts` is a near-exact copy of `journal.ts`'s shape (`parseNoteFile`/`serializeNoteFile`, thin wrappers over `parseFrontmatter`/`serializeFrontmatter`).
- **Slug**: `services/notes.ts`'s `uniqueSlug` slugifies the title (reusing `lib/slug.ts`, same as projects) and, on collision, appends `-2`/`-3`/... rather than rejecting — deliberately different from `createProject`'s "duplicate slug" 409, since a note's title ("Meeting notes", "Ideas") is far more likely to be reused verbatim than a project's, and the slug is filename-only, never shown as the note's displayed identity. The slug never changes once assigned, even when `updateNote` changes the title — verified explicitly in both `services/notes.test.ts` and the MCP tool test (retitle, then confirm the same file path still exists).
- **Index**: a new `notes` table (`slug, title, created, updated, tags, source_mtime, source_hash`) in `lib/index/db.ts`'s schema, reconciled by a new `reconcileNotes` in `reindex.ts` — structurally identical to `reconcileJournal` (a plain upsert-or-delete stat-diff, no join table to also maintain, unlike projects' tasks). **The index never caches note body text** — same rule journal entries already established (per PLAN.md's `listJournalYearFull` reasoning) — so `lib/index/queries.ts`'s new `queryAllNotes`/`querySearchNotes` return metadata only; only `getNote`/`loadNoteFile` (direct file reads) ever see the body. This does mean note search is title/tags-only, not full-text — an accepted limitation, not an oversight, matching the existing journal precedent.
- **A latent frontmatter bug this surfaced**: `lib/markdown/frontmatter.ts`'s `normalizeYamlDates` (written in milestone 4 for bare `YYYY-MM-DD` project/journal date fields) coerces any js-yaml-parsed `Date` back to a string — but it unconditionally sliced to `YYYY-MM-DD`, which would have silently dropped the time-of-day from a hand-edited, unquoted `NoteFrontmatter.created`/`updated` (e.g. `created: 2026-09-14T09:15:00.000Z` typed without quotes triggers the exact same YAML 1.1 timestamp auto-coercion as a bare date). Fixed by only slicing when the coerced `Date` lands exactly on UTC midnight (the only value a bare-date field could ever actually produce) — anything else keeps the full ISO string. Confirmed app-written files were never at risk either way: gray-matter/js-yaml already auto-quotes a string that would otherwise round-trip as a `Date` on reparse (visible in the pre-existing `journal-sample.md`/`project-sample.md` fixtures, both of which quote their date fields) — generated the `note-sample.md` fixture's exact byte content via a throwaway `gray-matter` script rather than hand-guessing the quoting style, then used it for both a round-trip test and a frontmatter-parsing test. Two new regression cases added directly to `frontmatter.test.ts` (full timestamp preserved; exact-midnight still normalizes to a bare date).
- **Routes**: `GET /api/notes` (list, or `?q=` to search — one route for both since they return the identical `IndexedNote[]` shape, unlike tasks' separate `/open` and `/search`), `POST /api/notes`, `GET/PATCH/DELETE /api/notes/:slug`. `PATCH` follows `updateProject`'s exact convention (`undefined` = leave alone, always write+bump `updated` when called at all — no attempt to detect a true no-op, matching `updateProject`'s own simplicity over `linkTask`'s idempotent-no-op style).
- **MCP tools**: `create_note`, `update_note`, `delete_note`, `get_note`, `list_notes` (optional `query` does the same title/tag search as the REST route's `?q=`) — full read+write parity from the start, per the user's own answer to the scoping question.
- **Workspace scaffolding**: `scaffoldWorkspaceDirs` now also creates `notes/` alongside `projects/`/`journal/`, so a workspace opened before this milestone self-heals the same way it already does for a missing `.poco/`.

## Frontend

- **`/notes`** (`NotesListPage.tsx`): most-recently-updated-first list, client-side title-substring + tag-pill filtering over the full loaded set — deliberately not round-tripping to the server's `?q=` for the UI, mirroring `ProjectsListPage`'s own reasoning that a personal collection this size doesn't need server-side filtering. "+ New note" skips a create-form popup entirely: it calls `createNote({title: 'Untitled note'})` and navigates straight to the new note's edit page, where the title is just another autosaving field — friction a form would only add for something this disposable to start (the equivalent of Projects' `Modal`+`ProjectForm` flow was considered and rejected for this reason).
- **`/notes/:slug`** (`NoteDetailPage.tsx`): title (a plain inline `<input>`, not a static heading — unlike `JournalDayPage`'s date), tags (`TagInput`), and body (`MarkdownEditor`) all autosave-debounced *together* through one `scheduleSave`, reusing `JournalDayPage`'s exact pattern: the shared `autosaveIntervalPreference`, a `dirtyRef` set only by explicit onChange handlers (never inferred by diffing against loaded data — `JournalDayPage`'s own comment documents why that diffing approach has a real race between the load-sync effect and the debounce-scheduling effect), and a flush-on-unmount effect for navigate-away. Added one narrow guard `JournalDayPage` didn't need: the unmount-flush never sends a blank title (an empty note title has no journal-entry equivalent to compare against, and a blank frontmatter title would look broken in the notes list). A delete button (confirm dialog, same `window.confirm` pattern as `HistoryPanel`'s own undo confirmation) navigates back to `/notes` on success. Reused `HistoryPanel` and `.journal-tags`/`.journal-body`/`.journal-save-status` CSS as-is — a note's body editor is visually identical to a journal entry's.
- **Nav**: a new "Notes" item in `AppShell` between Projects and Journal, with a new document-style icon.
- **i18n**: new `notesList`/`noteDetail` namespaces plus one new `appShell.nav.notes` key, in both `en.json` and `vi.json` — confirmed structurally identical afterward (254 leaf keys each, up from 226).
- **CSS**: `.notes-list`/`.note-row`/`.note-row-main`/`.note-title`/`.note-updated` (a trimmed-down copy of `.projects-list`/`.project-row` — no color tab, a last-updated timestamp instead of status counts), `.note-detail-head`/`.note-title-input` (the inline-editable title), `.notes-search-input`.

## Follow-up: Edit/Preview toggle for the note body ("add md preview for note body")

- A short follow-up request, but one that overlapped a settled decision: PLAN.md's "Journal editor" section already has the user's explicit answer to almost this exact question for the journal body ("add markdown preview... similar to Obsidian" → syntax-coloring only, no rendered/hide-the-marks view, after a clarifying question) — and `NoteDetailPage` already inherits that exact syntax coloring via the shared `MarkdownEditor`. Rather than assume "preview" meant something new versus already-satisfied, or silently reopen the journal decision, used `AskUserQuestion` again: edit↔preview toggle vs. an always-visible split view vs. "no, the existing coloring is what I meant." The user picked the toggle.
- **Rendering**: added `markdown-it` (`^15.0.2`) as a new client dependency — the first actual markdown-to-HTML renderer in this app (`MarkdownEditor` deliberately never renders, only colors). `client/src/lib/renderMarkdown.ts` wraps a single shared `MarkdownIt` instance configured `{ html: false, linkify: true, breaks: false }`. `html: false` is the load-bearing security choice, not just the default left unstated: `NoteDetailPage` feeds the render straight into `dangerouslySetInnerHTML`, and per PLAN.md's own "Agent access via MCP" a note body is genuinely untrusted-ish input (an MCP agent has full write access; an external sync tool could also drop arbitrary content into the file) — with `html: false`, any raw HTML in the source (a literal `<script>...</script>`, say) is escaped to inert text rather than parsed into real DOM nodes, so no separate sanitizer (DOMPurify etc.) was needed. Confirmed directly, not just assumed: rendered a body containing `<script>alert(1)</script>` and read back both the produced `innerHTML` (`&lt;script&gt;...`) and `document.scripts.length` in a real browser — no script node was created.
- **UI**: `NoteDetailPage.tsx` gained a `viewMode: 'edit' | 'preview'` toggle, reusing `CalendarPage`'s exact `.ws-row-btn`/`.is-active` segmented-control pattern (`role="radiogroup"`) rather than inventing a new toggle style. Preview renders off the current in-memory `body` state, not the last-saved value, so switching to Preview mid-edit (before the autosave debounce has fired) still reflects what was just typed. An empty body shows a distinct `t('noteDetail.previewEmpty')` message rather than a blank box. Title and tags stay editable in both modes — the toggle only affects the body.
- **Styling**: `.note-preview` in `app.css` reuses the same `--md-heading`/`--md-link`/`--md-quote`/`--md-code`/`--md-code-bg` custom properties `MarkdownEditor`'s `HighlightStyle` already uses, so headings/links/quotes/code read as the same colors switching between Edit and Preview, in both light and dark theme. One real bug found and fixed during verification: the preview `<div>` shares `.journal-body` for its box chrome (border/background/min-height), and the new typography rule was originally written as a bare `.note-preview { font-family: 'Newsreader', ...; }` — a single-class selector with the *same* specificity as `.journal-body`'s own `font-family: 'JetBrains Mono', ...`, so which one won depended entirely on source order (in this case, `.journal-body`'s later position in the file won, silently leaving Preview rendered in the monospace editor font instead of a reading-serif one). Fixed by combining both classes into one compound selector (`.journal-body.note-preview`), which has higher specificity than either alone and wins regardless of where either rule sits in the file — found by literally reading `getComputedStyle(...).fontFamily` in the browser rather than trusting the CSS as written, not by eyeballing a screenshot.
- **i18n**: new `noteDetail.viewMode.{sectionTitle,edit,preview}` and `noteDetail.previewEmpty` keys, both languages (260 leaf keys each afterward, up from 254).
- **Verified**: `npx tsc --noEmit` (client) clean, `npm run build -w client` clean; a throwaway `markdown-it` script confirmed the exact rendering/escaping behavior for headings/bold/italic/strikethrough/links/autolinks/lists/blockquotes/fenced-code/inline-code and the `<script>` case before wiring it into the page at all. **Verified live** in a real browser via the Browser pane, against the same kind of disposable scratch server+workspace this milestone's initial pass used (a fresh scratch `$HOME`/workspace/port, plus a throwaway, gitignored-by-never-being-tracked `client/vite.config.scratch.ts` pointed at that scratch backend on its own port 5199 — deleted immediately after, confirmed absent from `git status` — specifically so this didn't collide with the user's own already-running dev session on the normal 5173/4174 ports): the Edit↔Preview toggle switches correctly, a note with a heading/bold/link/list/blockquote/fenced-code-block renders each element with the right token color in both light and dark theme (theme switched via `PUT /api/preferences/theme` against the scratch server, not the user's own), an empty note shows the empty-state message, and the `<script>` case renders as literal escaped text with no script execution and no new `<script>` DOM node. All 130 server tests unaffected (client-only change) and re-confirmed passing.
