# Milestone 24 notes (Notes)

- New content type requested directly by the user: "Add notes feature. It's just a collection of md files with some meta: tag, create at, last modified." Not previously in PLAN.md, and CLAUDE.md's working conventions say a new feature/convention needs to be checked with the user before building, so before writing any code this session read PLAN.md/PROGRESS.md in full (per CLAUDE.md's own "before doing anything else" instruction) and then used `AskUserQuestion` to settle three design questions that would otherwise have been guesses: file layout (flat `notes/<slug>.md` vs. an id-based filename vs. year-bucketed like journal), whether notes get SQLite-indexed for a fast list/search aggregate, and whether MCP tools ship in the same pass as the REST API/UI. The user chose flat + slug filenames, indexed, and full MCP parity from the start — all three matching the closest existing precedent (projects for slug-filenames, tasks/journal for indexing, every other content type for MCP parity) rather than introducing a new pattern.
- Before writing any note-specific code, read every file it would need to mirror closely: `lib/markdown/{journal,project,frontmatter}.ts`, `services/{journal,projects}.ts`, `lib/index/{db,reindex,queries}.ts`, `routes/{projects,journal}.ts`, `mcp/tools.ts`, `lib/{slug,didYouMean,httpError,vaultGit,workspaces}.ts`, and on the client `App.tsx`, `AppShell.tsx`, `api/client.ts`, `pages/{JournalDayPage,ProjectsListPage}.tsx`, `types.ts`, `components/{TagInput,HistoryPanel,Modal,ProjectForm,ProjectCard,MarkdownEditor}.tsx`, and both `i18n/{en,vi}.json`'s existing key shapes. Notes ended up closest to journal entries (freeform body, no per-line grammar) for the file/service/index treatment, and closest to projects (a flat directory of one-file-per-item, a stable slug assigned at creation) for the filename/routing treatment.

## Storage + backend

- **Frontmatter**: `{title, created, updated, tags}` — `created`/`updated` are full ISO8601 UTC timestamps (not bare dates, unlike every other frontmatter date field in this app so far), `created` set once, `updated` rewritten on every write. `lib/markdown/note.ts` is a near-exact copy of `journal.ts`'s shape (`parseNoteFile`/`serializeNoteFile`, thin wrappers over `parseFrontmatter`/`serializeFrontmatter`).
- **Slug**: `services/notes.ts`'s `uniqueSlug` slugifies the title (reusing `lib/slug.ts`, same as projects) and, on collision, appends `-2`/`-3`/... rather than rejecting — deliberately different from `createProject`'s "duplicate slug" 409, since a note's title ("Meeting notes", "Ideas") is far more likely to be reused verbatim than a project's, and the slug is filename-only, never shown as the note's displayed identity. The slug never changes once assigned, even when `updateNote` changes the title — verified explicitly in both `services/notes.test.ts` and the MCP tool test (retitle, then confirm the same file path still exists).
- **Index**: a new `notes` table (`slug, title, created, updated, tags, source_mtime, source_hash`) in `lib/index/db.ts`'s schema, reconciled by a new `reconcileNotes` in `reindex.ts` — structurally identical to `reconcileJournal` (a plain upsert-or-delete stat-diff, no join table to also maintain, unlike projects' tasks). **The index never caches note body text** — same rule journal entries already established (per PLAN.md's `listJournalYearFull` reasoning) — so `lib/index/queries.ts`'s new `queryAllNotes`/`querySearchNotes` return metadata only; only `getNote`/`loadNoteFile` (direct file reads) ever see the body. This does mean note search is title/tags-only, not full-text — an accepted limitation, not an oversight, matching the existing journal precedent.
- **A latent frontmatter bug this surfaced**: `lib/markdown/frontmatter.ts`'s `normalizeYamlDates` (written in milestone 4 for bare `YYYY-MM-DD` project/journal date fields) coerces any js-yaml-parsed `Date` back to a string — but it unconditionally sliced to `YYYY-MM-DD`, which would have silently dropped the time-of-day from a hand-edited, unquoted `NoteFrontmatter.created`/`updated` (e.g. `created: 2026-09-14T09:15:00.000Z` typed without quotes triggers the exact same YAML 1.1 timestamp auto-coercion as a bare date). Fixed by only slicing when the coerced `Date` lands exactly on UTC midnight (the only value a bare-date field could ever actually produce) — anything else keeps the full ISO string. Confirmed app-written files were never at risk either way: gray-matter/js-yaml already auto-quotes a string that would otherwise round-trip as a `Date` on reparse (visible in the pre-existing `journal-sample.md`/`project-sample.md` fixtures, both of which quote their date fields) — generated the `note-sample.md` fixture's exact byte content via a throwaway `gray-matter` script rather than hand-guessing the quoting style, then used it for both a round-trip test and a frontmatter-parsing test. Two new regression cases added directly to `frontmatter.test.ts` (full timestamp preserved; exact-midnight still normalizes to a bare date).
- **Routes**: `GET /api/notes` (list, or `?q=` to search — one route for both since they return the identical `IndexedNote[]` shape, unlike tasks' separate `/open` and `/search`), `POST /api/notes`, `GET/PATCH/DELETE /api/notes/:slug`. `PATCH` follows `updateProject`'s exact convention (`undefined` = leave alone, always write+bump `updated` when called at all — no attempt to detect a true no-op, matching `updateProject`'s own simplicity over `linkTask`'s idempotent-no-op style).
- **MCP tools**: `create_note`, `update_note`, `delete_note`, `get_note`, `list_notes` (optional `query` does the same title/tag search as the REST route's `?q=`) — full read+write parity from the start, per the user's own answer to the scoping question.
- **Workspace scaffolding**: `scaffoldWorkspaceDirs` now also creates `notes/` alongside `projects/`/`journal/`, so a workspace opened before this milestone self-heals the same way it already does for a missing `.poco/`.

## Frontend

"+ New note" skips a create-form popup entirely: it calls `createNote({title: 'Untitled note'})` and navigates straight to the new note's edit page, where the title is just another autosaving field — friction a form would only add for something this disposable to start (the equivalent of Projects' `Modal`+`ProjectForm` flow was considered and rejected for this reason).

Reused `HistoryPanel` and `.journal-tags`/`.journal-body`/`.journal-save-status` CSS as-is — a note's body editor is visually identical to a journal entry's.

## Follow-up: editable filename ("allow edit note file name. I don't want they always be untitled-note-x")

- The real gap this exposed: "+ New note" always creates `untitled-note`/`untitled-note-2`/... (PLAN.md's deliberate auto-suffix-on-collision), and the slug is otherwise fixed forever after creation (also deliberate — PLAN.md's "the slug is filename-only... and never changes even if the title is edited later") — so a note titled properly later stays stuck with an `untitled-note-3.md` filename with no way to fix it. This is a real, previously-unaddressed gap in the original design, not a request to reopen the "slug doesn't auto-follow title" decision itself (an automatic re-slugify-on-every-title-edit was considered and rejected while writing this up — it would fire a file rename on every autosave tick while retitling, silently breaking any external reference to the old path repeatedly rather than once).
- **Backend**: `UpdateNoteInput` gained an optional `newSlug` (`services/notes.ts`), sanitized through the same `slugify()` creation already uses. Deliberately **rejects a collision with a 409** rather than auto-suffixing like creation does — creation's target title is often an arbitrary default ("Untitled note"), so picking *some* unique slug for it is harmless, but a rename's target is a specific, deliberate choice the caller typed, so silently substituting something else would be a surprise, not a convenience. `saveNoteFile` was generalized to take both the old and target slug: when they differ, it writes the new file first, then removes the old one, and stages *both* relative paths in the same `commitChange` call — confirmed this reads as a rename in `git log` (`rename_note <old> -> <new>`) rather than an unrelated add+delete pair. `PATCH /api/notes/:slug` and the `update_note` MCP tool both forward `newSlug` straight through — full REST/MCP parity maintained, matching every other field on this route.
- **Frontend**: `NoteDetailPage` gained a small, muted, click-to-edit filename row (`notes/<slug>.md`, a pencil icon, `.note-slug-btn`/`.note-slug-input`) — deliberately *not* folded into the continuous title/tags/body autosave debounce, since a rename is a real file move and committing it on every keystroke (the way title/tags/body do) would be far more disruptive than a debounced content edit. It commits only on blur/Enter (Escape cancels and reverts the draft), and on commit it first cancels any pending autosave timer and folds its latest title/tags/body values into the *same* rename request (`renameMutation`) — otherwise a separately-scheduled autosave could fire moments later against the just-removed old slug and fail. On success, `navigate('/notes/<newSlug>', {replace: true})` — `NoteDetailPageInner` is keyed by the URL's slug, so this remounts the page fresh at the new URL exactly the way navigating between two different notes already does, with no manual local-state cleanup needed. On a conflict (409), the field reopens with the typed draft preserved and the server's own message shown inline (`err.message`, not a translated string — same convention `HistoryPanel`'s revert-failure display already uses for a server-originated error).
- **Tests**: seven new `services/notes.test.ts` cases (rename moves the file and commits `rename_note <old> -> <new>`; `newSlug` is sanitized through `slugify` the same as a title at creation; a rename combined with title/body changes in one call applies all of them; a `newSlug` that sanitizes back to the *current* slug is a harmless no-op rename that still applies other field changes; renaming onto an existing note's slug throws with "already exists" and leaves the original file untouched; a `newSlug` that sanitizes to nothing (e.g. `"!!!"`) is rejected). `mcp/tools.test.ts`'s combined note-tools test extended with a rename step (via `update_note`'s `newSlug`) and a rename-conflict step, threading the renamed slug through the rest of that test's list/search/get/delete steps.

## Follow-up: don't create a file until the first real edit ("don't create new note file before user edit anything")

- The actual gap: "+ New note" called `create_note` immediately on click (so the note existed, on disk and in git history, before the user had typed a single character), then navigated to its edit page — meaning opening the page and then just clicking away left an `untitled-note-N.md` file and a `[api] create_note ...` commit behind every time. Journal entries already avoid the equivalent problem (`getJournalEntry` returns an in-memory default and only ever writes on an actual `PUT`/link call) — this follow-up brings notes to the same standard.
- **New route, not a flag on the existing page**: `/notes/new` renders a new `NewNotePage.tsx` rather than teaching `NoteDetailPage` an "I might not exist yet" mode — the two pages diverge in almost everything (no fetch, no delete button, no filename-rename control, no `HistoryPanel`, a completely different persistence trigger) enough that a shared component with several conditional branches felt more tangled than two small pages. To avoid duplicating the Edit/Preview toggle + `MarkdownEditor`/rendered-preview block between them, that piece was pulled out into a new shared `components/NoteBodyEditor.tsx` (also re-exporting `VIEW_MODE_ICONS` so `NoteDetailPage`'s filename-rename pencil icon, unrelated to the toggle, still has a home for the same glyph) — `NoteDetailPage.tsx` shrank accordingly.
- **Creation trigger**: `NewNotePage` holds local `title`/`tags`/`body` state exactly like `NoteDetailPage`, but its first edit to any of the three starts a debounce (reusing the same `autosaveIntervalPreference`) that calls `createNote` — not `updateNote`, since there's no slug yet — when it fires. If the debounce fires with all three fields back to empty (typed something, then deleted it all before the delay elapsed), it resets to idle without calling the API at all, rather than creating a blank note. On success it navigates to `/notes/<newSlug>` — from that point on it's rendered by the ordinary `NoteDetailPage`, the same "hand off once a slug exists" pattern the filename-rename follow-up already established.
- **Reserved slug**: `/notes/new` is a literal route segment, which React Router ranks above the dynamic `/notes/:slug` regardless of declaration order — so if a note ever legitimately slugified to `new`, it would become permanently unreachable by direct URL (shadowed by the draft page), reachable only via the notes list. `services/notes.ts` now has a small `RESERVED_SLUGS` set (just `'new'` today) that `uniqueSlug` treats as always-taken (so a note titled "New" falls through to `new-2`, the same as an actual filename collision) and that the rename path (`newSlug`) also rejects explicitly (a distinct "is a reserved filename" 409, not the generic "already exists" one, since the latter would be a wrong reason — no such file actually exists).
- **Flush-on-navigate-away, same as everywhere else**: leaving `/notes/new` before the debounce fires still creates the note immediately if anything was actually typed (fire-and-forget, mirroring `NoteDetailPage`/`JournalDayPage`'s own unmount-flush) — a `submittedRef` guard prevents a second, redundant create from firing when the debounce's own success has already navigated away (which itself triggers this same unmount cleanup). Leaving with nothing typed at all creates nothing, which is the entire point.
- **Tests**: two new `services/notes.test.ts` cases for the reserved-slug guard (creation auto-suffixes "New" to `new-2`; renaming onto `new` is rejected as reserved, original file untouched). No new MCP/route tests were needed — `create_note`/`update_note` themselves are unchanged (the deferred-creation behavior lives entirely in the client), so the existing service-level coverage already exercises the one small addition (the reserved-word check) directly.
- **Verified**: `npm test -w server` — 138/138 passing (up from 136). `npx tsc --noEmit` (server/client) clean, `npm run build -w client` clean, `en.json`/`vi.json` structurally identical (264 leaf keys each). **Verified live** against a fresh disposable scratch server+workspace+Vite-config trio, with the workspace's `autosaveIntervalSeconds` preference temporarily lowered to 2s (then raised to 120s for a later check) purely to make the debounce practical to wait out in a live browser session: (1) clicked "+ New note", confirmed `/notes/new` shows no timestamps/delete/filename/history chrome, and confirmed `GET /api/notes` still returned `[]` at that point; (2) clicked "← All notes" without typing anything and confirmed the list was still empty; (3) clicked "+ New note" again, typed a title, waited out the (2s) debounce, and confirmed it created the note, transitioned the URL to `/notes/<slug>`, and rendered the full ordinary detail page (filename row, timestamps, delete button, a `[api] create_note ...` history entry); (4) with the interval raised to 120s, typed into a fresh draft and immediately clicked "← All notes" (an in-app route change) — confirmed the note was still created (the flush-on-unmount path), while an earlier attempt using a hard browser-level navigation instead of an in-app link click did *not* reliably flush, which is an accepted, pre-existing limitation of this whole flush-on-unmount pattern (no client-side JS can reliably intervene in a real page unload) rather than a regression introduced here.
