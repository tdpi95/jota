# Milestone 27 notes (File attachments)

[← back to PROGRESS.md](../../PROGRESS.md)

- New feature requested directly by the user: "add new milestone: file attachment. allow user to attach files, images to journal, task and note. user can also use a profile image for project." Not previously in PLAN.md, so per CLAUDE.md's working conventions, read PLAN.md/PROGRESS.md in full first. This touches the on-disk storage format (a new kind of content) and several existing pages/components at once, so before writing any code, used `AskUserQuestion` to settle four real design forks: (1) how an attachment is referenced from a task/journal/note body — an inline markdown embed (no new grammar/frontmatter) vs. a structured `attachments: [...]` list field; the user chose inline embed. (2) where files live on disk — one flat `attachments/` folder vs. a subfolder per content type; the user chose per-type subfolders. (3) whether to also ship an MCP `attach_file` tool this pass; the user chose UI-only for now. (4) whether to cap upload size, given every attachment gets committed to the workspace's git repo; the user chose no limit.
- Surveyed the exact integration points before writing code (a background Explore pass over `project.ts`/`taskLine.ts`/`projects.ts`/`notes.ts`/`journal.ts`/`tasks.ts`/`index.ts`/`vaultGit.ts`/`db.ts`/`MarkdownEditor.tsx`/`ProjectForm.tsx`/`ProjectCard.tsx`/`client.ts`/`ProjectDetailPage.tsx`) — this confirmed two things that shaped the design: task/note/journal `description`/`body` were already fully opaque to every service function (no parsing at all), so embedding a reference needed zero server-side change to those write paths; and `MarkdownEditor` exposes no cursor/selection API, so a toolbar-triggered insert would have to append to the end of the field rather than at the cursor (a deliberate, documented simplification, not an oversight).

## Storage + backend

- **`server/src/services/attachments.ts`** (new): `ATTACHMENT_FOLDERS = ['tasks', 'journal', 'notes', 'projects']`, `saveAttachment(workspacePath, folder, originalName, buffer)` — sanitizes the filename (`path.basename` + a character allowlist, blocking directory traversal in the *original* filename itself, not just relying on the serving route), auto-suffixes a collision (`foo.png` → `foo-2.png`, same precedent as a note's colliding-title auto-suffix), writes under `<workspace>/attachments/<folder>/`, and commits it (`attach_file <path>`) — its own independent commit, decoupled from whatever later task/note/journal/project write embeds a reference to it. No SQLite index table: unlike every other content type, an attachment has no frontmatter/structured fields to parse and cache, so file-system-only is the correct fit for this index's stated purpose (a derived cache over *parsed* content).
- **`server/src/routes/attachments.ts`** (new): `POST /api/attachments/:folder` (`multer`, in-memory storage — a new server dependency; nothing in this codebase parsed `multipart/form-data` before) and `GET /api/attachments/:folder/:filename`, resolved against the *active* workspace per request (not a static mount computed once at app-creation time, since the active workspace can change at runtime) via `res.sendFile(filename, {root: attachmentsDir})` — Express's `root`-relative resolution itself rejects an escaping path, confirmed live rather than assumed (a `..`-laden request 404s).
- **Project profile image is the one structured exception**: `ProjectFrontmatter.profileImage?: string` (`server/src/types.ts`), a plain workspace-relative path (`attachments/projects/foo.png`, no leading `../` — it's a data field, not a link that needs to resolve when the raw file is opened elsewhere). `UpdateProjectInput.profileImage?: string | null` follows the exact `undefined` = leave alone / `null` = clear convention already established by `UpdateTaskInput.due`/`description` (confirmed by reading `tasks.ts` before adding this, rather than inventing a new convention). Deliberately **not** on `CreateProjectInput` — first attempt included it there too, but `ProjectForm`'s `onSubmit` signature types its payload as `CreateProjectInput & UpdateProjectInput`, and TypeScript's intersection of `string | undefined` (create) with `string | null | undefined` (update) collapses to `string | undefined` — silently disallowing the `null`-to-clear case in a way that only broke at compile time. Fixed by keeping `profileImage` on the update side only, which also matches the actual UX: the image control is edit-only (gated behind `showArchived`, the same flag the archived checkbox already used), sidestepping the "no slug yet to upload against" ordering problem a create-time upload would have hit.
- Everything else (task description, journal body, note body) needed **no server-side change** — confirmed by reading `createTask`/`updateTask`, `createNote`/`updateNote`, `putJournalEntry` first: each just assigns the string through untouched, so an embedded `![...](...)` round-trips exactly like any other markdown a human might type.

## Referencing convention (client-side, `client/src/lib/attachments.ts`)

- An attachment embedded in a task description/journal body/note body is a genuine **file-relative** markdown link — `../attachments/tasks/foo.png` (a task description lives inside `projects/<slug>.md`, 1 level deep), `../attachments/notes/foo.png` (`notes/<slug>.md`, 1 level deep), or `../../attachments/journal/foo.png` (`journal/<year>/<date>.md`, 2 levels deep) — not a `/api/attachments/...` URL baked into the text. This was the point of choosing "inline embed" over a structured field in the first place: the stored value has to stay a real, working relative link in any external tool pointed at the same workspace (Obsidian, a plain editor, `git show`), not just something this app's own router happens to understand.
- `parseAttachmentRefs(body, folder)` re-scans the current text for `![alt](...)`/`[alt](...)` references matching that specific folder's prefix, de-duplicated by filename — there's no separate stored list; the markdown text is the only source of truth, matching the "inline embed" decision literally rather than half-implementing a shadow list alongside it.

## `AttachmentField` (`client/src/components/AttachmentField.tsx`)

- One shared component — an "attach file" icon button (hidden `<input type="file">` behind it) plus the parsed thumbnail/chip list — used identically by `JournalDayPage`, `NoteBodyEditor`, and `TaskForm`. Uploading calls the new `POST /api/attachments/:folder`, then appends the resulting markdown reference to the *end* of the current text via the same `onChange` the surrounding editor already uses.
- **Closes a real, otherwise-silent gap for the journal specifically**: Notes has a Preview mode and the task view modal renders `description` as real HTML (both via the existing `renderMarkdownToHtml`), so an embedded image would show up there regardless. The journal editor, by contrast, deliberately never renders markdown as HTML (PLAN.md "Journal editor," a milestone-23 decision — not reopened here) — without `AttachmentField`, an attached image would be inert raw text with zero visual feedback anywhere in the app. Rather than special-casing the journal with its own gallery widget, the same component was used everywhere, so all three content types get identical, live (parsed on every keystroke, not just on save) thumbnail feedback independent of whichever preview mode (if any) the surrounding editor happens to have.
- **`renderMarkdown.ts`** (Notes' Preview mode, the task view modal): added `image`/`link_open` renderer-rule overrides that rewrite a matching file-relative `src`/`href` to `/api/attachments/<folder>/<file>` right before rendering — a browser has no way to resolve `../attachments/...` against this single-page app's URL, so without this the same reference that works when the raw `.md` file is opened elsewhere would render as a broken image here. A rewritten link also gets `target="_blank"` (opens the file rather than navigating the SPA away from the note/task); an ordinary, non-attachment link is untouched either way. `markdown-it`'s bundled types (`markdown-it@15`) type a token attribute value as `string | number`, not `string` — required a `typeof === 'string'` guard before calling the rewrite function, caught immediately by `tsc`.

## Follow-up: open in the system's default app ("open image, file by system apps when click on image, file link")

- Clicking an attachment (a thumbnail or file chip in `AttachmentField`, or an embedded image/link in Notes' Preview mode or the task view modal) previously just opened `/api/attachments/<folder>/<file>` in a new tab — inside Electron, a raw image/PDF URL landing in a plain browser tab isn't "opening the file," it's just displaying it in Chromium. The ask was for the OS's own default app (an image viewer, a PDF reader, a text editor) to handle it, the same as double-clicking the file in a file manager.
- **No client-side change was needed at all.** Every attachment link already carried `target="_blank"` (added in the main milestone specifically so a rewritten link opens in a new tab rather than navigating the SPA away), and Electron's `BrowserWindow` already had a `setWindowOpenHandler` in `electron/src/main.ts` intercepting *every* `window.open`/`target="_blank"` navigation app-wide — previously used only to hand a plain external link (e.g. Settings' git-download link) to `shell.openExternal` instead of letting it silently open (or get denied into) a second Electron window. Extended that one handler to recognize a URL whose path matches `/api/attachments/<folder>/<file>` and route it differently.
- **`openAttachmentPath(pathname)`** (new, `electron/src/main.ts`): resolves the active workspace's absolute path via a `fetch` to the embedded server's own `GET /api/workspaces/active` (the exact same call `jota:get-reminder-settings` already makes for the same reason — the main process doesn't track workspace state itself, only the server does), joins it with `attachments/<folder>/<file>`, and calls `shell.openPath(absolutePath)` — the identical primitive `openWorkspaceFolder` already uses successfully to reveal a workspace folder in the file manager, just pointed at a file this time; `shell.openPath` opens a file via the OS's own default-app association, a folder via the file manager, transparently.
- **A real path-traversal bug found and fixed before shipping, not after**: the first draft validated the resolved absolute path only against the *workspace* root (`absolutePath.startsWith(workspaceRoot)`), not against `attachments/<folder>/` specifically — a `path.resolve`-based join with a crafted `../../` in the URL's filename segment stays under the workspace root while still escaping the attachments folder entirely (e.g. landing on a project or note file elsewhere in the workspace), so the check would have let the wrong things through. Caught by writing a small standalone Node script exercising the exact regex/decode/path-join logic against real files *and* several traversal payloads (plain `../`, percent-encoded `..%2f`, and a percent-encoded slash reintroducing a path separator only *after* decoding — the classic bypass for a "no slashes in the raw URL" check done before decoding) before ever touching the browser — several of those payloads slipped through the first version's guard. Fixed properly by validating `folder`/`filename` as single, literal path segments (`isSafePathSegment`: non-empty, not `.`/`..`, no `/` or `\`) *after* decoding, rejecting outright rather than trying to sanitize — only then is a plain `path.join` used, which can't escape `attachments/<folder>/` no matter what either segment contains once both are known-safe. Re-ran the same script afterward to confirm every traversal payload is now rejected while ordinary filenames (including ones with spaces) still resolve correctly.
- **Verification scope, stated plainly**: `npx tsc --noEmit` and `npm run build -w electron` both clean; the regex/decode/traversal-guard logic itself was verified in isolation (a standalone script mirroring the exact code, against both benign and adversarial inputs, described above). What was **not** verified live is the actual end-to-end behavior inside a running Electron window (clicking a real link and watching a native image viewer/PDF reader actually open) — doing that safely would mean spinning up the full Electron + embedded-server + Vite-dev-server stack, which this app's dev mode hardcodes to fixed ports (4174/5173), risking a collision with the user's own already-running dev session; unlike the browser-only follow-ups above, there's no isolated-scratch-port equivalent for a full Electron launch without changing `main.ts`'s dev-mode port constants, which felt like more surface area than this fix warranted. This is a main-process-only change, so it also needs a full Electron app restart (not just a renderer/page reload) to take effect once running.

## Fix: the click-in-system-app follow-up didn't actually work for non-image files ("i still can't click on non-image file linke")

- The previous follow-up's approach (extending `setWindowOpenHandler` in `electron/src/main.ts` to resolve an `/api/attachments/...` URL and hand it to `shell.openPath`) turned out to be unreliable in practice, and this is why: `setWindowOpenHandler` only fires when Chromium decides a click is asking to create a *new window/tab*. For a file this app's `BrowserWindow` has no built-in viewer for (a PDF — Electron doesn't bundle Chrome's PDF viewer plugin unless `webPreferences.plugins` is explicitly enabled, which it isn't here), Chromium instead treats the click as a **download** and fires a `will-download` session event — which never reaches `setWindowOpenHandler` at all. The previous fix only ever had a chance of working for a file Chromium would render inline as its own new-window navigation (which is why the *image* case appeared to work when tested); a PDF or any other non-renderable-in-place file silently downloaded to the OS's default Downloads folder instead — indistinguishable from "the link did nothing" if the user didn't go check that folder.
- **Real fix**: stop depending on the browser's own navigate-vs-download decision at all. The renderer now intercepts the click *itself*, before Chromium ever gets to make that decision, and calls a new `jota:open-attachment` IPC bridge directly:
  - `electron/src/preload.ts`/`main.ts`: new `openAttachment(relPath)` bridge method. The core resolve-and-`shell.openPath` logic was pulled out of the old URL-pathname-shaped `openAttachmentPath` into a `openWorkspaceRelativeAttachment(relPath)` taking the plain `"attachments/<folder>/<file>"` shape directly (what the renderer already has, e.g. from `AttachmentInfo.path`) — `openAttachmentPath` (still used by `setWindowOpenHandler`, now demoted to a fallback for whatever the renderer's own click interception can't catch, like a middle-click) just extracts that same shape from a full URL and delegates to it. Same traversal-safe segment validation as before, unchanged.
  - `client/src/lib/attachments.ts`: `openAttachmentIfPossible(event, url)` — if `window.jota` exists, extracts `"attachments/<folder>/<file>"` from the URL, calls `event.preventDefault()`, and hands off to `bridge.openAttachment(relPath)`; does nothing (letting the plain `target="_blank"` anchor behavior proceed) when there's no bridge, e.g. a plain browser tab. `handleRenderedAttachmentClick(event)` is the same idea for a *rendered HTML* container (Notes' Preview mode, the task view modal) where there's no per-element React `onClick` to attach — one delegated handler on the container finds whichever `<a>` the click landed on/inside (covering the image-wrapping anchor from the fix above too) via `closest('a')`.
  - Wired onto `AttachmentField`'s own two `<a>` elements (image thumbnail, file chip) and as a container-level `onClick` on `NoteBodyEditor`'s `.note-preview` div and `TaskRow`'s `.task-desc` div.
- **Verified live**, and this time in a way that actually proves the mechanism rather than just checking DOM structure: against the same isolated scratch project/task as the earlier fix, injected a **mock** `window.jota = { openAttachment: (relPath) => { record(relPath); return Promise.resolve(true) } }` via `javascript_tool` (simulating the Electron bridge being present, since this sandbox can't run real Electron) before clicking. Confirmed: clicking the `doc.pdf` link called the mock with exactly `"attachments/tasks/doc.pdf"` and the page **did not navigate** (`location.href` unchanged) — proving the click was fully intercepted before any browser-native navigate/download decision could happen, which is exactly the scenario the previous fix failed at. Clicking the embedded image likewise called the mock with `"attachments/tasks/mock.png"`. Removing the mock (simulating a plain browser tab) and reloading confirmed `window.jota` is genuinely `undefined` there, so `openAttachmentIfPossible` takes its early-return no-op path — by inspection this cannot alter default behavior, since it does nothing at all in that branch.
- **What remains unverified, stated plainly (same caveat as the original follow-up)**: this proves the interception/IPC-call logic is correct, but not that `shell.openPath` itself successfully launches a real OS app for a real PDF inside an actual running Electron window — that would need the full Electron + embedded-server + Vite-dev-server stack running, which risks colliding with the user's own dev session on this app's hardcoded dev ports. Worth a real click-test after restarting the Electron app (a main-process change, so a renderer reload alone won't pick it up).
- `npx tsc --noEmit` (client, server, electron) and `npm run build -w client`/`npm run build -w electron` all clean; `npm test -w server` unaffected (161/161, no server-side changes).

## Fix: a filename with a space produced a link that couldn't even be parsed ("i mean file link below image is unclickable")

- A follow-up screenshot made the actual bug obvious: the file link wasn't rendering as a clickable link *at all* — it showed up as literal bracketed text, `[Z66_TongTaiGoRap_Project Timeline_091426-2.xlsx]` followed by `(../attachments/tasks/Z66_TongTaiGoRap_Project Timeline_091426-2.xlsx)`, in the task's rendered description. Root cause: the real filename contains a **space** ("...Project Timeline_..."), and `attachmentMarkdown()` wrote it into a *bare* CommonMark link destination (`[text](../attachments/.../name with space.xlsx)`) — per the CommonMark spec, a bare link destination (no `<...>`) cannot contain a literal space (or unbalanced parens) at all, so `markdown-it` correctly refuses to parse it as a link and falls back to rendering the raw `[...]...(…)` text. This wasn't a click-handling bug like the two before it — the link genuinely never existed in the rendered HTML. Confirmed directly with a two-line `markdown-it` repro (bracketed vs. bare form against the exact same filename) before touching any code, to be certain of the root cause rather than guessing from the screenshot alone.
- **Fix**: `attachmentMarkdown()` now always wraps the destination in `<...>` — CommonMark's angle-bracket link-destination form, which allows any character except a literal `<`, `>`, or newline (none of which a filename can ever contain — `sanitizeFilename`, server-side, already strips them), sidestepping both the space problem and a related one (unbalanced parens, e.g. `invoice (final).pdf`, which would also break a bare destination). `markdown-it` parses this form natively and — confirmed by direct inspection of its output — automatically percent-encodes the space in the rendered `href`/`src` (`Project%20Timeline`), so `renderMarkdown.ts` needed **no changes at all**.
- `parseAttachmentRefs` (the regex `AttachmentField` uses to build its own thumbnail/chip list, independent of `markdown-it`) needed updating to recognize the new bracketed form *in addition to* the old bare one — kept as two alternatives in one pattern rather than replacing the old pattern outright, so an attachment reference saved by an earlier version of this app (any bare-form filename *without* a space, which was never broken) still shows up in the list; only a bare-form reference that already has a space in it — impossible to write correctly in that form regardless of parser — doesn't retroactively fix itself, since the already-saved markdown text is genuinely invalid CommonMark. The parsed URL now always goes through `encodeURIComponent(filename)` too, regardless of which form matched, since a raw space in an `href`/`src` attribute is unreliable even when the browser tolerates it.
- **A pre-existing note/task with this exact bug** (a bare-destination reference to a space-containing filename, saved before this fix) won't self-heal — the saved markdown text itself is invalid and needs a one-time manual edit: wrapping the existing destination in `<...>` (e.g. `[name.xlsx](../attachments/tasks/name.xlsx)` → `[name.xlsx](<../attachments/tasks/name.xlsx>)`) fixes it in place, or removing the broken line and re-attaching the same file produces a correct new reference.
