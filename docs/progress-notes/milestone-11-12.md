- **Projects/Tasks UI** (`pages/ProjectsListPage.tsx`, `pages/ProjectDetailPage.tsx`; `components/{ProjectCard,ProjectForm,TaskRow,TaskForm,TimeSpentBadge,DueDateBadge,TagInput,MarkdownTextarea}.tsx`): the list page has a "+ New project" form (name/description/tags/color-swatch picker), an archived filter, and per-project todo/doing/done counts read straight off the already-fetched `ProjectSummary.tasks` (no separate counts endpoint needed). - **Journal UI** (`pages/{JournalYearPage,JournalDayPage}.tsx`): `/journal` redirects to `/journal/<year>/<today>` per PLAN.md. The year page lists every date the index has a row for (only dates with an actual file — matches `listJournalYear`'s source) with a hasBody dot and tags, plus year prev/next nav. The day page has an autosaving tag input + body textarea and the **linked-tasks section**: chips (task title + owning project's color dot) with a remove button, and a "+ Add task" picker backed by `GET /api/tasks/search?q=` (debounced 300ms), matching PLAN.md's spec exactly. There's no "get task by id" REST endpoint to resolve a linked chip's title/color from just its id, so chip resolution reuses `GET /api/projects` (already fetched for the nav elsewhere, and read straight from project files per PLAN.md's "which reads go where" — never stale) flattened into an id→task map client-side, rather than adding a new backend route for one UI need.
- **Two real bugs found and fixed during live testing** (not just typechecked — see "Verified live" below):
  1. **Journal autosave lost an edit made just before navigating away.** The original implementation scheduled the debounced save from a `useEffect` watching `[body, tags]`, which also raced against the *separate* effect that syncs freshly-loaded server data into that same local state — on the render where loaded data first lands, one effect sees the update and the other doesn't yet, and a stale/empty value could get scheduled for save; navigating away (the day-page remounts entirely on date change, by design) could then flush that stale value before the correct one ever got a chance to overwrite it, observed live as a typed tag and body edit reverting to empty on disk. Fixed by driving saves only from the actual `onChange` handlers via an explicit `dirtyRef` flag (true only on a real edit, cleared on load-sync and on successful save) instead of diffing two independently-updated snapshots — removes the ambiguity entirely rather than papering over the race. A `useEffect` with an empty dependency array now flushes any still-dirty edit synchronously in its cleanup (fire-and-forget `PUT`) so a fast prev/next-day click never drops work.
  2. **A 404 (e.g. a bad project slug in the URL) could crash `ProjectDetailPage`** with "Cannot read properties of undefined (reading 'project')". TanStack Query's default retry (3 attempts with backoff) leaves a real window on a query that ultimately errors: `isLoading` can go false between retry attempts before `isError` goes true, so a page gating on `isLoading`/`isError` alone can render `data!.project` while `data` is still `undefined`. Fixed at the `QueryClient` level (`main.tsx`): a 4xx (`ApiError` with `statusCode < 500`) is never retried (a bad slug won't start existing on attempt 2), 5xx/network errors keep the default retry behavior; `ProjectDetailPage` also gained a defensive `if (!data) return <Loading/>` rather than relying solely on that timing invariant holding forever.
