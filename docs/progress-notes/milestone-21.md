# Milestone 21 notes (Theming: color palettes + dark theme)

[← back to PROGRESS.md](../../PROGRESS.md)

- New milestone requested directly by the user ("add color palettes and dark theme; use current palette as default, add green, blue, violet") — started ahead of milestone 18's remaining items, same pattern as 19/20. Investigated the existing `language` preference end-to-end first (storage shape, route, service, client bootstrap, Settings picker) specifically to mirror it rather than invent a parallel mechanism, per CLAUDE.md's "don't introduce an alternative to a settled convention" guidance. PLAN.md gained a new "Theming" design section (mirroring "Localization"'s structure), a milestone-21 bullet + Verify step, a `client/src/lib/theme.ts` line in the Project scaffold, and a `/settings` bullet update.
- **Storage**: `WorkspaceRegistry.theme?: 'light' | 'dark'` and `accentPalette?: 'default' | 'green' | 'blue' | 'violet'` (`server/src/lib/workspaces.ts`), same app-wide shape as `language`/`launchAtLogin`. `services/workspaces.ts` gained `get/setThemePreference` and `get/setAccentPalettePreference` — `undefined` normalizes to `'light'`/`'default'` on read, same "no undecided state to track" reasoning `language` already uses. `routes/preferences.ts` gained `GET/PUT /api/preferences/theme` and `GET/PUT /api/preferences/accent-palette`, both 400ing on an invalid value. Two new cases in `server/src/services/workspaces.test.ts` (103 tests total, up from 101).
- **Deliberately no Electron bridge at all here** — one step further than `language`'s "no *preload* bridge, but the main process still polls the route for its own tray/notification strings": a color theme has no Electron-side consumer whatsoever (the tray icon and OS notifications aren't styled by this app's CSS), so nothing outside `client/` ever reads `theme`/`accentPalette`.
- **Client bootstrap**: `client/src/lib/theme.ts` (new) — `THEMES`/`ACCENT_PALETTES` const tuples + types, `ACCENT_PALETTE_SWATCH` (a literal oklch preview color per palette, purely for rendering the picker's swatch dot — same role as `lib/colors.ts`'s `COLOR_PALETTE` for the project color picker, never the source of the actual on-screen color), and `applyTheme`/`applyAccentPalette` (set `data-theme`/`data-palette` on `document.documentElement`). `main.tsx` fetches both preferences in the same `Promise.all` as the language fetch, applying each before the first `createRoot(...).render(...)` — avoids a flash of the wrong appearance the same way the language fetch avoids a flash of the wrong language, falling back to `'light'`/`'default'` on any failure.
- **`SettingsPage.tsx` gained Theme and Accent color sections**, right after Language — both reuse the exact `role="radiogroup"` + `.ws-row-btn`/`.is-active` pattern the Language picker already established (a new `.palette-picker`/`.palette-dot` CSS rule handles the small swatch dot on each accent-color button, `.lang-picker`'s flex-row rule is reused as-is for the theme picker). Local `theme`/`accentPalette` state is seeded straight from the `data-theme`/`data-palette` attributes `main.tsx` already applied before this page could mount — no separate loading state, same reasoning `i18n.language` already gets a pass on. Clicking an option calls the REST API then `applyTheme`/`applyAccentPalette` in the mutation's `onSuccess` — persists and switches instantly, no reload.
- **`app.css` token refactor** — the actual bulk of this milestone. Before: 15 tokens in `:root`, plus ~20 additional `oklch(...)` literals hardcoded directly in component rules (hover/active backgrounds, dashed borders, modal overlay, box-shadows), never tokenized. After: every color in the file is a custom property or an alpha variant of one.
  - Added `--accent-hue` (defaulting to 45, the app's original accent hue) and rewrote `--accent`/`--accent-hover`/`--accent-soft` to take their hue from `var(--accent-hue)` instead of a literal — the whole reason for using oklch here is that lightness/chroma stay perceptually constant while only the hue moves, so `[data-palette='green'|'blue'|'violet']` (145/250/305) each need to override *only* `--accent-hue`, nothing else. `'default'` needs no override rule at all — it *is* `:root`'s own value, which is exactly why `oklch(58% 0.15 45)` (the pre-milestone literal) had to survive unchanged as the hue-45 case, confirmed byte-identical live (see Verified below).
  - Added `--surface-hover`/`--surface-active`/`--surface-muted` (three progressively darker/more-saturated muted-neutral steps absorbing what were four near-identical hardcoded lightness/chroma combinations — e.g. `93% 0.012 75` and `93% 0.01 75` collapsed into the same token, a 0.002 chroma difference being visually inert), `--border-muted` (hover borders + dashed placeholder borders, similarly collapsing two near-identical literals), `--overlay-backdrop` (modal scrim), `--shadow-color-soft`/`--shadow-color-strong` (box-shadow colors, kept separate from the offset/blur which stays inline in each rule), `--drag-over-bg` (Kanban drag-over highlight), and `--good-border` (the one non-neutral literal found, `oklch(80% 0.05 155)` on the calendar's "has journal entry" indicator — already green-hued like `--good`, just never tokenized).
  - `:root[data-theme='dark']` overrides every one of the above in one block (dark backgrounds ~22-27% lightness, near-white text ~94%, accent/good/danger brightened to ~68-76% lightness for dark-background contrast) — deliberately does *not* touch `--accent-hue`, so whichever palette is active carries over unchanged; theme and palette are independent axes, not eight hardcoded combinations. `color-scheme` is set to `light`/`dark` alongside so native form controls/scrollbars follow.
  - Every hardcoded literal was replaced with the matching `var(...)` — grouped by exact matching literal and replaced with `replace_all` where the same value repeated verbatim across unrelated selectors (e.g. `oklch(94% 0.012 75)` appeared identically in three separate hover rules), confirmed with a final `grep 'oklch(' app.css | grep -v -- '--'` returning nothing outside the token-definition blocks.
- **Verified**: `npm test -w server` (103 tests, all passing, including the two new theme/accent-palette cases); `npx tsc --noEmit` clean for `server/`, `client/`, and `electron/`; `npm run build -w client` clean; a throwaway script confirmed `en.json`/`vi.json` have identical key trees (226 leaf keys each, up from 206 — `settings.theme.*`/`settings.palette.*` added to both). **Verified live** against the real running server + Vite dev server in an actual browser, driven via `javascript_tool` (the Browser pane's screenshot tool was unavailable this session — hidden-pane rendering timeout — so verification read computed styles directly rather than visually, which is if anything more precise for confirming exact token resolution): clicked through Theme/Accent-color on `/settings` and confirmed `document.documentElement`'s `data-theme`/`data-palette` attributes and every derived `getComputedStyle(...)` custom property (`--paper`, `--ink`, `--accent`, `--accent-hue`) updated correctly and persisted server-side (`GET /api/preferences/{theme,accent-palette}` read back the new value after each click); confirmed dark+green together on the Dashboard page (not just Settings) rendered coherent computed colors for `.app`, `.sidebar`, the active `.nav-item` (accent-soft background + accent text), and links; opened the New Project modal in dark mode and confirmed `.modal-overlay`'s `--overlay-backdrop` and `.modal`'s `--shadow-color-strong` box-shadow both resolved; cycled back through light+blue and light+violet and confirmed the hue-only override worked identically in light mode; and specifically confirmed light+`'default'`'s `--accent` computed to the exact pre-milestone literal (`oklch(58% 0.15 45)`) and `--paper` to the exact pre-milestone literal (`oklch(97.3% 0.012 75)`) — no visual regression for an existing install that never touches the new Settings sections. Left the real `Poco Demo` workspace's `theme`/`accentPalette` preferences reset to `light`/`default` afterward (the state they were in before this session's manual testing began).

## Follow-up: theme-aware highlight colors

The user asked, in a follow-up message, to "change highlight color based on theme" — clarified via `AskUserQuestion` into three concrete targets, all pursued: the today/due-today highlight, the journal-entry-day highlight, and the native text-selection highlight.

- **Found a real contrast bug, not just a naming gap**: measuring rendered contrast (canvas-readback + WCAG relative-luminance, since `getComputedStyle` returns the `oklch(...)` function unresolved rather than the rendered sRGB) showed the existing "white text on a solid `--accent`/`--good` fill" pattern (`.btn-primary`, `.page-action`, `.add-task-btn`, `.ws-add-btn`, `.cal-day.today`, `.cp-year-day.today`, the done-status checkmark) measured ~4.0-4.6:1 in light theme (fine) but only ~2.5-2.8:1 in dark theme (fails WCAG AA's 3:1 even for bold/large text) — dark theme deliberately *brightens* `--accent`/`--good` (so they still read as accent-colored *text* against the dark page background), and that same brightening is exactly what breaks white-on-fill contrast for the *button* pattern. Two different contrast needs pulling the same token in opposite directions is why this needed its own token rather than a tweak to `--accent`/`--good` itself.
- **Fix**: added `--accent-contrast`/`--good-contrast`/`--danger-contrast` (defaulting to `white`, matching every pre-existing use) to `:root`, overridden to `var(--paper)` — reusing the dark theme's own near-black background token, no new literal needed — inside `:root[data-theme='dark']`. Replaced all 7 `color: white` sites (6 on `--accent`, 1 — the status-btn's checkmark icon color, on `--good`) with the matching `var(--*-contrast)`. `--danger-contrast` has no current caller (nothing today fills a solid `--danger` background with text) but was added for symmetry and to head off the same bug the next time someone adds a destructive-action button — per PLAN.md's own "a hardcoded color literal is a regression here" convention.
- **Journal-entry-day highlight**: measured already correct *for light/dark* as-is (`--good-soft` got its dark-theme override in the original milestone-21 pass) — the wash-vs-paper contrast is intentionally low (~1.12:1 light, ~1.21:1 dark, "a soft wash" per PLAN.md's own wording for this feature) and consistent between themes, and the day-number text sitting on it uses `var(--ink)` already, so it reads correctly in both. **This measurement checked the wrong axis** — see the correction below; the user's actual complaint was about *palette*, not light/dark, and this conclusion was wrong for that axis.
- **Text selection**: added a `::selection { background: var(--accent-soft); }` rule (`app.css`, right after the `a`/`a:hover` rules) — previously the one visual left as the browser/OS's unthemed default blue, untouched by either `data-theme` or `data-palette`. Left `color` unset (inherits `var(--ink)`, already theme-correct) rather than adding a dedicated token — measured contrast is 11.6-13.3:1 in both themes, comfortably enough that `--accent-soft` alone does the job.
- **Verified**: `npx tsc --noEmit` + `npm run build -w client` clean; `npm test -w server` still 103/103 (CSS-only change). **Verified live**, contrast measured programmatically rather than by eye (canvas `fillStyle`/`getImageData` to force the browser to actually resolve each `oklch(...)` to rendered sRGB, then the standard WCAG relative-luminance contrast formula) across all 8 theme×palette combinations: on-fill text contrast went from ~2.5-2.8:1 to ~6.1-6.9:1 in dark theme for every palette, with light theme's ~4.0-4.6:1 completely unchanged (confirming the fix is additive, not a regression to the already-working light-theme case); `::selection` measured 11.6-13.3:1; the journal wash's already-correct behavior was measured, not just assumed. No preference values were mutated server-side during this pass (verification set `data-theme`/`data-palette` directly via `javascript_tool` rather than clicking through the Settings mutations), so the workspace's stored `theme`/`accentPalette` were undisturbed throughout.

## Correction: journal-entry highlight was still hardcoded green (wrong axis measured above)

The user reported, in a further follow-up: "journal entry highlight in calendar side bar and page is still green." The prior pass above measured the journal wash's *light-vs-dark* contrast and found it correct, but never checked whether it responded to the *palette* choice — it didn't. `.cal-day.has-journal`, `.cp-day.has-journal`, and `.cp-year-day.has-journal` all used `--good-soft`/`--good-border`, a fixed hue-155 semantic "success" color with no relationship to `--accent-hue` — so switching to Blue or Violet correctly left this one wash green, exactly as reported.

- **Distinguishing "done" green from "has a journal entry"**: `--good`/`--good-soft` are still exactly what they were and are deliberately *not* palette-tracking — the completed-task checkmark (`.status-btn.st-done`) and the active-workspace pill (`.ws-row-btn.is-active`) still mean "success/done" and should stay a fixed green regardless of accent palette, the same way most design systems keep a semantic success color independent of brand color. The bug was specifically that the journal-day highlight had been modeled as the same "done" semantic when it should have been an accent-colored one (it's marking "this day has content", not "this succeeded") — three call sites needed to move, nothing about `--good` itself was wrong.
- **Fix**: added `--accent-border` (`:root`, plus a `:root[data-theme='dark']` override) — exactly `--good-border`'s previous pattern (a mid-lightness border tint sitting between `--accent` and `--accent-soft`) but keyed to `var(--accent-hue)` instead of the literal 155. Switched all three `.has-journal` rules from `--good-soft`/`--good-border` to `--accent-soft`/`--accent-border`. `--good-border` itself is now unused anywhere (`--good-soft` still is, for the two "done" call sites above) and was deleted from both the light and dark token blocks rather than left dead.
- **`.cp-day.has-journal.today` (a day that's both) needed no change**: it already fully overrides `box-shadow`/`border-color` to a solid `var(--accent)` regardless of what `.has-journal` alone sets, so a day that's both today and journal-logged still reads as two distinguishable states — just via intensity (solid border over a soft wash) within one hue family now, rather than via two unrelated hues as before. Documented as a deliberate trade-off in both `app.css`'s comment and PLAN.md's "Theming" section, not an oversight.
- **Verified live**: confirmed via `getComputedStyle` on the real `.cp-day.has-journal` element (Calendar page) and `.cal-day.has-journal` element (sidebar) — not just the token definitions — that switching `data-palette` between all four values changes the rendered background/border hue (e.g. `oklch(0.93 0.03 250)` for Blue, `oklch(0.93 0.03 305)` for Violet), confirming the fix reaches the actual DOM, not only `:root`. `npx tsc --noEmit`, `npm run build -w client`, and `npm test -w server` (103/103) all re-confirmed clean after the token deletion.
