# Milestone 8 notes

[← back to PROGRESS.md](../../PROGRESS.md)

- `server/src/services/journal.ts` — `getJournalEntry`/`putJournalEntry`/`linkTask`/`unlinkTask` all read/write the day's file directly (never the index, per PLAN.md's "which reads go where" — single-entry reads are never stale); `listJournalYear` is the one aggregate view here and reads from the index instead, same split as milestone 4 already established for projects.
- **`getJournalEntry` returns a default, unpersisted entry (not a 404) when the file doesn't exist yet** — a deliberate choice beyond PLAN.md's literal route list: the frontend's journal day page and "+ log to today" (milestones 12/14) need something immediately editable for *any* date, and creating a file (and a git commit) for every date someone merely opens would be exactly the write-amplification PLAN.md warns against elsewhere. Nothing is written to disk until an actual `putJournalEntry` or `linkTask` call. `linkTask` *does* auto-create the file on first link (per PLAN.md, explicitly), but is a no-op (no write/reindex/commit) if the task is already linked; `unlinkTask` never creates a file — removing a link from an entry that doesn't exist is trivially already true.
- `year`/`date` are cross-validated against each other (`journal/:year/:date` where `:year` doesn't match `:date`'s own `YYYY-` prefix throws 400) — the file path is always derived from the date itself, so a mismatched year in the URL couldn't otherwise cause a bug, just a confusing silent success.
- `putJournalEntry`'s `linkedTasks` full-replace is deduped (PLAN.md: "insertion-ordered, deduped on add") even though PUT is a full replace rather than an incremental add — a client resending a list with an accidental duplicate shouldn't be able to write one to the file.
- `server/src/routes/journal.ts` — `GET /api/journal/:year`, `GET/PUT /api/journal/:year/:date`, `POST/DELETE /api/journal/:year/:date/links/:taskId`, all thin wrappers, mounted at `/api/journal`.
- Verified live: `GET` on a date with no file yet returned the default empty entry (nothing written); `PUT` created the file and committed `[api] upsert_journal_entry ...`; `POST .../links/:taskId` linked a task and committed `[api] link_task ...`; `GET /api/journal/:year` and `GET /api/tasks/:taskId/journal-links` both reflected the link; `DELETE .../links/:taskId` removed it and committed `[api] unlink_task ...`, confirmed via a follow-up `journal-links` call returning `[]`.
