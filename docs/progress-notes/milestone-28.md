# Milestone 28 notes (Pinned projects/notes)

[← back to PROGRESS.md](../../PROGRESS.md)

- New feature requested directly by the user: "replace recent projects section in dashboard by pinned projects and notes." Not previously in PLAN.md, so per CLAUDE.md's working conventions, read PLAN.md/PROGRESS.md first, then used `AskUserQuestion` to settle three design forks before writing any code:
  1. **Where pin state lives** — a frontmatter field on the project/note file (`pinned: true`, same convention as a project's `archived`) vs. an app-wide preference list in `~/.jota/config.json` (same storage the Dashboard's group filter already uses). The user chose the preference list.
  2. **How pinning is toggled** — a small pin icon directly on `ProjectCard`/`NoteRow` vs. a checkbox in the existing edit forms. The user chose the icon.
  3. **Section behavior** — keep the same collapsible disclosure + persisted open/closed state, and whether to keep the old top-3 cap or show every pinned item uncapped. The user chose: keep the collapsible, no cap.

## Storage + backend

- **No grammar change at all** — since pin state is an app preference, not vault content, neither `ProjectFrontmatter` nor `NoteFrontmatter` gained a field, and neither parser/serializer was touched. This is the direct consequence of the first `AskUserQuestion` answer: the alternative (a frontmatter field) would have needed the round-trip test re-verified for two file types; this needed none of that.
- **`lib/workspaces.ts`**: `WorkspaceRegistry` gains `pinnedProjectSlugs?: string[]` and `pinnedNoteSlugs?: string[]`, same shape and the same "app-wide, not per-workspace" reasoning already used for `dashboardGroupFilter` — pin*ning* is a personal organizing choice even though the slugs themselves are workspace-scoped identifiers. A slug no longer present in the active workspace (project/note deleted, or a leftover from a different workspace) is left for the client to drop silently, matching the group filter's own staleness handling — nothing here proactively prunes it.
- **`services/workspaces.ts`**: `get/setPinnedProjectsPreference` and `get/setPinnedNotesPreference`, both `undefined → []`, identical shape to `get/setDashboardGroupFilterPreference`.
- **Renamed, not kept alongside**: `dashboardRecentProjectsOpen`/`getDashboardRecentProjectsOpenPreference`/`GET/PUT /api/preferences/dashboard-recent-projects-open` all became `dashboardPinnedOpen`/`getDashboardPinnedOpenPreference`/`.../dashboard-pinned-open` — a clean rename (per this project's "no backwards-compatibility hacks" convention) rather than leaving a dead field beside a new one, since the section it names no longer exists under its old name either.
- **Routes**: `GET/PUT /api/preferences/pinned-projects` and `.../pinned-notes`, `{slugs: string[]}` in and out, same validation shape (`Array.isArray` + every element a string) as `dashboard-group-filter`.

## Frontend

- **`client/src/lib/pins.ts`** (new): `usePinnedProjects()`/`usePinnedNotes()`, each a thin `useQuery`+`useMutation` pair keyed `['pinnedProjects']`/`['pinnedNotes']` — shared by every page that renders a pinnable card/row (`ProjectsListPage`, `NotesListPage`, `DashboardPage`) so a toggle on one page is reflected on another without an explicit cross-page invalidation (the mutation's `onSuccess` writes straight into the shared query-cache entry via `queryClient.setQueryData`).
- **`PinButton.tsx`** (new): a small icon button — filled star when pinned, outline when not — that calls `e.preventDefault()`/`e.stopPropagation()` before its own `onToggle`, since every current caller (`ProjectCard`, `NoteRow`) is itself a full-row `<Link>`.
- **`ProjectCard.tsx`**: `pinned`/`onTogglePin` are both optional props (nothing breaks a caller that doesn't care about pinning). `variant="grid"` renders the button absolutely positioned in the card's top-right corner (`.pin-btn-grid`, needing `position: relative` added to `.project-card-grid` and `padding-right` on `.project-card-head` so a long project name doesn't run underneath it); `variant="row"` renders it inline after the task-count metadata, the row's natural trailing slot.
- **`NoteRow.tsx`**: same optional-props treatment, button rendered inline after `.note-updated`.
- **`ProjectsListPage.tsx`** / **`NotesListPage.tsx`**: each now calls its respective `usePinned*` hook and passes `pinned`/`onTogglePin` through to every card/row it renders — this is the only change to either page; the pin toggle itself needed no new UI here beyond wiring the button that was already added to the shared component.
- **`DashboardPage.tsx`**: the "Recent projects" section (`recentProjects` — top 3 by `lastActivity`, `RECENT_PROJECTS_LIMIT`) is replaced by a "Pinned" section. `pinnedProjects`/`pinnedNotes` are each built by mapping the *pinned-slugs* array (not the project/note list) through a lookup and filtering out misses — this both drops stale slugs silently and, as a side effect, orders the section by pin order (oldest-pinned-first) rather than by name/date. A new `notesQuery` (`['notes']`, same key `NotesListPage` uses, so it's cache-warm if that page was visited first this session) supplies the note data the Dashboard never needed before. The section renders the pinned-projects grid (unchanged `ProjectCard variant="grid"` markup) followed by a `.notes-list` of pinned `NoteRow`s when either is non-empty; the whole section (both sub-lists) shares one collapse toggle, same as the single list the old section had.
- **CSS**: `.pin-btn`/`.pin-btn.is-pinned`/`.pin-btn-grid` (new), `position: relative` added to `.project-card-grid`, `padding-right` added to `.project-card-head`, `.dashboard-pinned-notes { margin-top: 10px }` for spacing when the Dashboard's Pinned section renders both a projects grid and a notes list.
- **i18n**: `dashboard.recentProjects`/`dashboard.seeAllProjects` removed (the section this fed no longer caps or links to "all projects"), replaced by `dashboard.pinned` ("Pinned"/"Đã ghim"); `common.pin`/`common.unpin` added for the button's title/aria-label (both languages). Confirmed structurally identical afterward (297 leaf keys each).

## Follow-up: pin icon instead of star ("use pin icon instead of star icon")

- `PinButton.tsx`'s star-shaped SVG path was swapped for a thumbtack (head/cap-line/needle, three `<path>`s) — a literal "pin" reads less ambiguously than a star, which is more commonly associated with "favorite"/rating elsewhere. Filled vs. outline toggle behavior (and the button's own hover/`.is-pinned` accent-color CSS) is otherwise unchanged. Verified live against the same isolated scratch setup — the thumbtack renders correctly, filled and accent-colored, on both the pinned project grid card and the pinned note row.

## Follow-up: separate the Dashboard's three sections ("separate pinned section and filter, tasks section")

- The Pinned section, the group/tag filter rows, and the task buckets previously ran together with only each block's own bottom margin between them — no visual cue that they're distinct groupings. First fix: three separate wrappers (`dashboard-pinned-section`, `dashboard-filters`, `dashboard-tasks`), all sharing a `dashboard-section` class, plus one adjacency-based CSS rule (`.dashboard-section + .dashboard-section { margin-top / padding-top / border-top: hairline }`, the same divider shape this file already uses for `.ws-open-new`) — a divider between any two that land adjacent in the DOM.

## Follow-up: filters belong with tasks, not their own section ("filter should be in the same group with tasks")

- The three-way split put a divider *between* the filter rows and the task buckets they narrow — wrong grouping, since a filter is conceptually part of the list it's filtering, not a peer section next to it. Fixed by merging the filter rows and the task-bucket list into one shared wrapper (`dashboard-filters-and-tasks`, the only element still carrying `dashboard-section`) containing the (optional) `dashboard-filters` block followed by the loading/error state or the `dashboard-tasks` bucket list — plain, divider-free spacing between the filters and the buckets (the filter row's own existing `margin-bottom` already provided that), same as before this section's own follow-up. `Pinned` stays the only other `dashboard-section`, so the adjacency rule now draws exactly one divider, between Pinned and everything else, only when Pinned actually rendered. Verified live against the same isolated scratch setup (two projects in different groups, two tasks with different tags, so both filter rows and both buckets render) — confirmed Group/Tags filters now flow directly into "Due today"/"This week" with no rule between them, the one hairline divider still sits between Pinned and this combined group, and the console shows zero errors.
