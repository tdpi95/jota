## Milestone 18 notes, part 21 (MCP snippet: default to poco's currently-open workspace, don't hardcode it)

- Direct follow-up to part 20, at the user's request: the self-serve snippet always hardcoded `POCO_WORKSPACE` to whatever workspace was active *at the moment Settings happened to render* — but `server/src/mcp/index.ts`'s own `resolveWorkspacePath()` already falls back to the app registry's currently-active workspace whenever `POCO_WORKSPACE` is unset (milestone 10 design, unchanged). Hardcoding it into a saved host config meant an agent's target silently stayed pinned to whatever workspace was open the day the snippet was copied, even after switching workspaces in the app later — the opposite of the "whichever workspace is open" behavior a user copying this snippet would reasonably expect.
- **Fix**: `SettingsPage.tsx` no longer merges `POCO_WORKSPACE` into `mcpEnv` at all — the generated `env` for all three snippets is now exactly `mcpInfoQuery.data?.env` (the AppImage-only `DISPLAY`/`DBUS_SESSION_BUS_ADDRESS` from part 20, still included there since that one's a hard requirement, not a preference). All three snippet builders (JSON `env` key, TOML `env = {...}` line, `claude mcp add`'s `-e` flags) now omit the env entirely rather than emitting an empty `{}`/stray flag when there's nothing to add — the common dev/plain-node case, which has no extra env at all.
- **New UI copy** explains the default and the opt-in instead of silently changing behavior underfoot: when a workspace is open, a note names it directly ("these snippets target whichever workspace poco currently has open — right now that's `<path>`"); when none is open, a note says so and points out the agent won't have anything to target until either a workspace is opened or `POCO_WORKSPACE` is set by hand (matching `resolveWorkspacePath`'s own thrown error text) — this replaces the old `noActiveWorkspaceNote`, which used to talk about a placeholder path in the snippet instead, now moot since the snippet no longer shows a path at all by default. A third, always-shown note explains `POCO_WORKSPACE` as the way to *pin* an agent to one workspace regardless of what's open in the app (or to run the MCP server without the app's window open at all), with the current (or placeholder) path spelled out as a copy-pasteable example value.
- New `settings.agentAccess.{activeWorkspaceNote,pinWorkspaceNote}` i18n keys in both `en.json`/`vi.json`; `noActiveWorkspaceNote`'s text changed in both (same key, so no structural diff).
- **Verified**: `npx tsc --noEmit` clean for `client/`; `npm run build -w client` clean; a throwaway key-diff script confirmed `en.json`/`vi.json` stayed structurally identical (218 leaf keys each, up from 216 — the two new keys). Reproduced all four snippet-builder outputs directly (a standalone script mirroring `SettingsPage.tsx`'s exact logic) for both the no-extra-env shape (dev/plain-node: no `env` key/line/flag at all, no stray commas or trailing spaces) and the AppImage shape (`DISPLAY`/`DBUS_SESSION_BUS_ADDRESS` still present, `POCO_WORKSPACE` absent from all three) — confirming the omit-when-empty logic renders cleanly in both directions, not just type-checks. Not re-verified in a live browser pass — rests on `tsc` correctness plus the same rendering pattern parts 4/15/20 already established for this section.

## Milestone 18 notes, part 20 (fix: packaged-AppImage MCP snippet disconnecting under Claude Desktop)

- User-reported bug: after switching their `claude_desktop_config.json` to point at the packaged AppImage (part 19's fix), Claude Desktop reported "server disconnected" rather than connecting. `command`/`args` were exactly what Settings' self-serve snippet (and part 19's own fix) generate, so the config itself wasn't wrong.
- **Root cause, confirmed by direct reproduction, not guessed from the error text**: launching the AppImage with `--poco-mcp-server` always boots Electron's native/Chromium layer first — that happens before `main.ts`'s own JS even gets to check `process.argv` for the flag, no matter how short-lived or window-less that particular invocation turns out to be (this is inherent to launching the binary normally, i.e. not under `ELECTRON_RUN_AS_NODE` — see part 19's own note on why that env mode can't be used here instead). That native init needs a real display/session-bus connection to complete; without one it doesn't just skip GUI setup and continue headless, it **segfaults outright** (`ui/ozone/platform/x11/ozone_platform_x11.cc: Missing X server or $DISPLAY` → `ui/aura/env.cc: The platform failed to initialize. Exiting.` → crash). The user's own `~/.config/Claude/logs/mcp-server-poco.log` showed exactly this — `dbus/bus.cc: Failed to connect to the bus` and the same X11/aura errors on every attempt since switching to the AppImage command, one of which crashed mid-`tools/list`, which is what surfaced as "server disconnected".
- Confirmed live, not assumed: ran the actual packaged AppImage with `--poco-mcp-server` and `DISPLAY`/`DBUS_SESSION_BUS_ADDRESS` present in its env → clean start, a real `initialize`/`notifications/initialized`/`tools/list` round trip all succeed with zero errors. Ran the identical command with those two vars stripped from the env (simulating what the user's `mcp-server-poco.log` implied Claude Desktop was actually doing) → immediate segfault, exit code 139. Claude Desktop on Linux evidently spawns configured MCP server commands with a stripped environment that drops both vars even though the desktop session the user is running Claude Desktop from has them set correctly (confirmed: `$DISPLAY`/`$DBUS_SESSION_BUS_ADDRESS` were both present and valid in the user's own shell at the time).
- **The fix**: `server/src/lib/mcpInfo.ts`'s `McpLaunchInfo` gained an optional `env?: Record<string, string>` — extra env vars (beyond `POCO_WORKSPACE`, which the client already adds itself from the active workspace) the generated command actually needs to start reliably. Only the `$APPIMAGE` branch populates it, via a new `appImageDisplayEnv()` helper that reads `DISPLAY`/`DBUS_SESSION_BUS_ADDRESS` off *this embedded server's own* `process.env` (it was launched by the real, currently-running Electron app, which by definition already has a working display session right now) and includes each only if actually present — so an all-Wayland session with no `$DISPLAY`, or one without a user dbus session, still generates a usable snippet rather than a literal `"undefined"` string baked into it. Every other shape (`.ts`/dev, plain compiled `.js`) is an ordinary Node process with nothing extra needed, so `env` stays `undefined` there, unchanged from before.
- **Client**: `api/client.ts`'s `getMcpInfo()` return type gained the matching optional `env`. `SettingsPage.tsx` now builds one `mcpEnv = { ...mcpExtraEnv, POCO_WORKSPACE: mcpWorkspacePath }` object and threads it through all three snippet builders (Claude Desktop JSON, Codex TOML, and the `claude mcp add` one-liner's `-e KEY=VALUE` flags, one per entry) instead of hardcoding just `POCO_WORKSPACE` in each — so a non-AppImage snippet (where `mcpExtraEnv` is `{}`) renders identically to before this fix, and only the AppImage case's snippet grows the two extra lines/flags.
- **Verified**: `npx tsc --noEmit` clean for all three packages; `npm run build -w client` clean; `npm test -w server` (110, up from 107 — `mcpInfo.test.ts` gained 3 cases: both vars set, only `DISPLAY` set, neither set). **Verified live**, in three layers: (1) the direct segfault reproduction and its fix described above, run against the real packaged AppImage, not a mock; (2) a full MCP stdio round trip (`initialize` → `notifications/initialized` → `tools/list`, driven by a real JSON-RPC client script) against the AppImage with the fix's env vars present, confirming `tools/list` actually returns the full tool schema rather than just "it didn't crash"; (3) started a real dev server with `APPIMAGE` faked and hit `GET /api/system/mcp-info` directly, confirming it returns `{"command":"...Poco.AppImage","args":["--poco-mcp-server"],"env":{"DISPLAY":":0","DBUS_SESSION_BUS_ADDRESS":"unix:path=/run/user/1000/bus"}}` — the exact live values from the running session, not placeholders. Did not re-verify the Settings UI's rendering in a live browser pass for this fix specifically — rests on `tsc` correctness plus the already-live-verified pattern from part 4/15's original snippet builders, which this only extends.

## Milestone 18 notes, part 19 (fix: MCP config changing on every AppImage restart)
- User-reported bug: the Claude Desktop config Settings generates for a packaged install (part 15's fix) still changed on every app restart — `command`/`args` pointed at `resources/server/dist/mcp/index.js` under whatever `/tmp/.mount_Poco<random>` directory that *particular* launch happened to be mounted at. Part 15 fixed the wrong *file extension*/*command*; it never addressed that the path itself is ephemeral for an AppImage specifically — every launch gets a fresh, randomly-named FUSE mount, so a config an MCP host saves once (most read theirs once at startup and reuse it) breaks the moment the app restarts and gets mounted somewhere else.
- **The fix**: `$APPIMAGE` — an env var the AppImage runtime itself sets, to the mounted `.AppImage` *file's own* path (not the ephemeral mount directory) — is stable across restarts; it's what the user actually placed on disk and doesn't move. `server/src/lib/mcpInfo.ts`'s `getMcpLaunchInfo` now checks `env.APPIMAGE` *first*, before even looking at the caller's own `.ts`/`.js` extension: when set, it returns `{ command: $APPIMAGE, args: ['--poco-mcp-server'] }` — pointing an MCP host at the AppImage itself, not at anything under `resourcesPath`, so nothing ephemeral is ever exposed to the saved config. (`$APPIMAGE` reaches this code for free — it's set on the Electron main process by the AppImage runtime, and `main.ts`'s `spawnServer` already spreads `...process.env` into the embedded server's child-process env, so the server process this route runs in sees it same as the parent.)
- **`electron/src/main.ts`** gained the other half: recognizing `--poco-mcp-server` in `process.argv` as an alternate entrypoint on the *same binary*, checked before even the single-instance lock (this is a separate, short-lived invocation an MCP host can spawn repeatedly and independently of whatever GUI session is or isn't already running — it must not be blocked by, or itself acquire, that lock). When present: no window, no tray, no reminder scheduler, no lock — just resolve *this specific launch's own, currently-valid* `resourcesPath` (fresh every time, but always correct *for this process*) and spawn the real `resources/server/dist/mcp/index.js` under `ELECTRON_RUN_AS_NODE=1` with `stdio: 'inherit'`, exiting with its exit code when it exits. The ephemeral path is still used — it just gets resolved fresh on every invocation from inside a live process, instead of being baked into a config file that outlives any single mount.
- **Simplified `McpLaunchInfo`'s own shape while fixing this**: dropped the separate `entryPath` field (client used to do `[...args, entryPath]`) in favor of `args` always being the complete, ready-to-use array — the AppImage case has no meaningful "entry path" at all (the command *is* the entrypoint), so a field that sometimes doesn't apply was more awkward than useful. `client/src/api/client.ts`/`SettingsPage.tsx` updated to match (`mcpArgs` used directly, no appending).
- **Verified**: `npx tsc --noEmit` clean for all three packages; `npm test -w server` (107, up from 106 — `mcpInfo.test.ts`'s cases rewritten for the new `{command, args}` shape plus two new ones covering `$APPIMAGE` set, including that it takes priority over the `.ts`/`.js` extension check). **Verified live**, in three separate layers since no single test could exercise the whole chain without a real display:
  1. Rebuilt the AppImage and ran the packaged embedded server directly (`ELECTRON_RUN_AS_NODE=1 ./poco resources/server/dist/index.js`, `APPIMAGE=/fake/Applications/Poco.AppImage` set to simulate what the real runtime would set) — confirmed `GET /api/system/mcp-info` now returns `{"command":"/fake/Applications/Poco.AppImage","args":["--poco-mcp-server"]}`, ignoring the actual (still-ephemeral in this test) `resourcesPath` entirely.
  2. Isolated the exact spawn/stdio-forward/exit-propagation logic `main.ts`'s new branch uses (same `spawn(process.execPath, [mcpEntry], {env: {...ELECTRON_RUN_AS_NODE:'1'}, stdio:'inherit'})` shape) into a standalone script pointed at the real packaged `resources/server/dist/mcp/index.js`, ran it, and confirmed the MCP server started correctly and the wrapper exited with the right code once stdin closed (simulating the host disconnecting).
  3. **Could not verify the real end-to-end path** — actually running `<the built AppImage> --poco-mcp-server` — because doing so still requires Electron's own native GUI bootstrap to reach the point where this app's own JS branch-check even runs (confirmed: it segfaults on `ozone_platform_x11.cc: Missing X server` in this sandbox, same failure as trying to launch the GUI at all, since there's no way to skip Electron's native init and still have this same binary auto-load its packaged `main` entry — `ELECTRON_RUN_AS_NODE=1` looked like an escape hatch but isn't: tested directly, and requiring `'electron'` from the packaged `main.js` under that env throws `MODULE_NOT_FOUND` outright, and even if it didn't, node-mode Electron needs an explicit script path as its argument rather than auto-loading the packaged app's own entry, which isn't available for an external host to supply). This isn't a new limitation introduced here, though: Poco already requires a display to run *at all* as a GUI app, so a user without one couldn't use the AppImage-packaged MCP integration regardless — anyone running an MCP host that could plausibly spawn this command is, by construction, on a machine with a display already. Layers 1+2 above cover everything that's actually new logic; the remaining gap is exactly the same "no `$DISPLAY` in this sandbox" limitation every GUI-touching part of this milestone has already hit.

## Milestone 18 notes, part 18 ("Add to applications menu" toggle on Settings)
- Direct follow-up to part 17's icon investigation: an AppImage is a single portable file that never registers itself with the desktop environment on its own (a known AppImage rough edge, not something part 17's icon/WM_CLASS fixes touched) — so even with the icon and WM_CLASS both correct, the app still never showed up in an actual application menu/launcher unless the user manually created a `.desktop` entry themselves. User asked for a Settings option to do that.
- **New `electron/src/desktopEntry.ts`**, self-contained (no Electron `app`/`BrowserWindow` API — plain `node:fs`/`os`/`path`/`child_process` only, mirroring `loginItem.ts`'s style): `canCreateDesktopEntry()` is `true` only when `process.platform === 'linux'` **and** `process.env.APPIMAGE` is set — that env var is set by the AppImage runtime itself, to the mounted `.AppImage` file's own current absolute path, on every launch. It's the only way to know what to point a desktop entry's `Exec=` at (there's no fixed install location to hardcode — the user can rename/move the file freely), and it's naturally unavailable in dev or on macOS/Windows (which get a real Start Menu/Dock entry from their own native installer instead, not something this app needs to build itself).
  - `createDesktopEntry(iconSourcePath)` writes `~/.local/share/applications/poco.desktop` (`Exec=` quoted only when the AppImage path needs it — spaces etc. — same rule electron-builder's own generated entries use, confirmed against part 17's investigation) and copies the given icon to the standard `~/.local/share/icons/hicolor/512x512/apps/poco.png` location, then best-effort runs `update-desktop-database`/`gtk-update-icon-cache` (silently ignored if not installed — most desktop environments notice the new files on their own via inotify anyway).
  - **Deliberately does *not* hardcode `--no-sandbox`** in the generated `Exec=`, unlike the AppImage's own *internal* bundled `.desktop` entry (which does, unconditionally) — traced through `app-builder-lib`'s actual AppRun-generation source (`appImageUtil.js`) to confirm: launching the `.AppImage` file directly (which is what our `Exec=` does, as opposed to an already-extracted `AppRun`) re-triggers the AppImage runtime's own smarter startup, which probes (`unshare -Ur true`) whether it actually needs that flag and adds it itself only if so. Hardcoding it would have been copying the wrong entry's behavior.
  - `removeDesktopEntry()` deletes both files (`fs.rmSync(..., {force: true})` — a no-op, not an error, if already gone, so toggling off twice behaves the same as once).
- **`main.ts`** gained three IPC handlers (`poco:can-create-desktop-entry`, `poco:is-desktop-entry-installed`, `poco:set-desktop-entry-installed`) alongside the existing launch-at-login ones, reusing the exact same icon path (`appIconPath`, hoisted to a shared const — previously computed inline in `createWindow` alone) as both the `BrowserWindow`'s own icon and the source `createDesktopEntry` copies from, so there's one icon reference, not two. `preload.ts`/`client/src/lib/pocoBridge.ts` both gained the matching three-method bridge surface (hand-duplicated between the two, same reasoning as every other bridge method in this codebase — separate npm workspaces/tsconfigs).

Reflects and toggles the real on-disk state (`isDesktopEntryInstalled`/`setDesktopEntryInstalled`), same optimistic-update-then-revert-on-failure pattern as `commitLaunchAtLogin`. New `settings.desktopEntry.{label,saveFailed}` i18n keys in both `en.json`/`vi.json`.
- **Verified live end-to-end without needing a real display** — unlike the GUI-touching parts (16/17), this module never imports `electron` at all, so it's plain testable Node code: ran the *actual compiled* `electron/dist/desktopEntry.js` directly with `node -e`, `APPIMAGE`/`HOME` env vars pointed at scratch paths (never the real `~/.local/share`), and confirmed: `canCreateDesktopEntry()` correctly `false` with `APPIMAGE` unset (and `createDesktopEntry` throwing, not silently no-op-ing, per its own guard) and `true` with it set; the written `.desktop` file's exact contents (unquoted `Exec=` for a plain path, quoted for one containing spaces); the copied icon byte-identical (`md5sum`) to `electron/src/assets/icon.png`; `isDesktopEntryInstalled()` flipping `false`→`true`→`false` across create/remove; and removing twice in a row not throwing. Not verified against a real taskbar/dock (same no-`$DISPLAY` limitation as parts 14/16) — this rests on `app-builder-lib`'s own source confirming exactly what `desktopName`/`syncDesktopName` do, not on guessing from the warning text a second time.

## Milestone 18 notes, part 16 (single-instance lock)
- User-requested, prompted directly by having just built the AppImage (part 14): nothing stopped double-clicking it (or a Start Menu/Dock icon, or launch-at-login racing a manual launch) from spawning a second full copy of the process — its own embedded Express server on its own free port, its own tray icon, its own reminder scheduler, and — worst case — two processes racing to `git commit` to the same workspace at once.
- **`electron/src/main.ts` gained `app.requestSingleInstanceLock()`**, called as the very first thing after the module's top-level consts/lets (before any `ipcMain.handle`, before `app.whenReady`) — Electron's own documented pattern for this, and it must run this early for Electron to correctly arbitrate which process wins the lock. Returns `false` on the second (or third, ...) launch attempt, in which case that process calls `app.quit()` immediately and does nothing else — no server spawned, no window created, nothing to clean up. Everything that used to run unconditionally at the bottom of the file (every `ipcMain.handle`, `app.whenReady().then(...)`, `window-all-closed`/`activate`/`will-quit`) is now nested inside the `else` (lock-acquired) branch instead, specifically so none of it can run for a doomed second instance — gating only window creation (the more commonly-seen version of this pattern) would still have let a second instance spawn its own server process first.
- **The winning instance's `second-instance` event** (fired on *it*, not the losing process, per Electron's own design) calls the same `showMainWindow()` the tray's "Open" action already used — so a second launch attempt reads as "oh, it was already open" (window un-minimized and focused) rather than silently doing nothing, which would look like the click didn't register at all.
- No new preference/config surface — this isn't something a user would ever want to turn off (two copies of the same app fighting over one workspace's files has no legitimate use case here, unlike e.g. launch-at-login), so it's unconditional or existing constants, no new state in `~/.poco/config.json`.
- **Verified**: `npx tsc --noEmit` clean for `electron/`; `npm run build -w electron` clean. **Not verified live against a real second-launch attempt** — this sandbox has no `$DISPLAY`/`Xvfb`, and confirmed (again, as in part 14) that Electron's own native init crashes before any of this file's JS runs at all without one (`ozone_platform_x11.cc: Missing X server or $DISPLAY` → immediate exit), independent of `ELECTRON_RUN_AS_NODE` — that env var bypasses `app`/window creation entirely (used for the embedded *server* subprocess, a plain Node script that never touches the `electron` module's real API), so it can't be used to exercise `app.requestSingleInstanceLock()` either. This rests on `requestSingleInstanceLock`/`second-instance` being a stable, standard Electron API (documented since early Electron 5, unchanged since) used here in Electron's own textbook shape, plus a structural read of the diff confirming nothing that spawns a server/window/tray can execute before the lock check. A user building and running the real AppImage on their own machine (double-click it twice) is the natural way to confirm this live.

## Milestone 18 notes, part 15 (fix MCP self-serve config for a packaged install)
- Direct follow-up to the bug part 14 found but deliberately didn't fix inline: `GET /api/system/mcp-info` always resolved a `.ts` entrypoint path, and Settings' Claude Desktop/Codex/Claude Code snippets always hardcoded `npx tsx <path>` — both wrong for a packaged install, which ships only `resources/server/dist/mcp/index.js` (no `.ts` source, no `tsx` devDependency).
- **New `server/src/lib/mcpInfo.ts`**, `getMcpLaunchInfo(callerModuleUrl)`: takes a module URL (the route passes its own `import.meta.url`) and returns `{ entryPath, command, args }`. The key realization: `mcp/index.ts`/`mcp/index.js` is emitted (or not) by the exact same `tsc` compile step as `routes/system.ts` itself, so "does *this* file's own URL end in `.ts` or `.js`" is a reliable, zero-fs-check stand-in for "is the sibling MCP entrypoint source or compiled" — no need to separately detect "packaged vs. dev" as its own concept. `.ts` → `{ command: 'npx', args: ['tsx'] }` (unchanged dev behavior); `.js` → `{ command: 'node', args: [] }` (covers both a plain `node dist/index.js` production run and the Electron-packaged app identically — packaging isn't actually a distinct case here, "compiled" is the only thing that matters). Pulled out of `routes/system.ts` into `lib/` specifically so it's unit-testable against fabricated `.ts`/`.js` URLs without needing two real builds (matches this codebase's existing "route stays thin, `lib`/`services` hold the logic" pattern, e.g. `lib/vaultGit.ts`'s `isGitAvailable`).
- **`routes/system.ts`** now just calls `getMcpLaunchInfo(import.meta.url)` and returns it directly — same "resolved from this module's own location, not `process.cwd()`" property it always had, just extension-aware now.

## Milestone 18 notes, part 7 (task checklist / sub-tasks)
- User-requested feature, not previously in PLAN.md — confirmed three design questions with the user up front (CLAUDE.md: check before introducing a new grammar/convention) rather than guessing: on-disk shape, whether progress shows on the row/card, and MCP exposure. PLAN.md's Storage format and Routes sections were updated to document this as part of the design, not just the code (per CLAUDE.md).
- **Grammar** (`server/src/lib/markdown/taskLine.ts`): a checklist item is a plain `  - [ ] text` / `  - [x] text` line, one 2-space indent level beneath the task's own checkbox line — deliberately lighter than a full task line (no `@due`/`#tag`/`<!-- id -->`/time-tracking; `CHECKLIST_ITEM_RE` only accepts `[ ]`/`[x]`, no `[/]` doing). Checklist lines, if present, come immediately after the checkbox line and before the free-text description, with **no blank line separating the two sections** — matching the existing checkbox-line-to-description precedent (no blank line there either) and, more importantly, required for correct round-tripping: `parseProjectBody`'s checklist loop stops at the first indented line that isn't checkbox-shaped, so the description loop picks up exactly where it left off; a blank separator would instead round-trip into the description as a spurious leading blank line. Fully backward compatible — a task with no checklist lines parses to `checklist: []`, exercised by a dedicated test.
- **Types**: new `ChecklistItem { text: string; done: boolean }` in both `server/src/types.ts` and its hand-mirrored `client/src/types.ts`; `Task.checklist: ChecklistItem[]` is a required (never-undefined) field everywhere a `Task` is constructed.
- **Service layer** (`server/src/services/tasks.ts`): `checklist` is a full-array-replace field on both `CreateTaskInput` and `UpdateTaskInput` — same convention already established for `tags`, not an index-addressed add/toggle/remove tool per operation (the caller already has the current array from whatever `get`/`search` call preceded the mutation). Reused end-to-end by both front doors: `PATCH /api/projects/:slug/tasks/:taskId` (`server/src/routes/tasks.ts`) and the `create_task`/`update_task` MCP tools (`server/src/mcp/tools.ts`, `CHECKLIST_ITEM` zod schema), per CLAUDE.md "both the REST routes and the MCP tools must call these same functions."
- **SQLite index** (`lib/index/{db,reindex,queries}.ts`): `tasks.checklist` new column, JSON-serialized like `tags`, included in `TASK_JOIN_SELECT`/`mapTaskRow` so every aggregate read (`listOpenTasks`, `searchTasks`, `getTaskSummary`, the Dashboard buckets) carries it too — not just single-project/journal reads. Since `CREATE TABLE IF NOT EXISTS` is a no-op against an already-existing `tasks` table, `openIndexDb` also runs a one-time `ALTER TABLE tasks ADD COLUMN checklist TEXT NOT NULL DEFAULT '[]'` wrapped in try/catch (swallowing the "duplicate column" error on every subsequent open) — the first schema migration this index has needed; existing workspaces (the user's own `~/pivot-demo` included) pick it up on next open with no explicit `/api/index/rebuild` required. Covered by a dedicated test that hand-creates a pre-migration `tasks` table, confirms `openIndexDb` heals it, and that a second open is a no-op.
- **UI**: new `client/src/components/ChecklistEditor.tsx` (add/edit-text/toggle/remove, same full-array-`onChange` convention as `TagInput`) wired into `TaskForm` between Tags and Description (matching on-disk order). `TaskRow` shows a `checklist-badge` ("done/total") next to the due/tag badges whenever a task has checklist items, and — expanding the row now also triggers on checklist items alone, not just a description — renders the items as directly-clickable checkboxes in the expanded view (`toggleChecklistItem` sends the whole updated array through the existing `onSave`, no new mutation path). Checklist item text intentionally has no strikethrough when checked (muted color only), matching this same session's earlier "no strikethrough on done tasks" preference for consistency.

## Milestone 18 notes, part 3 (auto-refresh after an out-of-band vault change)
- User-reported gap, not in PLAN.md's original milestone-18 scope: an already-open UI never picked up a change made outside its own mutations — most concretely, an MCP agent writing to the same workspace from a separate process (per PLAN.md's own "MCP is decoupled from whichever workspace the app has open" — a real, separate process, not something the running Express server hears about in-process). `main.tsx`'s query defaults (`staleTime: 10_000`, `refetchOnWindowFocus: false`) were deliberate for the reasons stated there, but neither refetches on its own, so nothing closed this gap by accident.
- **Mechanism decided with the user up front** (CLAUDE.md: check before introducing a new convention) — presented as a choice between filesystem-watching + push (SSE), a plain polling interval on existing queries, and polling a cheap "did anything change" signal; the user picked the third: **poll the workspace's git HEAD commit hash**. Every write, from either front door, is already a commit (PLAN.md "Backup & recovery"), so a changed HEAD is a reliable, cheap-to-compute signal that something external touched the vault — no new dependency (chokidar/ws), no watcher-lifecycle-across-workspace-switches complexity.
- **`lib/vaultGit.ts` gained `getHeadCommit(workspacePath)`** (`git rev-parse HEAD`, `null` for a repo with no commits yet) and a new `GET /api/vault/head` route (`routes/vault.ts`) wrapping it.
- **`client/src/components/VaultChangePoller.tsx`** (new, renders nothing, mounted once in `AppShell` alongside `WorkspaceSwitcher`/`CalendarSidebar`): polls `/api/vault/head` every 4s (`staleTime: 0` on that one query — it must never answer from cache) and, when the hash differs from the last one seen, calls `queryClient.invalidateQueries()` with no key — the same "something changed, re-fetch everything" pattern `WorkspaceSwitcher` already uses for a workspace switch, cheap enough against a personal local vault not to bother picking specific query keys. The very first resolved hash is only recorded, never treated as a change (a `useRef` starting at `undefined`, distinct from a real `null`/hash value).
- **Verified**: `npm test -w server` (93 tests, up from 92 — one new case in `vaultGit.test.ts` covering `null` → hash → next-hash across commits); `npx tsc --noEmit` clean for `server/` and `client/`. **Verified live end-to-end**, but in an isolated scratch sandbox rather than against the user's own running dev session (its Express server is spawned once by Electron via plain `tsx`, not `tsx watch`, so it wouldn't have had the new route until restarted, and killing/restarting a session the user might have open wasn't this session's call to make without asking): a scratch `$HOME` (isolated `~/.pivot/config.json`) and a throwaway workspace, driving a genuinely separate MCP server process (`server/src/mcp/index.ts` via a real stdio client, mirroring milestone 10's own verification style) to call `create_task` — confirmed the already-running (third, independent) Express server's `/api/vault/head` picked up the new hash immediately, tagged `[mcp:create_task]` in `git log`. The user then restarted their own dev session, moved a task todo→doing via a live MCP tool call in this same conversation against their real `Pivot Demo` workspace, and confirmed the open UI updated on its own — real end-to-end confirmation, not just the isolated sandbox test.
