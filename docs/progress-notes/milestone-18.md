## Milestone 18 notes, part 33 (fix: find input rendered "#" offset/clipped)

- User-reported, with a screenshot: typing `#` into the find input showed it visibly offset from the left edge with extra surrounding space, looking cut off/hard to see — described as "auto indented and hidden."
- **Root cause**: `.find-panel { font-family: inherit }` (part 32) inherited from its actual DOM parent — the editor itself (`.journal-body`), which sets `font-family: 'JetBrains Mono'` *and* `line-height: 1.75` for full lines of prose/code. A line-height that much taller than the font-size doesn't reconcile cleanly with a plain `<input>`'s own internal single-line text box across browsers, which showed up as the query text rendering visibly off-center/offset within the field — confirmed live by temporarily zooming just the `<input>` element (`element.style.zoom`, scoped to it alone so the rest of the page layout/scroll stayed put) and outlining its real bounding box: the glyph sat noticeably away from center, in a box far taller (~32px) than a single line of 12.5px text needs.
- **Fix**: gave `.find-panel` its own explicit `font-family` (the app's actual UI font stack, `'Manrope', -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif` — the same one every other input in the app already renders with, e.g. `TagInput`, the note title field) and `line-height: normal`, instead of inheriting the editor's prose-sized values. This was also a pre-existing inconsistency worth fixing on its own terms: the find panel is app chrome, not document content, and was the only input in the whole app rendering in the code font. Not a hunt for a "clever" fix — the general lesson (this app's own `.md-editor .cm-placeholder`/`.cm-selectionBackground` comments already document related instances) is that inheriting an editor's *content* typography into a UI *control* sitting on top of it doesn't reliably hold up.
- **Verified**: `npx tsc --noEmit` clean for `client/` (CSS-only change). **Verified live**: reproduced the exact bug first (zoomed the real `<input>` in place, confirmed the oversized ~32px box and off-center glyph, and confirmed via `getComputedStyle` that `line-height` was `21.875px`/`font-family` was JetBrains Mono before the fix), then confirmed after — box height dropped to ~24px, `font-family` reads `Manrope, ...`, `line-height: normal`, and the same zoomed-in-place inspection showed the `#` centered cleanly with balanced padding on all sides; also re-checked the replace row and the `Aa`/`ab`/`.*` toggle buttons (same panel, same font change) still render correctly.

## Milestone 18 notes, part 32 (VS Code-style find/replace panel)

- User request: "use icons and collapsible replace inputs like in vscode." `@codemirror/search`'s default `SearchPanel` has a fixed DOM (a flat row of text buttons — "next"/"previous"/"all"/"replace"/"replace all" — plus labeled checkboxes, and the replace fields always visible) that can't be reshaped into that layout with CSS alone; the fix needed a different panel, not different styling.
- **New `client/src/lib/vscodeSearchPanel.ts`** (`VscodeSearchPanel`, plain DOM — no JSX, matching how the rest of `MarkdownEditor.tsx` already builds CodeMirror's own DOM) plugs in via `search()`'s `createPanel` option — an undocumented-in-prose but real, stable part of its config facet (`search({ top: true, createPanel: (view) => new VscodeSearchPanel(view) })`, `MarkdownEditor.tsx`). Implements the same `Panel` interface (`dom`/`mount`/`update`/`top`) the default one does, and reuses 100% of `@codemirror/search`'s own query/command machinery (`SearchQuery`, `setSearchQuery`, `getSearchQuery`, `findNext`/`findPrevious`, `replaceNext`/`replaceAll`, `closeSearchPanel`) — only the DOM and the glue around it are new, so none of the underlying search behavior (or the existing `--find-match-bg` highlight theming from part 31) needed to change.
- **Layout**: a single search row (chevron toggle · find input · a live "n of m" match-count readout · `Aa`/`ab`/`.*` icon-style toggle buttons for case/whole-word/regex · previous/next chevrons · a close ×), with the replace row (input + replace/replace-all icons, indented to align under the search input via a same-width spacer) collapsed behind that chevron by default — same interaction VS Code's own find widget uses, expand on click, focuses the replace field on open. `Aa`/`ab`/`.*` are plain styled text (small square toggle buttons, `ab` underlined) rather than abstract icon glyphs, since that's literally what VS Code's own find widget uses for these three specifically — not a simplification, a faithful match.
- **Match count has no built-in equivalent to ask `@codemirror/search` for** — `countMatches()` is a plain full-document cursor scan (`query.getCursor(view.state)`, iterating `.next()` until `.done`), the same cost `selectMatches`/`replaceAll` already pay internally for the same job; recomputed on every relevant `update()` (doc change, selection change, or a query change), acceptable for this app's personal-note/journal-sized documents.
- **A real bug caught during live verification, not assumed away**: the replace row's `hidden` attribute was being silently overridden — `.find-row { display: flex }` (an author-stylesheet rule, same specificity tier as `[hidden]`'s own UA-stylesheet `display: none`) simply came later/won, so the "collapsed" replace row rendered anyway despite `hidden === true` in the DOM. Fixed with an explicit `.find-row[hidden] { display: none }`, higher-specificity than the plain class rule. Caught by literally checking `getComputedStyle(...).display` against the `.hidden` property after the first "why is this still showing" screenshot, not by inspection alone.
- **A second false alarm, correctly ruled out rather than "fixed" blind**: the match-count readout stayed stuck on `? of N` after pressing Enter in the find field during live testing, even after adding an `e.keyCode === 13` fallback (matching what the default `SearchPanel` this replaces already does, for the same reason). Root cause, confirmed by temporarily logging the raw event: this environment's browser-automation tool, when asked to press "Return", dispatches a keydown with `key: ""`/`keyCode: 0`/`which: 0` — no usable identifying data at all — while asking for "Enter" (the DOM-standard name, which is what a real physical Enter/Return key always reports as `event.key` in every real browser) produced a correct `key: "Enter"` and worked immediately. Reverted the `keyCode` fallback once this was confirmed as a test-tool naming quirk, not a real gap — `e.key === 'Enter'` alone is correct and is what the rest of this app's own keyboard-shortcut code (`KeyboardShortcuts.tsx`) already uses.

## Milestone 18 notes, part 31 (fix: find highlight could hide the matched text)

- User-reported, with a screenshot: searching a heading like "## IPs" highlighted "IPs" in a solid box with no visible text at all. Root cause: part 29's `.cm-searchMatch-selected` rule set both `background: var(--accent)` and `color: var(--accent-contrast)` (white), expecting the white text to override whatever the matched text's own color was — but a heading's text isn't plain: it's syntax-highlighted (`--md-heading = var(--accent)`, i.e. the *same* green) via its own nested `<span>` with an explicit `color` rule from `syntaxHighlighting()`. CSS inheritance can't be beaten by a parent's `!important`: an element's *own* explicit color rule (even a weak one) always wins over an inherited value from an ancestor, `!important` or not — `!important` only settles conflicts between rules that both target the *same* element. So the heading span kept its own green text, now sitting on a solid green (`--accent`) highlight background — same color as itself, effectively invisible. Confirmed by reproducing live (typed a scratch `## IPs` heading + code fence into an existing note, searched "IPs") and inspecting the actual DOM: the matched text's own nested span (`ͼo`-classed, wherever `@lezer/markdown`'s recursive heading tag lands) still carried `--md-heading`'s green, untouched by the parent match span's `color` override.
- **Fix, not a workaround**: stopped trying to force text color at all — instead gave `.cm-searchMatch`/`.cm-searchMatch-selected` their own dedicated, *translucent* background tokens (`--find-match-bg`/`--find-match-selected-bg`, new, warm yellow/orange, fixed hue independent of `--accent-hue` and every `--md-*` token) instead of reusing `--accent-soft`/`--accent`. Two deliberate choices, both following precedent already in this file: (1) a **fixed hue distinct from the app's own accent-family colors** (same reasoning `--md-code`'s comment already gives for itself — "so it stays visually distinct from links/headings regardless of accent palette") specifically so a match highlight can never again coincide with a heading/link's own `--accent` text color; (2) **translucent, not opaque** — the exact same fix `--md-code-bg`'s own comment already documents for a different bug (an opaque code-block background hiding the selection-highlight layer underneath it) — letting whatever text color sits under the highlight show through, tinted, rather than betting on a `color` override that CSS inheritance rules out from working in the first place.
- **Verified**: `npx tsc --noEmit` clean for `client/` (CSS-only change, no source edits needed beyond the token/rule update). **Verified live**: reproduced the exact bug first (scratch `## IPs` heading, confirmed via DOM inspection the matched span's `color` came from its own nested syntax-highlight span, untouched by the parent match span), then confirmed the fix — the same heading's "IPs" now renders clearly legible (green heading text on a warm-yellow highlight, warm-orange for the current/selected match), re-checked a match inside a plain-text line and inside a link (both still fully legible, no regression), then reverted the scratch edit directly via `PATCH /api/notes/misc` (the UI's own flush-on-unmount hadn't actually landed the delete before a same-session re-fetch showed stale content — a real gap worth another look sometime, but out of scope here since it's pre-existing autosave behavior, not something this change touched) — confirmed via a fresh `GET /api/notes/misc` that the user's actual "Misc." note is back to its exact original content.

## Milestone 18 notes, part 30 (fix: find didn't work unfocused or in Preview)

- Direct same-session follow-up, user-reported: "it doesn't work when the editor is not focus or in preview mode." Both real gaps in part 29's approach of relying on `MarkdownEditor`'s own `searchKeymap` binding alone: that binding is attached to the CodeMirror view's own DOM and only fires while *that view* has focus (nothing catches the key if focus is on, say, the tag input, or nowhere in particular), and Preview mode unmounts `MarkdownEditor` entirely (`NoteBodyEditor`/`JournalDayPage` swap it for a rendered-HTML `<div>`), so there's no CodeMirror view at all to bind to.
- **`MarkdownEditor` gained an imperative handle** (`forwardRef` + `useImperativeHandle`, new exported `MarkdownEditorHandle` interface with one method, `openFind()`: focuses the view then calls `@codemirror/search`'s `openSearchPanel(view)` directly, rather than depending on a keymap match) — the first ref/imperative-API surface this component has needed; every previous prop (`autoFocus` included) was declarative.
- **New `client/src/lib/useFindShortcut.ts`**, one shared hook used by both `NoteBodyEditor` and `JournalDayPage` (the only two places with an edit/preview toggle over a `MarkdownEditor`): a page-scoped `window` keydown listener (removed on unmount, same lifetime as any other per-page shortcut in this app) that, on Cmd/Ctrl+F, switches `viewMode` to `'edit'` first if it wasn't already, then calls the ref's `openFind()`.
- **A real timing bug on the Preview→Edit path, caught live rather than assumed fixed**: calling `openFind()` synchronously in the effect that reacts to the mode switch silently did nothing — confirmed via the DOM (`viewMode` flipped to `'edit'`, `.cm-editor` mounted, but no `.cm-search` panel ever appeared). Root cause: React StrictMode (dev only) deliberately double-invokes a freshly-mounted component's effects — mount, synthetic unmount, remount — to catch impure effects; `MarkdownEditor`'s own creation effect destroys its `EditorView` on that synthetic unmount (`view.destroy(); viewRef.current = null`), so at the exact moment the parent's passive effect ran (same commit's effect flush), the child was momentarily mid-dance with `viewRef.current` back to `null` — `openFind` correctly no-ops on a null view, so the call just silently did nothing. Fixed by deferring that call one tick via `setTimeout(..., 0)`, which fires after StrictMode's synchronous double-invoke has settled and the view is the real, stable instance (cleared on effect cleanup, so a fast unmount/remount can't leave a stale timer calling into a torn-down ref).
- **Verified**: `npx tsc --noEmit` clean for `client/`. **Verified live**, both regressions specifically: (1) clicked the tag input (confirmed via `document.activeElement` it had focus, not the editor) on an existing note already in Edit mode, pressed Ctrl+F — panel opened correctly; (2) switched a note to Preview (confirmed `.cm-editor` count was 0), pressed Ctrl+F — view switched back to Edit and the panel opened with focus already in the Find field, confirmed via `document.activeElement.classList.contains('cm-textfield')`; repeated both checks on a real journal entry (a past day, which defaults to Preview) with the same result. No lasting changes to the user's real vault content — search doesn't modify the document, so nothing needed cleanup this time.

## Milestone 18 notes, part 25 (fix: excessive line spacing in the task description preview)

- User-reported, with a screenshot of the view modal (part 23/24): a task description rendered as markdown had huge gaps between the intro paragraph and a bullet list, and between the list items themselves — visibly more than the `.note-preview` typography's own margins (`p`: 14px, `li`: 4px) would produce.
- **Root cause, confirmed by inspecting the live DOM/computed styles, not guessed**: `.task-desc` still carried `white-space: pre-line` from when it displayed the description as raw text (pre-milestone-18-part-22, before descriptions were rendered as HTML). `markdown-it`'s output has literal `\n` text nodes between sibling block tags (`<p>...</p>\n<ul>\n<li>...`) — normally insignificant whitespace that collapses to nothing, but `white-space: pre-line` (inherited from the `.task-desc` container down into every descendant, since it's an inherited CSS property) makes those newlines render as real line breaks, adding a full extra line-height between every block element on top of its own CSS margin. ## Milestone 18 notes, part 16 (single-instance lock)
- User-requested, prompted directly by having just built the AppImage (part 14): nothing stopped double-clicking it (or a Start Menu/Dock icon, or launch-at-login racing a manual launch) from spawning a second full copy of the process — its own embedded Express server on its own free port, its own tray icon, its own reminder scheduler, and — worst case — two processes racing to `git commit` to the same workspace at once.
- **`electron/src/main.ts` gained `app.requestSingleInstanceLock()`**, called as the very first thing after the module's top-level consts/lets (before any `ipcMain.handle`, before `app.whenReady`) — Electron's own documented pattern for this, and it must run this early for Electron to correctly arbitrate which process wins the lock. Returns `false` on the second (or third, ...) launch attempt, in which case that process calls `app.quit()` immediately and does nothing else — no server spawned, no window created, nothing to clean up. Everything that used to run unconditionally at the bottom of the file (every `ipcMain.handle`, `app.whenReady().then(...)`, `window-all-closed`/`activate`/`will-quit`) is now nested inside the `else` (lock-acquired) branch instead, specifically so none of it can run for a doomed second instance — gating only window creation (the more commonly-seen version of this pattern) would still have let a second instance spawn its own server process first.
- **The winning instance's `second-instance` event** (fired on *it*, not the losing process, per Electron's own design) calls the same `showMainWindow()` the tray's "Open" action already used — so a second launch attempt reads as "oh, it was already open" (window un-minimized and focused) rather than silently doing nothing, which would look like the click didn't register at all.
- No new preference/config surface — this isn't something a user would ever want to turn off (two copies of the same app fighting over one workspace's files has no legitimate use case here, unlike e.g. launch-at-login), so it's unconditional or existing constants, no new state in `~/.poco/config.json`.
- **Verified**: `npx tsc --noEmit` clean for `electron/`; `npm run build -w electron` clean. **Not verified live against a real second-launch attempt** — this sandbox has no `$DISPLAY`/`Xvfb`, and confirmed (again, as in part 14) that Electron's own native init crashes before any of this file's JS runs at all without one (`ozone_platform_x11.cc: Missing X server or $DISPLAY` → immediate exit), independent of `ELECTRON_RUN_AS_NODE` — that env var bypasses `app`/window creation entirely (used for the embedded *server* subprocess, a plain Node script that never touches the `electron` module's real API), so it can't be used to exercise `app.requestSingleInstanceLock()` either. This rests on `requestSingleInstanceLock`/`second-instance` being a stable, standard Electron API (documented since early Electron 5, unchanged since) used here in Electron's own textbook shape, plus a structural read of the diff confirming nothing that spawns a server/window/tray can execute before the lock check. A user building and running the real AppImage on their own machine (double-click it twice) is the natural way to confirm this live.

- **Grammar** (`server/src/lib/markdown/taskLine.ts`): a checklist item is a plain `  - [ ] text` / `  - [x] text` line, one 2-space indent level beneath the task's own checkbox line — deliberately lighter than a full task line (no `@due`/`#tag`/`<!-- id -->`/time-tracking; `CHECKLIST_ITEM_RE` only accepts `[ ]`/`[x]`, no `[/]` doing). Checklist lines, if present, come immediately after the checkbox line and before the free-text description, with **no blank line separating the two sections** — matching the existing checkbox-line-to-description precedent (no blank line there either) and, more importantly, required for correct round-tripping: `parseProjectBody`'s checklist loop stops at the first indented line that isn't checkbox-shaped, so the description loop picks up exactly where it left off; a blank separator would instead round-trip into the description as a spurious leading blank line. Fully backward compatible — a task with no checklist lines parses to `checklist: []`, exercised by a dedicated test.
- **Types**: new `ChecklistItem { text: string; done: boolean }` in both `server/src/types.ts` and its hand-mirrored `client/src/types.ts`; `Task.checklist: ChecklistItem[]` is a required (never-undefined) field everywhere a `Task` is constructed.
- **Service layer** (`server/src/services/tasks.ts`): `checklist` is a full-array-replace field on both `CreateTaskInput` and `UpdateTaskInput` — same convention already established for `tags`, not an index-addressed add/toggle/remove tool per operation (the caller already has the current array from whatever `get`/`search` call preceded the mutation). Reused end-to-end by both front doors: `PATCH /api/projects/:slug/tasks/:taskId` (`server/src/routes/tasks.ts`) and the `create_task`/`update_task` MCP tools (`server/src/mcp/tools.ts`, `CHECKLIST_ITEM` zod schema), per CLAUDE.md "both the REST routes and the MCP tools must call these same functions."
- **SQLite index** (`lib/index/{db,reindex,queries}.ts`): `tasks.checklist` new column, JSON-serialized like `tags`, included in `TASK_JOIN_SELECT`/`mapTaskRow` so every aggregate read (`listOpenTasks`, `searchTasks`, `getTaskSummary`, the Dashboard buckets) carries it too — not just single-project/journal reads. Since `CREATE TABLE IF NOT EXISTS` is a no-op against an already-existing `tasks` table, `openIndexDb` also runs a one-time `ALTER TABLE tasks ADD COLUMN checklist TEXT NOT NULL DEFAULT '[]'` wrapped in try/catch (swallowing the "duplicate column" error on every subsequent open) — the first schema migration this index has needed; existing workspaces (the user's own `~/pivot-demo` included) pick it up on next open with no explicit `/api/index/rebuild` required. Covered by a dedicated test that hand-creates a pre-migration `tasks` table, confirms `openIndexDb` heals it, and that a second open is a no-op.
- **UI**: new `client/src/components/ChecklistEditor.tsx` (add/edit-text/toggle/remove, same full-array-`onChange` convention as `TagInput`) wired into `TaskForm` between Tags and Description (matching on-disk order). `TaskRow` shows a `checklist-badge` ("done/total") next to the due/tag badges whenever a task has checklist items, and — expanding the row now also triggers on checklist items alone, not just a description — renders the items as directly-clickable checkboxes in the expanded view (`toggleChecklistItem` sends the whole updated array through the existing `onSave`, no new mutation path). Checklist item text intentionally has no strikethrough when checked (muted color only), matching this same session's earlier "no strikethrough on done tasks" preference for consistency.

## Milestone 18 notes, part 3 (auto-refresh after an out-of-band vault change)
- User-reported gap, not in PLAN.md's original milestone-18 scope: an already-open UI never picked up a change made outside its own mutations — most concretely, an MCP agent writing to the same workspace from a separate process (per PLAN.md's own "MCP is decoupled from whichever workspace the app has open" — a real, separate process, not something the running Express server hears about in-process). `main.tsx`'s query defaults (`staleTime: 10_000`, `refetchOnWindowFocus: false`) were deliberate for the reasons stated there, but neither refetches on its own, so nothing closed this gap by accident.
- **Mechanism decided with the user up front** (CLAUDE.md: check before introducing a new convention) — presented as a choice between filesystem-watching + push (SSE), a plain polling interval on existing queries, and polling a cheap "did anything change" signal; the user picked the third: **poll the workspace's git HEAD commit hash**. Every write, from either front door, is already a commit (PLAN.md "Backup & recovery"), so a changed HEAD is a reliable, cheap-to-compute signal that something external touched the vault — no new dependency (chokidar/ws), no watcher-lifecycle-across-workspace-switches complexity.
- **`lib/vaultGit.ts` gained `getHeadCommit(workspacePath)`** (`git rev-parse HEAD`, `null` for a repo with no commits yet) and a new `GET /api/vault/head` route (`routes/vault.ts`) wrapping it.
- **`client/src/components/VaultChangePoller.tsx`** (new, renders nothing, mounted once in `AppShell` alongside `WorkspaceSwitcher`/`CalendarSidebar`): polls `/api/vault/head` every 4s (`staleTime: 0` on that one query — it must never answer from cache) and, when the hash differs from the last one seen, calls `queryClient.invalidateQueries()` with no key — the same "something changed, re-fetch everything" pattern `WorkspaceSwitcher` already uses for a workspace switch, cheap enough against a personal local vault not to bother picking specific query keys. The very first resolved hash is only recorded, never treated as a change (a `useRef` starting at `undefined`, distinct from a real `null`/hash value).
- **Verified**: `npm test -w server` (93 tests, up from 92 — one new case in `vaultGit.test.ts` covering `null` → hash → next-hash across commits); `npx tsc --noEmit` clean for `server/` and `client/`. **Verified live end-to-end**, but in an isolated scratch sandbox rather than against the user's own running dev session (its Express server is spawned once by Electron via plain `tsx`, not `tsx watch`, so it wouldn't have had the new route until restarted, and killing/restarting a session the user might have open wasn't this session's call to make without asking): a scratch `$HOME` (isolated `~/.pivot/config.json`) and a throwaway workspace, driving a genuinely separate MCP server process (`server/src/mcp/index.ts` via a real stdio client, mirroring milestone 10's own verification style) to call `create_task` — confirmed the already-running (third, independent) Express server's `/api/vault/head` picked up the new hash immediately, tagged `[mcp:create_task]` in `git log`.
