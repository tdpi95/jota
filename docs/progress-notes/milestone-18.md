## Milestone 18 notes (task drag-and-drop, project modal, custom color, tag filter)
- Started ahead of the rest of milestone 18's originally-scoped items (first-run/loading/error states, backup job, README, `electron-builder` config — still outstanding) at the user's request; PLAN.md's milestone-18 bullet, its Routes section, and its Frontend section were all updated to document these as part of the design, not just the code.
- **Task reordering has no dedicated field** — order is, and remains, purely the position of a task's block in `ParsedProjectFile.blocks` (`server/src/lib/markdown/project.ts`). `updateTask` (`server/src/services/tasks.ts`) gained an optional `afterTaskId?: string | null` on `UpdateTaskInput`: `undefined` (every pre-existing caller) leaves position untouched, `null` moves the block to the front of the file, a task id moves it to immediately after that task's block (404 if unknown, same style as the existing `findTaskBlock`). Reuses the existing `PATCH /api/projects/:slug/tasks/:taskId` route/service — no new endpoint, and not exposed via the MCP server (a UI-only affordance; agents don't need manual reordering). The commit-message logic was extended to note `reordered` alongside any `status a→b` note on the same line.
- **Drag-and-drop is native HTML5 DnD** (`draggable`/`dragstart`/`dragover`/`drop`), not a new dependency — this is a mouse-driven Electron desktop app, not touch, so no `dnd-kit`/`react-beautiful-dnd` was added. `ProjectDetailPage.tsx` wraps each `TaskRow` in a thin draggable `<div>` locally (not inside `TaskRow` itself, which `DashboardPage` also reuses across multiple projects and must stay non-draggable) and computes the drop position from pointer Y against sibling rows' `getBoundingClientRect()` via a `rowRefs` ref map. No optimistic local reordering — same invalidate-and-refetch pattern as every other mutation on the page; dropping across columns sends both `status` and `afterTaskId` in one `updateTask` call.
- **`Modal`** (`client/src/components/Modal.tsx`) is the first modal/dialog component in the app (there was no prior pattern to reuse) — a portal-rendered overlay+card, closable via Escape, backdrop click, or an explicit × button. `ProjectForm` gained a `bare` prop so it renders without its own `.form-panel` chrome when nested inside `Modal` (which already supplies the card). Both `ProjectsListPage` ("+ New project") and `ProjectDetailPage` ("Edit project") now open this modal instead of toggling an inline form — fixes the page-layout-shift the inline form caused.
- **Custom color**: one more control after the 12 `COLOR_PALETTE` swatches in `ProjectForm` — a native `<input type="color">` sized/styled (`::-webkit-color-swatch` override) like the other swatches, `.selected` whenever the current color isn't one of the 12 presets. The server never validated `color` against the palette, so a custom hex round-trips with zero server changes.
- **Tag filter** on `ProjectsListPage`: a `useState<string[]>` toggled by clicking tag pills (derived via `projects.flatMap(p => p.frontmatter.tags)`), **multi-select, OR-matched** (a project shows if it has *any* selected tag — narrowing to an AND match goes to zero results fast on a small, sparsely-tagged project list; OR keeps adding a filter widening rather than a likely dead end) with a "Clear" affordance once any are active, composed with the existing `showArchived` filter — same client-side-filter-the-fetched-array pattern as `showArchived`, no new query/endpoint.
- **Kanban drop-zone height fix**: each column's `.task-list` only grew to fit its own rows, so a short column (e.g. Doing with one task) had no droppable element at all in the vertical range where a much longer sibling column's (e.g. Done with fifteen) rows lived — dropping there hit blank page background, not a `drop` handler. Fixed by having `.pd-columns` stretch every column to the tallest one's height (grid's `align-items: stretch`, the default, in place of `start`) and `.task-list` grow (`flex: 1`) to fill it, so the empty space below a short column's last row is now real, droppable (and highlighted) area. Confirmed `flex: 1` is a no-op on `DashboardPage`'s reuse of `.task-list` (its parent isn't a flex container there).
- **"← All projects" back-link** on `ProjectDetailPage`, and the task quick-add (`TaskForm compact`) moved above the Kanban board instead of below it — both simple placement/UX requests, no data-model changes.
- **Verified**: `npx tsc --noEmit` (server + client) clean; `npm test -w server` (90 tests, up from 85 before this milestone — 5 focused `updateTask`/`afterTaskId` cases added to `tasks.test.ts`: move-to-front, move-after-a-task, reorder+status-change commit message, reorder to an unknown id 404s, and an explicit backward-direction case (`done` → `todo`) proving the drag-driven status+reorder path has never had a directional restriction). Verified live and repeatedly against the actual `~/pivot-demo` workspace while the user had their own `npm run dev` Electron session open against it (server on :4174 + Vite on :5173 were already running as theirs — never restarted, and mutations made for verification were always reverted back to the state I found, leaving the user's own concurrent edits untouched): created a project with a hand-picked custom hex via the new modal and confirmed the exact value landed in frontmatter and rendered on the project row/card; the (originally single-select, later multi-select OR) tag filter correctly isolated projects and composed with "Show archived"; the Edit-project modal opened pre-filled with no page-shift and closed cleanly via Escape without saving. Real mouse-drag simulation isn't supported by this sandbox's browser-automation tool (CDP mouse events don't synthesize native HTML5 `dragstart`/`dragover`/`drop`), so the drag path itself was exercised by dispatching real `DragEvent`s with a `DataTransfer` from the page's own console against the live UI: a forward move (Todo → Doing) confirmed status/timer/file-order/git-commit all correct; after the drop-zone fix, a drop ~900px below a short column's own rows (previously dead space) confirmed `drag-over` highlighting and a successful drop; each test mutation was reverted afterward via the API.

## Milestone 18 notes, part 5 (open workspace folder button)
- Small user-requested addition to each workspace row on Settings' list: a folder icon-button (same icon shape as `AppShell`'s own "Projects" nav item, for visual consistency) that reveals that workspace's folder in the OS's default file manager — a convenience for finding/hand-editing the markdown files directly, which fits this app's own "markdown must stay portable and hand-editable outside the app" principle (CLAUDE.md) rather than fighting it.
- **Another native-OS capability, so it goes through the preload bridge** like `pickFolder`/launch-at-login/reminder settings before it (CLAUDE.md: "The only things that go through the `preload.ts` bridge are what a browser genuinely can't do"). `electron/src/preload.ts` and `client/src/lib/pivotBridge.ts` both gained `openWorkspaceFolder(path): Promise<boolean>` (hand-duplicated between the two, same reasoning as every other bridge method — separate npm workspaces/tsconfigs); `main.ts`'s `ipcMain.handle('pivot:open-workspace-folder', ...)` calls `shell.openPath(path)`, which resolves to `''` on success or a human-readable error string on failure (never rejects) — translated to the plain boolean the bridge contract promises, with the raw error logged server-side for debugging.
- **Electron-only, hidden not disabled** when there's no bridge (a plain browser tab has no OS file manager to hand off to) — same pattern as the "+ Open folder" add-workspace button and the reminder/launch-at-login sections. A failure (folder moved/deleted since being registered) surfaces as an inline `field-error` below the workspace list, cleared on the next attempt.
- **Verified**: `npx tsc --noEmit` clean for `server/`, `client/`, and `electron/` (including `npm run build -w electron`, which actually compiles `main.ts`/`preload.ts` — this feature touches both); `npm test -w server` (94, unaffected — no server-side surface here at all, purely an Electron+client change); `en.json`/`vi.json` stayed structurally identical (178 leaf keys each, up from 176). Not click-tested inside a running packaged/launched Electron window in this pass (would need the user's own dev session restarted, which — per the same reasoning as milestone 18 parts 3 and 4 — wasn't this session's call to make unprompted); `shell.openPath` is a standard, stable Electron API and the IPC wiring here is structurally identical to `pickFolder`'s already-live-verified round trip (milestone 3), so this rests on that precedent rather than a fresh live pass.

- **`lib/vaultGit.ts` gained `isGitAvailable()`** (`git --version`, wrapped in try/catch — `false` on anything from git missing to a broken PATH). Each snippet has its own `navigator.clipboard.writeText` copy button (`.ws-row-btn`, reused rather than a new button style) with a transient "Copied!" state; a clipboard-permission failure is swallowed silently since the snippet is still plain selectable text in a `<pre>`.

## Milestone 18 notes, part 3 (auto-refresh after an out-of-band vault change)
- User-reported gap, not in PLAN.md's original milestone-18 scope: an already-open UI never picked up a change made outside its own mutations — most concretely, an MCP agent writing to the same workspace from a separate process (per PLAN.md's own "MCP is decoupled from whichever workspace the app has open" — a real, separate process, not something the running Express server hears about in-process). `main.tsx`'s query defaults (`staleTime: 10_000`, `refetchOnWindowFocus: false`) were deliberate for the reasons stated there, but neither refetches on its own, so nothing closed this gap by accident.
- **Mechanism decided with the user up front** (CLAUDE.md: check before introducing a new convention) — presented as a choice between filesystem-watching + push (SSE), a plain polling interval on existing queries, and polling a cheap "did anything change" signal; the user picked the third: **poll the workspace's git HEAD commit hash**. Every write, from either front door, is already a commit (PLAN.md "Backup & recovery"), so a changed HEAD is a reliable, cheap-to-compute signal that something external touched the vault — no new dependency (chokidar/ws), no watcher-lifecycle-across-workspace-switches complexity.
- **`lib/vaultGit.ts` gained `getHeadCommit(workspacePath)`** (`git rev-parse HEAD`, `null` for a repo with no commits yet) and a new `GET /api/vault/head` route (`routes/vault.ts`) wrapping it.
- **`client/src/components/VaultChangePoller.tsx`** (new, renders nothing, mounted once in `AppShell` alongside `WorkspaceSwitcher`/`CalendarSidebar`): polls `/api/vault/head` every 4s (`staleTime: 0` on that one query — it must never answer from cache) and, when the hash differs from the last one seen, calls `queryClient.invalidateQueries()` with no key — the same "something changed, re-fetch everything" pattern `WorkspaceSwitcher` already uses for a workspace switch, cheap enough against a personal local vault not to bother picking specific query keys. The very first resolved hash is only recorded, never treated as a change (a `useRef` starting at `undefined`, distinct from a real `null`/hash value).
- **Verified**: `npm test -w server` (93 tests, up from 92 — one new case in `vaultGit.test.ts` covering `null` → hash → next-hash across commits); `npx tsc --noEmit` clean for `server/` and `client/`. **Verified live end-to-end**, but in an isolated scratch sandbox rather than against the user's own running dev session (its Express server is spawned once by Electron via plain `tsx`, not `tsx watch`, so it wouldn't have had the new route until restarted, and killing/restarting a session the user might have open wasn't this session's call to make without asking): a scratch `$HOME` (isolated `~/.pivot/config.json`) and a throwaway workspace, driving a genuinely separate MCP server process (`server/src/mcp/index.ts` via a real stdio client, mirroring milestone 10's own verification style) to call `create_task` — confirmed the already-running (third, independent) Express server's `/api/vault/head` picked up the new hash immediately, tagged `[mcp:create_task]` in `git log`. The user then restarted their own dev session, moved a task todo→doing via a live MCP tool call in this same conversation against their real `Pivot Demo` workspace, and confirmed the open UI updated on its own — real end-to-end confirmation, not just the isolated sandbox test.

## Milestone 18 notes, part 2 (Dashboard: quick-add, recent projects, task search)
