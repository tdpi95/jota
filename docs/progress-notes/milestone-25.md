- Requested by the user after a design conversation about what an MCP agent can/can't answer today ("what's the IP range of the bank", "how to run this command", arbitrary questions about note content): note/journal bodies were never cached in the index (title/tags and a `has_body` flag only), there was no search across tasks+notes+journal at once, and no search tool combined free text with a date range. Task `description` was already cached and already substring-searched — that part needed no change.
- **Schema** (`server/src/lib/index/db.ts`): added a `body TEXT NOT NULL DEFAULT ''` column to both `journal_entries` and `notes`, plus three standalone FTS5 virtual tables — `tasks_fts(id UNINDEXED, project_slug UNINDEXED, text, description, tags)`, `notes_fts(slug UNINDEXED, title, tags, body)`, `journal_fts(date UNINDEXED, tags, body)`. Confirmed FTS5 is actually available in this project's `node:sqlite` build before committing to the design (a throwaway script exercising `CREATE VIRTUAL TABLE ... USING fts5`, `MATCH`, `bm25()`, and `snippet()` all worked). Not "external content" FTS5 tables (no `content=` option) since the natural keys here (task id, note slug, journal date) aren't integer rowids — kept in sync by explicit delete-then-insert during reconciliation, matching the plain-table upsert pattern already used everywhere else in `reindex.ts`, rather than triggers.
- **Migration gotcha caught before it shipped**: the existing `checklist`-column migration pattern (`ALTER TABLE ... ADD COLUMN ... DEFAULT` on an already-open index, swallowing the "duplicate column" error on repeat opens) isn't sufficient on its own for `body` — reconciliation skips reparsing a file whose `source_mtime` hasn't changed, so an *existing, untouched* note/journal entry would keep an empty `body` (and be unsearchable) forever after upgrading, never just until the next reconcile. Fixed by also zeroing `source_mtime` on every existing row of `journal_entries`/`notes`, but only in the branch where the `ALTER TABLE` actually just added the column (not on a workspace whose index already has it) — the next `reconcileWorkspace` then sees every such row as "changed" (no real file mtime is ever exactly `0`) and reparses it for real. Covered by a dedicated test (`reindex.test.ts`) that seeds a legacy-shape `journal_entries` row already at the file's real current mtime, confirming this exact "unchanged file, needs backfill anyway" case actually gets backfilled, not just the empty-index case the `checklist` migration's own test covers.
- **Cross-type query** (`server/src/lib/index/queries.ts`): `queryFullTextSearch(workspacePath, {query, from?, to?, types?})` runs one `MATCH` query per requested FTS table (all three if `types` omitted), each joined back to its real table for full field access and a `snippet(..., -1, '**', '**', '…', 12)` excerpt, independently date-filtered (task: `relevantDateOf` — the same done/due/created field `get_task_summary` already uses; note: `updated`; journal: the entry's own date), then merged and sorted by date descending and capped at 50 (same cap `querySearchTasks`/`querySearchNotes` already use). Sorted by date, not `bm25()` relevance — a virtual table's relevance score isn't comparable to another virtual table's, so "relevance across three separate corpora" isn't a single meaningful ranking; recency is the same tie-break every other aggregate view here already uses.
- `toFtsMatchQuery` quotes each whitespace-separated token as an escaped literal phrase and joins with FTS5's default implicit `AND`, specifically so ordinary text containing FTS5 query syntax (bare `AND`/`OR`/`NOT`, `*`, `column:`, unbalanced quotes — a version string, a path, "C++") is matched literally instead of throwing a syntax error.
- **New service** `server/src/services/search.ts` (`searchEverything`) — its own module rather than folded into `services/{tasks,notes,journal}.ts`, since it crosses all three; same "aggregate queries get their own isolated file" precedent as milestone 9's `lib/index/queries.ts`. Empty/whitespace-only query returns `[]`, same convention as `searchTasks`/`searchNotes`.
- **REST**: `GET /api/search?q=&from=&to=&types=` (`server/src/routes/search.ts`, mounted at `/api/search`), `types` as a comma-separated list.
- **MCP**: new `search_everything({query, dateRange?: {from, to}, types?})` tool (`server/src/mcp/tools.ts`) — the one tool that combines free-text search with a date range, which nothing else does (`get_task_summary`'s `dateRange` filters structured counts, not text). Existing `search_tasks`/`list_notes` tools needed no interface change to start matching body/description too, now that it's cached and FTS-searchable.
- Left genuinely open per PLAN.md's note (not decided unilaterally): whether `search_everything` should also cover project name/description — out of scope for the initial pass, task/note/journal was the explicit ask. (Resolved in a same-milestone follow-up below.)

## Follow-up: a real bug — "search 112.109.92.22 in Everything shows nothing, but it's in my OCB note" (same session)

- **Reproduced against the user's actual real running server/workspace** (not a scratch instance — the user pointed at their own live `Everything` workspace and a real search miss): `GET /api/search?q=112.109.92.22` on their real, already-running dev server returned `results: []`, even though the phrase genuinely existed in a note titled "OCB". `GET /api/index/status` showed `lastReconciledAt` from *before* this session's schema work — meaning nothing had reconciled that workspace since the `body`/FTS columns were added, despite the server process having been up (and presumably restarted via `tsx watch` picking up the code changes) the whole time.
- **Root cause, found by tracing every call site of `reconcileWorkspace`**: it is only ever invoked from a *write* path — `services/{tasks,notes,journal,projects,sync}.ts`, plus the vault revert route. Nothing calls it when a workspace is opened or switched (`services/workspaces.ts`'s `addWorkspace`/`openWorkspace` never did, confirmed by reading them directly), and nothing calls it at process boot for whatever workspace is already active (`index.ts`'s `startServer` just calls `app.listen()`). This directly contradicts what PLAN.md's "Sync strategy" section has said from the start — "Startup/open-time reconciliation (runs whenever a workspace is opened, **not just process boot**)" — which turned out to describe intended behavior that was never actually wired in. It happened to not matter until now because every previous milestone's index changes only affected *new* writes going forward; this was the first time an existing, unindexed field needed on-demand backfilling for content nobody was actively editing.
- **Immediate fix for the user**: `POST /api/index/rebuild` against their real, already-running server (safe and fully reversible — the index is explicitly a derived, always-rebuildable cache, never a source of truth) — confirmed this alone made the IP searchable immediately, without touching any of their actual vault files.
- **Root-cause fix**: `services/workspaces.ts`'s `addWorkspace` (both branches — a brand-new registration over an existing populated folder, and the "adopt an already-registered path" delegation to `openWorkspace`) and `openWorkspace` itself now call `reconcileWorkspace`, best-effort (log-and-continue on failure, same convention as every write path). `index.ts`'s `startServer` additionally reconciles whatever workspace is already active right after the HTTP server starts listening — this is the half that specifically covers "the app was just restarted with the same workspace still active," which is arguably the *most* common real-world case and the one that actually bit the user here (not a fresh add/switch).
- **Verified**: `npm test -w server` — 151/151 passing (up from 149): two new `workspaces.test.ts` cases — `addWorkspace` over an existing folder with an un-indexed project file indexes it immediately, and re-`openWorkspace`-ing after a file was dropped onto disk while another workspace was active picks it up, both without any explicit `reconcileWorkspace`/`rebuild` call from the test. `npx tsc --noEmit` clean (server/client/electron).
- **Verified live**, twice: (1) against the user's actual real server — reproduced the miss, ran the rebuild, confirmed the fix, all against their real `Everything` workspace (read-only from the vault's perspective; only the derived `.sqlite3` cache was touched). (2) against a freshly built isolated scratch reproduction of the exact bug scenario — a hand-written `~/.jota/config.json` pointing at an already-"active" workspace containing a note with the target IP, `.jota/cache` deliberately absent (simulating "never indexed") — started the scratch server fresh with **no** explicit rebuild call, and confirmed `GET /api/search` found the note immediately purely from the new startup-reconcile code, proving the actual fix (not just the one-time manual workaround) works. Scratch server and temp directories torn down afterward.

## Follow-up: whole-word-only matching — "zago" should match "zagoo" (same session)

- User reported the search was matching whole words only — typing "zago" found nothing even though "zagoo" existed in a note.
- **Cause**: `toFtsMatchQuery` quoted every token as an exact literal phrase (`"zago"`), which FTS5 matches as that exact token — not a prefix. Confirmed empirically (a throwaway script against this project's `node:sqlite` build) that the correct FTS5 syntax for a prefix query on a quoted/escaped phrase is the `*` placed **outside** the closing quote — `"zago"*` — not inside it (`"zago*"`, which SQLite treats as a literal, non-matching character sequence and silently returns nothing, no error). Multi-token queries compose correctly with this too: `"foo"* "bar"*` still ANDs the two prefix conditions.
- **Fix**: `toFtsMatchQuery` (`lib/index/queries.ts`) now appends `*` after each token's closing quote. An exact whole-word query still matches (a full word is trivially its own prefix), so this is a strict superset of the old behavior, not a behavior swap.
- **Verified**: `npm test -w server` — 152/152 passing (up from 151): a new `services/search.test.ts` case confirms `query: 'zago'` finds a note containing "Zagoo" (case-insensitive too, per the existing `COLLATE`-equivalent FTS5 default). `npx tsc --noEmit` clean.
- **Verified live**, twice: against the user's actual real running server (`tsx watch` auto-picked up the change) — confirmed the exact IP search from the previous follow-up still returns its one result, and a truncated prefix of it (`112.109`) now also matches; and against a fresh isolated scratch server reproducing the user's literal example — created a note containing "Zagoo", searched "zago", got the note back with `**Zagoo**` correctly bolded in the snippet. Scratch server and temp directory torn down afterward.
