## Follow-up: conflict resolver (2026-09-24)

- User report: the Sync panel said "Some files changed on both sides since the last sync and were left untouched — resolve manually, then sync again", followed by a bare list of paths. The user couldn't tell what changed in each file, where the conflicts were, or how to resolve them. The old notice's "resolve manually" meant editing both copies outside the app until they matched, with no view of either side.
- Two forks confirmed via `AskUserQuestion` before building: **resolution actions** (keep mine / keep theirs / hand-merged version, vs. whole-file keep-one-side only, vs. diff only — chose all three), and **a last-synced copy per text file** for a true three-way view (vs. two-way only — chose three-way). Full design in PLAN.md, "Resolving a conflict".

### Backend

- `server/src/lib/textMerge.ts` (new): Myers line diff (common prefix/suffix trimmed first; the edit distance is capped at 2000, and past that the differing middle is reported as one delete-all/insert-all block, which keeps the trace's ~D² memory bounded), `diffHunks` (unified-style, 3 lines of context, nearby changes joined into one hunk), `merge3` (diff3-style walk over stable/unstable regions: one side changed → take it; both made the same change → take it once; otherwise a `conflict` chunk with base/local/remote), and `merge2` (the no-base fallback, where every difference is a conflict). Pure, no git dependency.
- `lib/sync/webdav.ts`: base snapshots under `.jota/cache/webdav-base/`, written at every point a baseline entry is recorded and removed wherever one is deleted. `resetSyncState` clears the snapshot dir too. `computeDiff` backfills a missing snapshot for a same/same file from the local copy (cheap, local disk only), so workspaces synced before this change start getting three-way views without a re-sync. New `getConflict` and `resolveConflict` work on a single path: a local stat plus a remote `stat` PROPFIND on that one file, never the full-tree listing. A `created`/`created` file whose contents turn out identical gets its baseline recorded, and `getConflict` returns `null`, the same as `computeDiff`'s content-compare. `isValidSyncPath` rejects empty, absolute, `..`, backslash, and dot-segment paths, so the resolve route can't be used to write under `.git`/`.jota` or outside the workspace.
- Optimistic concurrency: `getConflict` returns `version = {localMtimeMs, remoteEtag}`, and `resolveConflict` refuses (`reason: 'changed'` → 409) if either side moved since. It checks this before any write.
- `services/webdavSync.ts`: `getConflict` (404 when the file isn't in conflict) and `resolveConflict`. A resolution that rewrites or deletes the local file commits it (`[api] webdav resolve <path>: kept the server's version` etc.) and reconciles the index. A plain pull doesn't commit to git; a resolution does, because it's the one path where the user explicitly chooses to throw local content away, so it needs to be undoable.
- `routes/webdavSync.ts`: `GET /conflict?path=`, `POST /conflict/resolve`.

### Frontend

- `components/WebdavConflictModal.tsx` (new), opened from a per-file "Resolve…" button in Settings' conflict list. `Modal` gained a `wide` prop (`.modal--wide`, 880px). The conflict list now reads only `webdavStatusQuery.data.conflicts`. It used to prefer a push/pull mutation's own result, which would have kept showing a file after it was resolved.
- Merge tab: unchanged runs over 8 lines collapse to 3 + 3 with a "Show N unchanged lines" expander. Each conflict spot offers this device's / the server's / "Keep both" (hidden when both sides carry the same `<!-- id:... -->` token — found while testing live: on a task line both sides had edited, keeping both would have duplicated the task id) and a `<details>` for the base lines. "Edit the text by hand" starts from the current draft with markers for unpicked spots, and Save stays disabled while any line starts with a 7-char marker.
- i18n: `settings.sync.webdav.conflict.*` (en + vi), `resolve`, and a rewritten `conflictNotice`. Plural-free phrasing ("{{count}} spot(s)") so `en.json`/`vi.json` stay structurally identical (355 leaf keys each). CSS reuses `--good-soft`/`--danger-soft`/`--surface-muted` only, with no new theme tokens.

## Follow-up: no false conflicts when only this device changed (2026-09-24)

- User report, right after the resolver shipped: "there is actually no update on server, only changes from local. it would be tedious to resolve conflicts on every push."
- **Diagnosed read-only against the live Nextcloud workspace** (`~/Documents/Jota/Everything`): the current `.jota` baseline's etags all matched the server (no etag churn). But 3 files (`projects/general-work.md`, `paymentservice.md`, `poco-development.md`) had **no baseline entry at all**. Cause: the Poco→Jota rename (`0b29d8f`) changed the per-workspace folder from `.poco/` to `.jota/` with no migration, so the old `.poco/cache/webdav-sync-state.json` was orphaned. On the first sync after the rename, every file still identical on both sides was silently re-baselined by the content-compare. The files edited locally since the last sync differed from the server, had no baseline to tell which side moved, and were reported as `created`/`created` conflicts. For all 3, the orphaned baseline's etag equalled the server's current etag, and the server's bytes matched a blob in local `git log --raw` for that path, so the server really was unchanged.
- **Fix** (`lib/sync/webdav.ts`): the no-baseline branch of `computeDiff` checks `vaultGit.isInFileHistory` on the server bytes before declaring a conflict. On a match it records `{localMtimeMs: 0, remoteEtag}` as the baseline (0 never equals a real mtime, so the local side keeps reading as `modified` until pushed), writes the server bytes as the base snapshot, and reports a plain push. A new `refineBothChanged` pass does the same for `modified`/`modified` entries, in order: identical bytes → both same; server equals the base snapshot → server same; local equals the base snapshot → local same (lets a real server edit pull cleanly); server in local git history → server same. It only fetches files that are already conflict candidates, never the whole tree. No migration of the old `.poco/` state was added: the current `.jota` state already exists for the affected workspace, so a "fall back to `.poco`" migration would never trigger, and the git-history check covers this and any future baseline loss.
- **Verify**: `npm test -w server` 204/204, with 4 new `webdav.test.ts` cases: a lost baseline where the server has an older committed version → push, not conflict; a lost baseline where the server has content this device never had → still a conflict, server untouched; a server rewrite with identical bytes (new etag) plus a local edit → push; an identical local rewrite (new mtime) plus a real server edit → pull. A mutation check confirmed three of these fail with the new checks disabled; the "never had" case is the guard that stays a conflict either way. Dry run against the live Nextcloud data, using a scratch copy of the workspace and a `status` call only (reads the server, writes nothing to it): the old behaviour showed 3 conflicts, the new one reports `{toPush: 7, toPull: 0, conflicts: []}`. The user's real workspace wasn't pushed to or modified.

## Follow-up: clickable "N to push" / "N to pull" (2026-09-24)

- User request: "show which files are pushed/pull when clicking on x to push/x to pull".
- `status` now also returns `pushFiles`/`pullFiles` (`{path, change: 'added'|'modified'|'deleted'}`, sorted), built from the same diff entries that produce the counts, so a list is exactly what the next push or pull transfers. `toPush`/`toPull` are kept and now equal the list lengths. There's no extra request or server cost: the diff was already computed for the counts.
- Settings: the two counts are `.sync-count-btn` toggles (dotted underline, accent color while open, disabled at 0) opening a `.sync-pending-list` under them, one row per file with a colored ADDED/MODIFIED/DELETED label (`settings.sync.webdav.change.*`, en + vi, 358 leaf keys each). The list reads from the live status query each render, so it empties itself after a push or pull.
- Verify: `npm test -w server` 205/205. The new `webdav.test.ts` case covers an added, a modified, and a deleted file to push plus a modified and an added file to pull, and asserts the lists equal the paths `push`/`pull` then actually report as synced. The 5 older tests that compared a whole status object now compare only the count fields. Client `tsc` and `vite build` are clean. Verified live on the isolated scratch stack (a temporary `launch.json` entry, removed afterwards): "2 to push" listed ADDED `projects/groceries.md` and MODIFIED `projects/website.md`; "1 to pull" listed ADDED `notes/phone-idea.md`; after Push the count went to 0, the button disabled, and the open list emptied.
