# Milestone 5 notes

[← back to PROGRESS.md](../../PROGRESS.md)

- `server/src/lib/vaultGit.ts` — `commitChange(workspacePath, {origin, message, paths?})` stages the given paths (or `-A` for the one-time initial commit) and commits as `[origin] message` (e.g. `[api] update_task t_9f0e21 status todo→doing (website-redesign)`); best-effort like the rest of the write path — logs and returns on any failure (git missing, nothing staged) rather than throwing, since the file write it follows already succeeded and is authoritative. `getHistory`/`getDiff` are read-only (`git log`/`git show`); `revertCommit` (`git revert --no-edit`) is the one function here that *does* throw on failure (with git's own stderr), since a user-invoked revert failing silently would be worse than a file write's git commit failing silently.
- `ensureGitHistory(workspacePath)` (also in `vaultGit.ts`) reuses `lib/workspaces.ts`'s `ensureGitRepo` and then makes the one-time "initial commit of whatever's already there" PLAN.md calls for — idempotent (checks `getHistory(...).length > 0` first). `services/workspaces.ts`'s `addWorkspace`/`openWorkspace` now call this instead of the bare `ensureGitRepo`, so every workspace has real git history from the moment it's added, not just an empty `.git/` — needed for `history`/`diff`/`revert` to have anything to operate on. `ensureGitRepo` itself gained a companion `ensureGitIdentity` check (sets a local `pivot`/`pivot@localhost` identity only if neither a local nor global one already resolves) so commits succeed in a fresh environment with no global git config, without ever overriding a real one.
- `server/src/routes/vault.ts` — `GET /api/vault/history?path=&limit=`, `GET /api/vault/diff/:commit`, `POST /api/vault/revert/:commit`, all thin wrappers over `vaultGit.ts`; revert also re-runs `reconcileWorkspace` afterward (best-effort, PLAN.md "Recovery surface" — index self-heals for the reverted file(s)).
- `services/workspaces.ts` gained `getActiveWorkspaceOrThrow` (structured 400 instead of `null`) — shared by both `routes/index.ts` and `routes/vault.ts`, which only make sense against a currently-open workspace.
- **Bug found and fixed while wiring this up**: `lib/markdown/frontmatter.ts`'s `parseFrontmatter` returned js-yaml's native `Date` objects for any unquoted `YYYY-MM-DD` frontmatter scalar (e.g. hand-typing `created: 2026-09-10` with no quotes — exactly how a human would naturally write it, per CLAUDE.md "must stay hand-editable"). That's invisible in milestone 1's own round-trip fixture (which happens to quote its dates) but broke milestone 4's index writes the moment a real unquoted date reached SQLite ("Provided value cannot be bound to SQLite parameter"). Fixed by recursively normalizing any `Date` found in parsed frontmatter back to `YYYY-MM-DD` inside `frontmatter.ts` itself (the one place PLAN.md says the YAML library's quirks should be isolated) — covered by `frontmatter.test.ts`.
- Verified live: seeded a scratch workspace with a project + journal file (deliberately using unquoted frontmatter dates to catch the bug above), committed the project creation and a later status-change edit as two separate commits, confirmed `GET /api/vault/history` lists both with the `[origin] message` format; `GET /api/vault/diff/:commit` on the status-change commit showed exactly the one changed line; `POST /api/vault/revert/:commit` restored the file to `[ ]` (todo) and appended a `Revert "..."` commit to history; confirmed the index (`GET /api/index/status`) reflects the reverted state afterward.
